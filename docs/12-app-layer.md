# Слой приложения: окна, экраны, навигация, маршруты

**Статус: предложено (2026-09-28), на обсуждение.** Кода нет. Вопросы, по которым нужно
решение, собраны в конце и пронумерованы.

## Зачем и где граница

Сейчас Espalier — библиотека для экранов внутри обычного UIKit/AppKit-приложения: окно,
контроллеры, навигацию, меню делает приложение, а ноды живут в `NodeView`/`NodeNSView`. Так
и остаётся — это **первый способ**, и он не становится вторым сортом.

**Второй способ** — своё приложение целиком, как в SwiftUI: точка входа, окна, экраны,
стек навигации, вкладки, боковая панель, маршруты, deep links, меню, команды уровня окна и
приложения. Пишется один раз для iPhone, iPad, Apple TV и Mac.

Правила границы:

1. **Слой приложения стоит только на публичном API нижних модулей.** Всё, что ему нужно от
   `Nodes` и адаптеров, сначала становится публичным API там (список — ниже, «Что нужно от
   нижних модулей»). Тогда первый способ получает те же возможности, и слой приложения
   нельзя «сломать изнутри».
2. **Можно смешивать в обе стороны.** Стек экранов на нодах встраивается в UIKit-приложение
   как обычный `UIViewController`; экран приложения на нодах может показать готовый
   `UIViewController`/`NSViewController`.
3. **Системное поведение не переписываем.** Свайп назад, панели навигации, вкладки, боковая
   панель iPad и Mac, кнопка Menu на пульте, восстановление окон — у системных контейнеров.
   Экраны рисуют ноды, а контейнеры — система (вопрос 1).

## Что взято из Weave, а что нет

Weave (`/Users/resoul/projects/v2/Weave`) — прошлая попытка своего SwiftUI. Взгляд на её
устройство:

| В Weave | Берём | Меняем — почему |
|---|---|---|
| `Application` с `@main`, `compose()` собирает сцены через result builder; платформа выбирается в одном месте | да: протокол, `@main`, декларативный список окон | без асинхронных фабрик сцен, политик сбоя запуска и отчёта о запуске — для первой версии лишнее |
| `WindowScene` + `Window` + `Router` сцены | одно понятие `Window` (описание окна) | сессии сцен и `UIWindowScene` — дело адаптера, пользователю не видны |
| `Controller<N, A, R>` + `ViewModel` + `Action`/`Route`-трубы + `Coordinator` + `ScreenRegistry` с асинхронными фабриками | маршрут как значение, «маршрут → экран» | пять понятий на один экран; три generic-параметра тянут стирание типов (`AnyController`) повсюду; асинхронная фабрика потребовала защиты от устаревших переходов. У нас: `Screen` (нода) + обычные объекты модели на `StateCore` + одна функция «маршрут → экран» |
| Зависимость от Flux для состояния и событий | нет | `StateCore` и `async`/`await` уже есть |
| `NavigationController`, нарисованный нодами: `animated` игнорируется, свайпа назад нет, Menu на TV и панели — свои | нет | системные контейнеры: `UINavigationController`, `UISplitViewController`, `UITabBarController`, `NSSplitViewController` (вопрос 1) |
| Машина состояний жизни на 8 состояний у каждой ноды и контроллера | нет | у нод уже есть монтирование и задачи показа (04); экрану — «появился / ушёл» |
| `CommandRegistry` с областями, отдельный от фокуса | нет | уже заменён командами по цепочке фокуса (03, «Команды»); слой приложения продлевает цепочку до окна и приложения |
| `DeepLinkPipeline`: очередь до готовности приложения, проверки доступа | очередь холодного старта | без вечного списка «уже виденных»: в Weave одну и ту же ссылку нельзя открыть второй раз |
| Восстановление навигации повтором маршрутов через фабрику | да | экраны всегда строятся из маршрутов, не из сохранённых объектов |
| Запоминание фокуса при уходе с экрана и возврат при `pop` | да | в UIKit это делает система; на Mac — наш контейнер |

## Модель

### Приложение и окна

```swift
@main
struct MailApp: Application {
    let store = MailStore()

    var windows: [Window] {
        Window("main", title: "Mail") {
            Split(sidebar: MailboxesScreen(store: store)) {
                Stack(root: MailRoute.inbox) { route in store.screen(for: route) }
            }
        }
    }

    var menuBar: MenuBar {
        MenuBar {
            Menu("Message") { Command.newMessage; Divider(); Command.flag; Command.archive }
        }
    }

    func open(_ url: URL) -> Bool { ... }   // deep link
}
```

- `Application` — протокол; экземпляр создаётся один раз при запуске и живёт всё время
  работы. `windows` — какие окна есть: на iPhone и TV показывается первое, на iPad и Mac
  приложение открывает ещё (`openWindow("compose", route: ...)`).
- `Window` — описание окна: id, заголовок, корневой контейнер. Одно описание может дать
  несколько настоящих окон (как `WindowGroup`): каждое со своим состоянием навигации.
- `menuBar` — модель меню, которая уже есть (`MenuBar`, 03). Стандартные меню (приложение,
  Правка, Окно, Справка) слой добавляет сам, приложение — свои.

### Экран

```swift
final class InboxScreen: Screen {
    init(store: MailStore) {
        super.init()
        title = "Inbox"
        toolbar = [.newMessage, .flag]
        handle(.flag, isEnabled: { !table.selection.isEmpty }) { ... }
    }

    override func appeared() { ... }
    override func layoutSpec() -> LayoutSpec? { ... }
}
```

- `Screen` — подкласс `Node` (вопрос 3): корень дерева одного экрана, то, что лежит в стеке
  или во вкладке. Сверху — то, что нужно контейнеру: `title`, `toolbar`, `appeared()` /
  `disappeared()`, `navigation` — стек, в котором экран лежит (как `navigationController` у
  `UIViewController`).
- **Кнопки панели — команды.** `toolbar: [Command]`: заголовок, сочетание и включённость
  берутся из той же модели, что меню и клавиши. Команда, выключенная для меню, выключена и
  на панели.
- Состояние экрана — `StateCore` в самом экране или в объекте модели. Отдельного
  `ViewModel`-протокола нет: кто хочет MVVM, делает его обычным классом.
- Зависимости передаются через `init`. Окружения со скрытым внедрением нет; тема и условия
  показа уже приходят через `NodeHost`.

### Маршруты и стек

```swift
enum MailRoute: Hashable, Codable {
    case inbox
    case message(Mail.ID)
    case compose(draft: Draft.ID?)
}

let stack = Stack(root: MailRoute.inbox) { route in
    switch route {
    case .inbox: InboxScreen(store: store)
    case .message(let id): MessageScreen(id: id, store: store)
    case .compose(let draft): ComposeScreen(draft: draft, store: store)
    }
}

stack.push(.message(id))
stack.pop()
stack.path = [.inbox, .message(id)]   // deep link, восстановление
```

- **Источник правды — `path: [Route]`** (значение `StateCore`, видно в `layoutSpec()` и
  наблюдателях). Контейнер сводит показанные экраны с путём: новые элементы строятся функцией
  «маршрут → экран», ушедшие отпускаются, общие остаются теми же объектами. Один маршрут
  может стоять в пути дважды.
- Возврат пользователем — свайп, кнопка «назад», Menu на пульте, Cmd-[ на Mac — меняет
  `path` после завершения перехода; прерванный свайп путь не меняет.
- Экран строится **синхронно**. Экран, которому нужны данные, показывает заглушку и грузит
  сам: без асинхронных фабрик нет и переходов, устаревших к концу загрузки (вопрос 7).
- Маршрут — тип стека (`Stack<MailRoute>`). У приложения может быть один тип на всё или свой
  у каждого стека (вопрос 4).

### Контейнеры

| Наше | iPhone / iPad | Apple TV | Mac |
|---|---|---|---|
| `Window` | `UIWindowScene` + `UIWindow` | то же | `NSWindow` + `NSWindowController` |
| `Screen` | `UIViewController` с `NodeView` | то же | `NSViewController` с `NodeNSView` |
| `Stack` | `UINavigationController` | то же; Menu возвращает | свой контейнер: переход сдвигом, «назад» в панели окна, Cmd-[ |
| `Tabs` | `UITabBarController` (на iPad — с боковой панелью) | вкладки сверху | `NSTabViewController` или переключатель в панели окна |
| `Split` | `UISplitViewController`; на iPhone сворачивается в стек | нет, показывается основная часть | `NSSplitViewController` с боковой панелью |
| модальный показ | `present` (лист, на весь экран) | на весь экран | лист окна (`beginSheet`) |
| `toolbar` | `navigationItem`, кнопки панели | нет | `NSToolbar` |
| `menuBar` | `UIMenuBuilder` | нет | `NSApp.mainMenu` |

На Mac системного стека навигации нет; его делает адаптер, и ему же запоминать фокус при
уходе с экрана.

### Команды на уровне окна и приложения

Сейчас команда идёт от ноды с фокусом наружу до корня дерева (03, «Команды»). Слой
приложения продлевает цепочку:

```
нода с фокусом → … → корень экрана (Screen) → контейнеры (Stack, Split, Tabs) → окно → приложение
```

- `Stack` сам выполняет `Command.back`, пока в пути больше одного маршрута. На корне стека он
  выключен и отдаёт «назад» дальше: внешнему стеку, а на TV — системе, то есть выход из
  приложения. Вложенные стеки работают без кода в приложении.
- Окно выполняет «Закрыть окно»; приложение — «Новое окно», «Настройки», команды без экрана.
  Приложение объявляет обработчики так же: `handle(.newMessage) { ... }`.
- Меню и панели включают пункт по тому же `canPerform`.

### Жизнь экрана и приложения

- `Screen.appeared()` / `disappeared()` — по завершении перехода, как `viewDidAppear`. Задачи
  показа нод (04) уже заканчиваются, когда нода уходит с экрана.
- `Application.phase` — `.active`, `.inactive` или `.background`; это значение `StateCore`,
  на него можно подписаться.
- Окно закрыто — его экраны отпускаются, их задачи отменены.

### Deep links и восстановление

- `Application.open(_ url:) -> Bool` получает ссылку. Приложение переводит её в маршрут и
  ставит путь: `stack.path = [.inbox, .message(id)]`. На холодном старте адаптер держит
  ссылку, пока не построено первое окно, потом отдаёт.
- Маршрут `Codable` → окно сохраняет пути своих стеков, выбранную вкладку и открытую боковую
  панель: в сессию сцены на iOS и в восстановление окна на Mac. При запуске ставит их
  обратно, экраны строятся заново функцией «маршрут → экран». Сохранённых объектов нет.

### Вместе с UIKit и AppKit

```swift
// Стек экранов на нодах внутри обычного UIKit-приложения.
let stack = Stack(root: MailRoute.inbox) { ... }
window.rootViewController = stack.makeViewController()

// Готовый UIKit-экран внутри стека на нодах.
case .settings: ControllerScreen(SettingsViewController())
```

`makeViewController()` / `ControllerScreen` есть в адаптерах UIKit и AppKit. `Application`
для этого не нужен: можно взять только стеки и экраны.

### Проверка без окон

Логика контейнеров — путь, команды «назад», включённость пунктов, сведение экранов с путём
— живёт в модуле без UIKit/AppKit и проверяется `swift test` на Mac и Linux. Адаптеры
только применяют результат к системным контейнерам и проверяются в Simulator и UI-тестами
демо.

## Модули

Название продукта в имени нельзя, `App` — протокол SwiftUI (та же проблема, что с `Layout`).
Предложение (вопрос 2):

```
AppShell         Application, Window, Screen, Stack, Tabs, Split, путь и маршруты, цепочка
                 команд окна и приложения. Без UIKit/AppKit; зависит от Nodes и StateCore.
AppShellUIKit    системные контейнеры UIKit (iOS, iPadOS, tvOS, Catalyst), точка входа,
                 makeViewController, ControllerScreen
AppShellAppKit   NSWindow, свой стек, NSSplitViewController, NSToolbar, главное меню,
                 точка входа
```

Точка входа (`static func main()`) у каждой платформы своя, и на каждой платформе непуст
только один адаптер. Приложению для всех платформ сразу нужен один `import`: либо модуль-
зонтик, который под `#if canImport` переэкспортирует нужный адаптер, либо оба импорта, где
один пустой (вопрос 5).

## Что нужно от нижних модулей

Сначала в `Nodes` и адаптерах — это полезно и первому способу:

1. **Цепочка команд за корнем дерева.** У `NodeHost` — внешний получатель команд:
   `canPerform`/`perform` после корня спрашивают его. Через него экран отдаёт команду
   контейнеру, окну и приложению. В UIKit-приложении так же подключаются свои контроллеры.
2. **Кнопки пульта и клавиши, которые дерево не взяло**, уже уходят вверх по цепочке
   ответчиков (сделано): Menu попадает к `UINavigationController`.
3. **Панель из команд**: `UIBarButtonItem(Command)` и `NSToolbarItem(Command)` с
   включённостью по `canPerform`, как у пунктов меню.
4. **Галочка у пункта** (состояние вкл/выкл) — для меню «Вид» и панелей.

## Вопросы

1. **Контейнеры — системные или нарисованные нодами?** Предложение: системные. Свайп назад,
   панели, крупные заголовки, боковая панель iPad, Menu на TV, доступность и восстановление
   окон тогда работают сразу. Нарисованные (как в Weave) дают любые переходы, но всё это
   пришлось бы делать заново. Свои переходы можно добавить позже как отдельный стиль стека.
2. **Имена модулей:** `AppShell` / `AppShellUIKit` / `AppShellAppKit`? Другие варианты —
   `Shell…`, `Screens…`.
3. **`Screen` — подкласс `Node` или отдельный объект, у которого есть корневая нода?**
   Предложение: подкласс. Меньше понятий; экран сразу выполняет команды, как любая нода.
4. **Тип маршрута:** свой у каждого стека (`Stack<Route>`) или один на приложение?
   Предложение: свой у стека. Одно `enum` на приложение — частный случай.
5. **Один `import` для всех платформ:** модуль-зонтик с `@_exported import` под
   `#if canImport` или два импорта?
6. **«Назад» на Mac:** Cmd-[ (как в Finder и Safari) вместо Escape у `Command.back`? Или
   Escape оставить модальным окнам, а стеку — Cmd-[?
7. **Экран строится синхронно** (данные грузит сам) — согласны отказаться от асинхронных
   фабрик?
