# Слой приложения: окна, экраны, навигация, маршруты

**Статус: семь решений приняты пользователем (2026-09-28); A0 сделан** — мосты в `Nodes`
(команды за корнем, показ хоста) и контракт экрана и стека, проверенный прототипом
(раздел «A0»). A1 сделан: модули `AppShell`, `AppShellUIKit`, `AppShellAppKit` (раздел
«A1»); A2 сделан — приложение и сцены (раздел «A2»); A3 сделан частями: панель из команд,
модальный показ, лист на части высоты, предупреждения; вкладки и `Split` — раздел «A3,
часть 3»; A4 — восстановление состояния (раздел «A4»); A5 — несколько окон и окно
настроек (раздел «A5»). Решения собраны в конце. Примеры показывают желаемую форму API; это не существующий компилируемый API.

## Зачем и где граница

Сейчас Espalier — библиотека для экранов внутри обычного UIKit/AppKit-приложения: окно,
контроллеры, навигацию, меню делает приложение, а ноды живут в `NodeView`/`NodeNSView`. Так
и остаётся — это **первый способ**, и он не становится вторым сортом.

**Второй способ** — своё приложение целиком, как в SwiftUI: точка входа, окна, экраны,
стек навигации, вкладки, боковая панель, маршруты, deep links, меню, команды уровня окна и
приложения. Пишется один раз для iPhone, iPad, Apple TV и Mac.

Правила границы:

1. **Слой приложения стоит только на публичном API нижних модулей.** Всё, что ему нужно от
   `Nodes` и адаптеров, сначала становится публичным API там (список — ниже, «Что нужно от
   нижних модулей»). Тогда первый способ получает те же возможности, и слой приложения
   нельзя «сломать изнутри».
2. **Можно смешивать в обе стороны.** Стек экранов на нодах встраивается в UIKit-приложение
   как обычный `UIViewController`; экран приложения на нодах может показать готовый
   `UIViewController`/`NSViewController`.
3. **Системные контейнеры — основа.** Они дают платформенные переходы, панели и точки
   интеграции. Синхронизация пути, отмена интерактивного перехода, команды, жизненный цикл,
   фокус пользовательских нод и восстановление данных всё равно требуют нашего адаптера
   и проверки. Использование системного контейнера само по себе этого не реализует.

## Что взято из Weave, а что нет

Weave — предыдущий проект, изученный как внешний источник идей, а не зависимость.
Проверены исходники относительно его корня: `Sources/Weave/Application.swift`,
`Sources/Weave/Platform/ApplicationEntryPoint.swift`, `Sources/WeaveUI/Navigation.swift`,
`Sources/WeaveUI/Coordinator.swift`, `Sources/WeaveUI/DeepLink.swift`,
`Sources/WeaveUI/NavigationRestoration.swift`, `Sources/WeaveUI/Lifecycle.swift`.
Наличие механизма в модели не означает, что он подключён к каждому платформенному событию:
например, в просмотренном `scene(_:willConnectTo:options:)` параметры подключения
игнорируются. Новый слой должен проверять весь путь от события ОС до показанного экрана.

| В Weave | Берём | Меняем — почему |
|---|---|---|
| `Application` с `@main`, `compose()` собирает сцены через result builder; платформа выбирается в одном месте | да: протокол, `@main`, декларативный список окон | без асинхронных фабрик сцен, политик сбоя запуска и отчёта о запуске — для первой версии лишнее |
| `WindowScene` + `Window` + `Router` сцены | одно понятие `Window` (описание окна) | сессии сцен и `UIWindowScene` — дело адаптера, пользователю не видны |
| `Controller<N, A, R>` + `ViewModel` + `Action`/`Route`-трубы + `Coordinator` + `ScreenRegistry` с асинхронными фабриками | маршрут как значение, «маршрут → экран» | обязательных протоколов модели и труб действий нет. Экран владеет содержимым; модель — обычный объект на `StateCore`; фабрика синхронна. От конфликтов переходов это не освобождает: системные анимации остаются асинхронными |
| Зависимость от Flux для состояния и событий | нет | `StateCore` и `async`/`await` уже есть |
| `NavigationController`, нарисованный нодами: `animated` игнорируется, свайпа назад нет, Menu на TV и панели — свои | нет | системные контейнеры: `UINavigationController`, `UISplitViewController`, `UITabBarController`, `NSSplitViewController` (вопрос 1) |
| Машина состояний жизни на 8 состояний у каждой ноды и контроллера | не переносим целиком | отдельно описываем владение экраном, его показ, активность окна и отменяемый переход; адаптер передаёт видимость хосту нод |
| `CommandRegistry` с областями, отдельный от фокуса | нет | уже заменён командами по цепочке фокуса (03, «Команды»); слой приложения продлевает цепочку до окна и приложения |
| `DeepLinkPipeline`: очередь до готовности приложения, проверки доступа | очередь холодного старта | без вечного списка «уже виденных»: в Weave одну и ту же ссылку нельзя открыть второй раз |
| Восстановление навигации повтором маршрутов через фабрику | да | экраны всегда строятся из маршрутов, не из сохранённых объектов |
| Запоминание фокуса при уходе с экрана и возврат при `pop` | да | используем системное поведение там, где оно работает, и явно поддерживаем идентичность пользовательских focus items; проверяем возврат на всех платформах |

## Модель

### Приложение и окна

```swift
@main
struct MailApp: Application {
    let store = MailStore()

    @WindowBuilder var windows: [Window] {
        Window("main", title: "Mail") {
            Split(sidebar: NodeScreen(MailboxesNode(store: store))) {
                Stack(root: MailRoute.inbox) { route in store.screen(for: route) }
            }
        }
    }

    var menuBar: MenuBar {
        MenuBar {
            Menu("Message") { Command.newMessage; Divider(); Command.flag; Command.archive }
        }
    }

    func open(_ request: OpenRequest) -> OpenResult { ... }
}
```

- `Application` — протокол на MainActor; экземпляр создаётся один раз при запуске и живёт
  всё время работы. Деревья, модели `StateCore` и фабрики экранов не объявляются `Sendable`.
- `windows` — стабильные описания доступных окон; одно из них назначается окном запуска
  явно. Объявление описания не открывает все его экземпляры при старте.
- `Window` — описание: id, заголовок, фабрика содержимого. Одно описание может дать
  несколько настоящих окон, каждое со своим id экземпляра и состоянием навигации.
  Фабрика создаёт новое дерево; один объект экрана или ноды нельзя разделить между окнами.
- Открытие нового окна имеет результат: открыто, активировано существующее или не
  поддерживается. Несколько окон запрашиваются только там, где это разрешено платформой
  и конфигурацией приложения. На iPhone/tvOS нельзя молча проигнорировать запрос или
  выбрать первое описание вместо запрошенного: альтернативный показ задаёт приложение.
- `menuBar` — модель меню, которая уже есть (`MenuBar`, 03). Стандартные меню (приложение,
  Правка, Окно, Справка) слой добавляет сам, приложение — свои.

### Экран

```swift
final class InboxScreen: NodeScreen {
    init(store: MailStore) {
        let content = InboxNode(store: store)
        super.init(content)
        title = "Inbox"
        toolbar = [.newMessage, .flag]
        content.handle(.flag, isEnabled: { ... }) { ... }
    }

    override func appeared() { ... }
}
```

- `Screen` — отдельный экранный контракт на MainActor (вопрос 3), а не подкласс `Node`.
  `NodeScreen` — обычная реализация, владеющая корневой нодой. `ControllerScreen` в адаптере
  представляет готовый нативный контроллер без фиктивного дерева нод. Форму общего
  контракта (базовый класс или протокол) проверяем в A0 на этих двух реализациях.
- `title`, `toolbar`, `appeared()` / `disappeared()` и обработчики команд принадлежат
  экрану. В простом случае достаточно `NodeScreen(existingNode)` без нового подкласса;
  `layoutSpec()` остаётся методом ноды. Обязательного `ViewModel` нет.
- Экран получает узкую ссылку на операции навигации, которая не удерживает стек и экран
  циклически. Для типизированного `push` фабрика может передать замыкание в `init`;
  глобального роутера и обязательного типа маршрута у всех экранов нет.
- **Кнопки панели — команды.** `toolbar: [Command]`: заголовок, сочетание и включённость
  берутся из той же модели, что меню и клавиши. Команда, выключенная для меню, выключена и
  на панели.
- Состояние экрана — `StateCore` в ноде, самом экране или в объекте модели. Отдельного
  `ViewModel`-протокола нет: кто хочет MVVM, делает его обычным классом.
- Зависимости передаются через `init`. Окружения со скрытым внедрением нет; тема и условия
  показа уже приходят через `NodeHost`.

### Маршруты и стек

```swift
enum MailRoute: Hashable, Codable {
    case inbox
    case message(Mail.ID)
    case compose(draft: Draft.ID?)
}

let stack = Stack(root: MailRoute.inbox) { route in
    switch route {
    case .inbox: InboxScreen(store: store)
    case .message(let id): MessageScreen(id: id, store: store)
    case .compose(let draft): ComposeScreen(draft: draft, store: store)
    }
}

stack.push(.message(id))
stack.pop()
stack.path = [.inbox, .message(id)]   // deep link, восстановление
```

- **Источник желаемой навигации — `path: [Route]`** (наблюдаемое значение `StateCore`).
  В этой версии путь включает корень и не бывает пустым. Внутри стек хранит записи с
  отдельными идентификаторами: равенство маршрутов не означает тождество экранов.
  Прямое присваивание пути сохраняет самый длинный равный префикс; оставшийся суффикс
  создаётся заново. Правила идентичности и подтверждения перехода описаны ниже.
- Возврат пользователем — свайп, кнопка «назад», Menu на пульте, Cmd-[ на Mac — меняет
  `path` после завершения перехода; прерванный свайп путь не меняет.
- Экран строится **синхронно**, без сети и тяжёлой работы в фабрике. Экран, которому нужны
  данные, показывает состояние загрузки и загружает их в принадлежащей ему задаче.
  Синхронность фабрики не отменяет необходимость сериализовать системные переходы.
- Маршрут — тип стека (`Stack<MailRoute>`). У приложения может быть один тип на всё или свой
  у каждого стека (вопрос 4). Базовое требование — `Hashable`; `Codable` требуется только
  для включённого восстановления, `Sendable` — при передаче значения между акторами.

### Идентичность и согласование переходов

Маршрут отвечает «что открыть», запись стека — «какой это экземпляр экрана».
Внутри каждая запись содержит стабильный id, маршрут и принадлежащий ей экран.

- `push(.message(id))` всегда создаёт новую запись, даже если такой маршрут уже сверху.
- Присваивание равного пути не пересоздаёт экраны и не повторяет загрузку. Например,
  `[inbox, message(A), message(A)] → [inbox, message(A)]` удаляет только последнюю запись.
- При `[inbox, message(A)] → [inbox, message(B)]` корень остаётся, верхний экран заменяется.
  Сравниваем позиции префикса, а не ищем экраны по всему массиву через словарь маршрутов.
- Отдельная операция замены позволяет создать новый экземпляр даже для равного маршрута.
  Если позже понадобится перестановка с сохранением экранов вне общего префикса, это API
  с явными id записей; не обещаем такое поведение у простого `[Route]`.
- `pop` на корне ничего не удаляет и возвращает «не выполнено». Пустой путь отклоняется с
  диагностикой, прежний путь сохраняется. Наблюдаемое состояние пути изменяется только
  проверяемыми операциями стека; наружу не выдаётся бесконтрольно изменяемый `State<[Route]>`.
- Фабрика вызывается один раз на новую запись, не на каждый пересчёт нод или смену темы.
  `Codable`-маршрут содержит идентификаторы данных, а не экран, замыкание или сервис.

`path` — желаемое состояние, `presentedPath` — только для чтения, последний подтверждённый
путь нативного контейнера. Обычно они равны; во время перехода могут отличаться. Второй
путь не является ещё одним источником команд и не имеет публичного setter.
Снимок восстановления берётся из подтверждённого состояния, не из промежуточного жеста.

Адаптер держит не более одного нативного перехода одновременно. У изменения модели есть
ревизия, у перехода — id, исходные записи и целевые записи. Это состояние уровня
контейнера, не новая машина из восьми состояний у каждой ноды.

| Событие | Изменение состояния |
|---|---|
| Программный push/pop/замена пути | Проверить запрос, изменить желаемый путь и ревизию; начать согласование, если адаптер свободен |
| Ещё один запрос во время перехода | Обновить желаемый путь; не запускать конкурентную анимацию. После завершения согласовать с последним желаемым состоянием |
| Начался интерактивный Back | Запомнить ревизию и исходные записи; пока не менять путь и не освобождать экраны |
| Back подтверждён, ревизия не изменилась | Один раз отразить фактический pop в обоих путях без новой анимации |
| Back отменён, ревизия не изменилась | Сохранить путь, экземпляры и время жизни задач; завершить переход |
| Во время Back пришёл новый программный путь | Дождаться результата жеста, обновить только фактически показанное состояние, затем согласовать его с новым путём |
| Пришёл callback старого перехода | Не перезаписывать более новую ревизию; сопоставить callback с текущим переходом |
| Окно окончательно закрыто | Отменить принадлежащую ему работу и игнорировать запоздалые callbacks |

Нативный массив контроллеров сопоставляется с id записей, не с равенством маршрутов.
В UIKit окончание проверяется по transition coordinator и фактическому стеку; один
`willShow` не доказывает успешный pop. [Apple: isCancelled](https://developer.apple.com/documentation/uikit/uiviewcontrollertransitioncoordinatorcontext/iscancelled),
[Apple: didShow](https://developer.apple.com/documentation/uikit/uinavigationcontrollerdelegate/navigationcontroller(_:didshow:animated:)).

Синхронная фабрика не делает сеть и возвращает экран загрузки/ошибки для отсутствующих
данных. Некорректное подключение одного экранного объекта к двум записям отклоняется до
начала нативного перехода. Ошибка применения адаптером возвращается диагностикой: если
не было нового запроса, желаемое состояние откатывается к подтверждённому; более новый
запрос не затирается. Автоматического бесконечного повтора неудачного перехода нет.

На `pop` восстанавливается фокус сохранённого экземпляра экрана после раскладки. Храним
идентификатор или слабую ссылку, проверяем, что цель ещё существует и доступна; иначе
используем предпочтительную цель экрана. Не гарантируем фокус на удалённой строке и не
сериализуем runtime-адреса нод для следующего запуска. Accessibility-фокус и клавиатурный
или tvOS-фокус — разные механизмы, их проверки отдельны.

### Контейнеры

| Наше | iPhone / iPad | Apple TV | Mac |
|---|---|---|---|
| `Window` | `UIWindowScene` + `UIWindow` | то же | `NSWindow` + `NSWindowController` |
| `NodeScreen` | `UIViewController` с `NodeView` | то же | `NSViewController` с `NodeNSView` |
| `Stack` | `UINavigationController` | то же; Menu возвращает | свой контейнер: переход сдвигом, «назад» в панели окна, Cmd-[ |
| `Tabs` | `UITabBarController`; новые режимы боковой панели — по доступности ОС | вкладки сверху | сначала `NSTabViewController` |
| `Split` | `UISplitViewController`; адаптер согласует компактное представление с моделью выбора | явно заданное приложением компактное представление | `NSSplitViewController` с боковой панелью |
| модальный показ | `present` (лист, на весь экран) | на весь экран | лист окна (`beginSheet`) |
| `toolbar` | `navigationItem`, кнопки панели | команды доступны через явно заданные элементы экрана | `NSToolbar` |
| `menuBar` | `UIMenuBuilder` | нет | `NSApp.mainMenu` |

На Mac системного стека навигации нет; его делает адаптер, и ему же запоминать фокус при
уходе с экрана.

Минимумы пакета сохраняются: iOS/tvOS 16, macOS 14. Например, новый режим вкладок и боковой
панели появился в iPadOS 18 и не может быть единственным вариантом для iPadOS 16:
[Apple, WWDC24](https://developer.apple.com/videos/play/wwdc2024/10147/).
`Split` не должен молча делать sidebar недоступным на TV. Приложение предоставляет
компактную навигацию с доступом к тем же назначениям; её отсутствие — диагностируемая
неподдерживаемая конфигурация. Не сводим автоматически всю модель split к одному path.

### Команды на уровне окна и приложения

Сейчас команда идёт от ноды с фокусом наружу до корня дерева (03, «Команды»). Слой
приложения продлевает цепочку:

```
нода с фокусом → … → корень нод → Screen → активная ветка контейнеров → окно → приложение
```

- `Stack` выполняет `Command.back`, пока в пути больше одного маршрута. На корне он не
  обрабатывает команду и даёт её внешнему контейнеру. На TV не обработанный приложением
  Menu/Back уходит системе; библиотека не завершает процесс и не имитирует Home.
  Это соответствует [рекомендации Apple для Back](https://developer.apple.com/design/human-interface-guidelines/remotes).
- Событие обрабатывается один раз: если узел или модель стека выполнили команду, тот же
  press не должен повторно вызвать системный `pop`. Если UIKit выполнил возврат сам,
  адаптер отражает результат в модели, не запускает второй возврат.
- Пункты меню, клавиши и панель используют один и тот же поиск получателя. Учитывается
  активное окно и активная ветка, включая нативный контроллер; скрытая вкладка команду
  не получает. В A3 модальное представление вводит границу: команда не проваливается
  случайно к скрытому стеку под ним.
- Cmd-[ означает возврат в стеке на Mac. Escape сначала принадлежит отмене текущего
  взаимодействия и закрытию разрешённого модального показа. Сопоставление клавиш задаёт
  адаптер; существующий `Command.back` с Escape нельзя изменить только в новом слое,
  оставив старые меню и обработчики с другой семантикой.
- Окно выполняет «Закрыть окно»; приложение — «Новое окно», «Настройки», команды без экрана.
  Приложение объявляет обработчики так же: `handle(.newMessage) { ... }`.
- Меню и панели включают пункт по тому же `canPerform`.

### Жизнь экрана и приложения

- Стек удерживает экран, пока запись есть в пути или пока экран нужен завершающемуся
  переходу. `push` не уничтожает предыдущий экран; успешный `pop` освобождает удалённый.
- `Screen.appeared()` / `disappeared()` сообщают о подтверждённой смене показа. При
  отменённом интерактивном возврате прежний экран не считается окончательно ушедшим;
  не запускаем повторно его задачи только из-за начала и отмены жеста.
- Нахождение ноды в дереве и геометрия внутри её хоста не доказывают, что сам экран
  показан. Нужен публичный сигнал состояния показа хоста: скрытая вкладка или экран под
  непрозрачным следующим экраном прекращает задачи показа, сохраняя ноды и модель.
  Частично видимый экран под sheet может оставаться показанным, но перестаёт быть
  получателем команд. Геометрическая видимость, доступность ввода и активность окна —
  разные признаки. Их точную передачу проверяем в A0/A1 и расширяем для модальных окон A3.
- Задачи уровня показа прекращаются при уходе; задачи времени жизни экрана — при удалении
  записи; работа уровня приложения живёт у сервиса приложения. Не привязываем всё к
  одному `disappeared()`. Запоздалый результат проверяет актуальность запроса и владельца.
- Фаза каждого окна (`active`, `inactive`, `background`) наблюдаема отдельно. Общая фаза
  приложения — active, если активно хотя бы одно окно; иначе inactive при наличии
  foreground-окна; иначе background. Команды выбирают окно по платформенному контексту.
- Отключение `UIScene` не означает уничтожение её сессии: освобождение представления и
  сохранение данных восстановления отделены от окончательного закрытия экземпляра окна.

### Deep links и восстановление

- Адаптер нормализует URL и user activity холодного и тёплого старта в запрос с контекстом
  целевого окна. Декодирование URL не создаёт экран и не выполняет пользовательское действие.
  Приложение выбирает окно, вкладку, путь и модальный показ. Одного глобального `stack.path`
  для многоконного приложения недостаточно.
- `OpenResult` различает принятие, отложенную обработку и неподдерживаемый запрос/ошибку.
  Принятие не означает, что анимация завершена. Точное написание типов — часть A4.
- До готовности нужного окна запросы стоят в ограниченной очереди в порядке получения.
  Размер очереди задаётся явно; переполнение отклоняет новый запрос с диагностикой,
  а не молча теряет старый. Повторно открытая позднее ссылка — новый допустимый запрос.
  Возможная дедупликация одной доставки ОС не использует вечный набор маршрутов.
- Если нужен вход в аккаунт, приложение владеет отложенным намерением, затем продолжает
  его или отменяет. Результат асинхронной проверки несёт ревизию: старый запрос не может
  перезаписать более новую навигацию или открыть закрытое окно.
- Восстановление включается отдельно для каждого контейнера. Снимок хранит версию схемы,
  id описания и экземпляра окна, стабильные id контейнеров, пути, выбранную вкладку и
  выбор в split. Для разных типов маршрутов используются отдельные кодеки контейнеров;
  одного `Codable` у общего enum приложения не требуется. Нативные объекты не сохраняются.
- Восстанавливаем состояние атомарной установкой пути без воспроизведения исторических
  `push`, сетевых команд и эффектов. Фабрика создаёт экран, а не повторяет действие вроде
  отправки письма. Черновики и бизнес-данные сохраняет модель, не механизм навигации.
- Неизвестная версия без миграции возвращает контейнер к корню с диагностикой. Для
  неизвестного/недоступного маршрута сохраняется только валидный префикс; нельзя выкинуть
  середину и открыть дочерний экран без его родителя. Нужна проверка текущего аккаунта и
  доступа. Маршруты восстановления могут быть исключены приложением как чувствительные.
  Для частичного восстановления записи декодируются по отдельности в версионированной
  оболочке; обычное декодирование всего `[Route]` через синтезированный `Codable` не
  обещает сохранить префикс после ошибки одного элемента.
- На старте порядок: создать модель окна → применить доступный снимок → обработать новый
  внешний запрос. Новый deep link имеет приоритет. Поздно доставленный снимок не
  перезаписывает уже изменённую пользователем или ссылкой навигацию.

В UIKit адаптер сам предоставляет данные через механизм восстановления сцен; контейнер
не сериализует маршруты автоматически. [Apple: сохранение состояния сцены](https://developer.apple.com/documentation/uikit/uiscenedelegate/staterestorationactivity(for:)).
Данные сессии могут быть недоступны при первом подключении и прийти позже:
[Apple: stateRestorationActivity](https://developer.apple.com/documentation/uikit/uiscenesession/staterestorationactivity).

### Вместе с UIKit и AppKit

```swift
// Стек экранов на нодах внутри обычного UIKit-приложения.
let stack = Stack(root: MailRoute.inbox) { ... }
window.rootViewController = stack.makeViewController()

// Готовый UIKit-экран внутри стека на нодах.
case .settings: ControllerScreen(SettingsViewController())
```

`makeViewController()` / `ControllerScreen` планируются в адаптерах UIKit и AppKit.
`Application` для этого не нужен: можно взять только стеки и экраны.

Это планируемые API. Один стек имеет один активный нативный контейнер, повторное получение
адаптера не создаёт вторую независимую навигацию. Нативный контроллер принадлежит ровно
одному месту показа; нельзя вставить тот же объект в два стека. `ControllerScreen`
соблюдает containment, передаёт lifecycle и ввод нативному контроллеру. Изменять внутренний
массив контроллеров принадлежащего библиотеке стека извне нельзя; навигация идёт через
его модель. Мост не требует замены делегата приложения или точки входа чужого приложения.

### Проверка без окон

Логика контейнеров — путь, команды «назад», включённость пунктов, сведение экранов с путём
— живёт в модуле без UIKit/AppKit и проверяется `swift test` на Mac и Linux. Адаптеры
только применяют результат к системным контейнерам и проверяются в Simulator и UI-тестами
демо.

## Модули

Название продукта в имени нельзя, `App` — протокол SwiftUI (та же проблема, что с `Layout`).
Предложение (вопрос 2):

```
AppShell         Application, Window, Screen, NodeScreen, Stack, Tabs, Split, путь и
                 маршруты, цепочка команд окна и приложения. Без UIKit/AppKit;
                 зависит от Foundation, Nodes и StateCore.
AppShellUIKit    системные контейнеры UIKit (iOS, iPadOS, tvOS, Catalyst), точка входа,
                 makeViewController, ControllerScreen
AppShellAppKit   NSWindow, свой стек, NSSplitViewController, NSToolbar, главное меню,
                 точка входа
```

Точка входа (`static func main()`) реализуется адаптером. В конкретной сборке активна одна
реализация: UIKit под `#if canImport(UIKit)`, AppKit под
`#if canImport(AppKit) && !canImport(UIKit)`. В Catalyst выбирается UIKit.
В Linux доступны модель и тестовый исполнитель переходов, нативной точки входа нет.

Рекомендация для первой версии: явный `import AppShell` и импорт нужного адаптера;
общий файл нескольких платформ выбирает адаптер через `#if canImport`. Не делаем
`@_exported import` условием работы публичного API. Модуль с одним импортом можно добавить
позже после проверки способа экспорта на минимальной поддерживаемой версии Swift.
Нижние модули не зависят от `AppShell`; рендерер не знает маршрутов и окон.

Настройка исполняемого приложения остаётся явной: `Info.plist`, декларации сцен, URL types,
associated domains и возможности нескольких окон не появляются от одного `@main`.
Для A2 нужен минимальный пример конфигурации каждого демо. До кода новых адаптеров нужно
согласовать дополнение перечня платформенных модулей в `AGENTS.md`: действующий перечень
не содержит `AppShellUIKit`/`AppShellAppKit`. Это не разрешение импортировать UIKit в core.

2. **Кнопки пульта и клавиши, которые дерево не взяло**, уже уходят вверх по цепочке

3. **Панель из команд**: `UIBarButtonItem(Command)` и `NSToolbarItem(Command)` с

4. **Галочка у пункта** (состояние вкл/выкл) — для меню «Вид» и панелей. Сделано

5. **Состояние показа хоста**, отдельное от монтирования нод, с корректным прекращением

6. **Сопоставление стандартных команд с вводом платформы**: Back, Cancel/Dismiss и

7. **Фокус экрана**: публичное получение/запрос предпочтительной цели и проверка её

## A0: контракт экрана и стека (2026-09-28)

**Статус: проверен прототипом, публичного API нет.** Прототип был
отдельным пакетом `Prototypes/AppShellModel`; в A1 его код переехал в `Sources/AppShell`,
тесты — в `Tests/AppShellTests`, прототип удалён.

**Экран.**

```swift
open class Screen: CommandResponder        // init — package: наследуют только слой и адаптеры
    var title: String
    var toolbar: [Command]
    internal(set) var isPresented: Bool     // подтверждённый показ
    open func appeared()                    // после конца перехода; отменённый жест — ничего
    open func disappeared()
open class NodeScreen: Screen               // NodeScreen(node, title:) — без своего класса
    let root: Node
open class ControllerScreen: Screen         // в адаптере: UIViewController / NSViewController
```

- Экран — `CommandResponder`: команды, которые не выполнило его содержимое, идут экрану,
  затем стеку (`screen.outer = stack`), затем тому, что вокруг стека (`stack.outer`).
  Адаптер ставит `host.outerResponder = screen` для `NodeScreen`.
- Экран принадлежит одному месту: фабрика, вернувшая экран из другого стека, получает
  `.rejected(.screenInUse)`, путь не меняется. Отпущенный стеком экран можно поставить снова.
- Состояние показа нод — `NodeHost.isShown` (сделано в A0), а не `isPresented`: экран под
  листом показан, но не сверху.

**Стек.**

```swift
final class Stack<Route: Hashable>: CommandResponder
    init(root: Route, screen: @escaping @MainActor (Route) -> Screen)
    var path: [Route]                       // желаемый; наблюдаем через StateCore
    var presentedPath: [Route]              // подтверждённый; пуст до первого показа
    var revision: UInt64
    func push(_:) / pop() / replaceTop(with:) / setPath(_:) -> NavigationResult
    func close()
    weak var presenter: StackPresenter?     // для адаптеров
    func screen(for: StackEntryID) -> Screen?
    func backBegan() -> StackMove?          // системный возврат; nil — не давать начать
    func moveEnded(_ id: UInt64, completed: Bool)

enum NavigationResult { case accepted, unchanged, rejected(NavigationRejection) }
enum NavigationRejection { case atRoot, emptyPath, screenInUse, closed }
protocol StackPresenter { func present(_ move: StackMove) }   // один переход за раз
struct StackMove { let id; let from: [StackEntryID]; let to: [StackEntryID] }
```

- Записи — `StackEntryID` + маршрут + экран; наружу адаптеру — только id и экран по id.
  `push` равного маршрута — новая запись; `setPath` сохраняет самый длинный равный префикс.
- Один переход за раз. Запросы во время перехода меняют `path` и `revision`; по окончании
  стек переходит к последнему пути одним новым переходом от показанного.
- `moveEnded` чужого или позднего перехода ничего не меняет. Возврат пользователя, законченный
  без новых запросов, — `path` теряет верх вместе с показом, новый переход не просится.
  Отпущенный жест — всё как было, `appeared`/`disappeared` не вызываются. Программный
  переход, который платформа не смогла, без новых запросов возвращает `path` к показанному,
  без повторов.
- Стек выполняет `Command.back`, пока в пути больше корня. Кнопка Menu на TV и Cmd-[ идут по
  цепочке команд до стека, программный `pop` — одно действие на нажатие; в корне команда
  уходит дальше, на TV — системе.
- Фабрика вызывается один раз на запись; экран отпускается, когда записи нет ни в `path`,
  ни в показанном, ни в идущем переходе. `close()` отпускает все экраны, запросы потом —
  `.closed`, поздние `moveEnded` не слышны.

**Что прототип показал и что меняется в A1.**

- Корень делает фабрика в `init`; экран корня, уже занятый, — ошибка программиста
  (остановка). Остальные случаи — значения `NavigationResult`, без исключений.
- Стек не держит `presenter` — его держит адаптер, который держит стек. Без презентера ничего
  не показано: `presentedPath` пуст, `appeared` не зовётся.
- `backBegan()` возвращает `nil` в корне и во время другого перехода: UIKit-адаптер
  запрещает жест свайпа (`gestureRecognizerShouldBegin`). Кнопку «назад» панели UIKit
  адаптер ведёт тем же путём, что свайп, или заменяет своей, которая выполняет
  `Command.back`, — решается в A1 по поведению `UINavigationController`.
- Не вошло в прототип: обновление панели при смене `title`/`toolbar`, возврат фокуса при
  `pop`, кодек путей (A4), вкладки и split (A3).
- До кода адаптеров A1 в `AGENTS.md` нужно добавить `AppShellUIKit`/`AppShellAppKit` к
  перечню модулей, где разрешены UIKit и AppKit.

## Маршруты-URL (2026-09-28)

**Статус: реализовано в `AppShell` (модель); подключение к `Application.open` — A2.** По
предложению пользователя — маршруты как на веб-сервере: `/catalog/:category/:id`.

```swift
let routes = RouteTable<ShopRoute> {
    RoutePattern("/catalog", .catalog)
    RoutePattern(
        "/catalog/:category/:id",
        route: { .product(id: try $0.value("id")) },
        values: { route in
            guard case .product(let id) = route else { return nil }
            return ["id": String(id)]
        }
    )
}
stack.setPath(try routes.path(for: "/catalog/shoes/42"))
routes.url(for: stack.path)   // "/catalog/shoes/42"
```

- **URL — весь путь стека, а не один экран.** Каждое начало пути, которое берёт шаблон, —
  экран, от короткого к длинному: `/catalog`, `/catalog/shoes`, `/catalog/shoes/42`. Дерево
  вложенности объявлять не нужно: оно выводится из префиксов. Начало, которое не берёт ни один
  шаблон, своего экрана не имеет (`/account/orders/7` — счёт и заказ, без списка заказов). Весь
  URL должен быть взят, иначе `RouteError.unknownPath`.
- Сегменты: литерал, `:name` — один сегмент, `*name` — остаток (только для всего URL, его
  начала экранами не становятся). Из подходящих шаблонов выигрывает тот, что больше называет
  сам (`/catalog/new` важнее `/catalog/:category`), затем первый объявленный.
- Значения: `$0.value("id")` — любой `LosslessStringConvertible` (`Int`, `UUID`, свои типы),
  с ошибкой `missingParameter`/`invalidParameter`; `$0["q"]` — из пути, иначе из query.
  Декодирование и кодирование процентов — таблицы.
- **В обе стороны.** `url(for: path)` — шаблон последнего маршрута, значения всех маршрутов
  пути (ближний к верху побеждает): категория товара берётся у списка под ним. `nil`, если
  у маршрута нет шаблона или не хватает значения. Для deep links, universal links,
  «Поделиться», Handoff, восстановления и имён экранов в аналитике.
- Путь, прочитанный из URL, — канонический путь этого URL: экран, открытый иначе
  (из поиска), при восстановлении по URL окажется в своём каноническом пути.
- Таблица — значение `Sendable` (маршрут — `Hashable & Sendable`, замыкания `@Sendable`):
  её держат в константе. Схема и хост URL — дело приложения; таблица смотрит путь и query.
- Координатора-класса нет: таблица (URL ↔ путь) + `Stack` (путь ↔ экраны).

Проверено: 6 тестов (вложенный путь, начало без экрана, литерал важнее параметра, ошибки,
query и `*rest`, URL пути со значениями всех маршрутов и кодированием, стек по URL).

Открыто (к A2/A3): модальный показ в URL (`#compose` или `?sheet=`) — у листа своя
идентичность, в путь стека он не входит; первый сегмент, выбирающий вкладку (A3); правила
доступа (`requires` с перенаправлением на `/login?next=`) — в таблице или в приложении;
версия схемы URL для восстановления (A4).

## A2: приложение и сцены (2026-09-28)

**Статус: реализовано** (без UI-тестов — отложены пользователем). Всё строится на сценах, как
на платформах Apple: объявление окна — `WindowScene` (конфигурация сцены; не `Scene` — это
протокол SwiftUI), живое окно — `SceneSession` (как `UISceneSession`).

```swift
@main
struct LayoutDemo: Application {
    private let model = DemoModel()
    var scenes: [WindowScene] { WindowScene("main", title: "Layout demo") { model.stack } }
    var menuBar: MenuBar { MenuBar { DemoModel.menu } }
    func started(_ shell: Shell) { shell.handle(.newMessage) { ... } }
    func open(_ request: OpenRequest) -> OpenResult {
        model.open(request.url) ? .opened : .unsupported   // DemoModel.routes
    }
}
```

- `AppShell`: `Application` (на MainActor; `scenes` через `@SceneBuilder`, `menuBar`,
  `started`, `open`), `WindowScene` (id, заголовок, фабрика содержимого — новое на каждую
  сессию), `SceneContent` (`Stack` или `Screen`), `SceneSession` (содержимое, `activation`,
  `close()`, `Command.closeWindow` — Cmd-W, включена, где платформа может закрыть сцену),
  `SceneActivation` (как `UIScene.ActivationState`), `Shell` (сессии, `activation`
  приложения — самая активная из сцен, `open(_:in:)`, команды приложения), `OpenRequest`,
  `OpenResult` (`opened`, `queued`, `unsupported`, `queueFull`).
- Цепочка команд: нода → … → экран → стек → сессия сцены → приложение (`Shell`).
- Ссылки: до первой показанной сцены ждут в очереди (по умолчанию 16, переполнение —
  `.queueFull`, прежние остаются) и уходят в порядке прихода; дальше — сразу, повтор той же
  ссылки — обычная новая ссылка.
- `AppShellUIKit` — всё на сценах: `Application.main()` → `UIApplicationMain` с делегатом,
  конфигурация сцены с делегатом сцены. Сессия — по `UISceneSession.persistentIdentifier`,
  вид сцены — в `userInfo` сессии. **Отключение сцены** (`sceneDidDisconnect`) отпускает окно
  и контроллеры, сессия с содержимым и путём стека остаётся; при повторном подключении стек
  показывает то, что показывал, без хода. **Уничтожение** (`didDiscardSceneSessions`) —
  окончательное закрытие: `Shell.sessionClosed`, стек закрыт. Закрыть — `requestSceneSession
  Destruction`, только если приложение берёт несколько сцен. Активация — из
  `sceneDidBecomeActive`/`WillResignActive`/`WillEnterForeground`/`DidEnterBackground`.
  Ссылки — `openURLContexts` и `urlContexts` подключения. Меню приложения на iPad — после
  View (`buildMenu`, на tvOS недоступно).
- `AppShellAppKit`: `Application.main()` → `NSApplication` с делегатом; сцена — `NSWindow`,
  закрытие окна — конец сессии; активация — ключевое, свёрнутое, скрытое приложение. Главное
  меню `NSMenu(standardAround:)`: меню приложения (About, Hide, Hide Others, Show All, Quit),
  File (Close Window — `Command.closeWindow`), Edit (Undo…Select All — действия AppKit), меню
  приложения, Window (Minimize, Zoom, Bring All to Front; `windowsMenu`). Ссылки —
  `application(_:open:)`, в ключевое окно.
- Демо: все три приложения — `Application`; TV-пробы — `ControllerScreen(ScreenController)`,
  `STACK_PROBE` — свой стек. `DemoModel.routes`: `/`, `/messages/:id`.

Проверено: 4 теста `Shell` (сессия со своим содержимым и цепочка команд до приложения,
очередь ссылок и её предел, активация приложения, закрытие только закрываемой сцены и

## A3, часть 1: панель из команд (2026-09-28)

**Статус: реализовано.** A3 разбит на части: панель и галочка, затем модальный показ,

```swift
let screen = NodeScreen(message, title: mail.sender)
screen.toolbar = [.flagMessage]
screen.handle(.flagMessage, isOn: { mail.isFlagged }) { toggleFlag() }
```

- `Screen.toolbar` показывается: **iPhone/iPad** — кнопками справа в панели навигации
  (`navigationItem.rightBarButtonItems`, первая команда — левее), **Mac** — в панели окна.

  нодами, как и решено в «Контейнерах».
- Кнопка отправляет команду тем же путём, что пункт меню: для экрана на нодах — от ноды с
  фокусом (или последней нажатой) наружу через экран и стек; для `ControllerScreen` — экрану и
  дальше. Включённость — `canPerform` той же цепочки. В UIKit кнопки обновляются по
  `Observer`: всё, что читают `isEnabled`, и перенос фокуса; и ещё раз, когда экран вот-вот
  покажется (`willShow`) — для условий, которые никто не наблюдает. В AppKit кнопки проверяет
  сама панель (`NSToolbarItemValidation` у `NodeNSView` и у стека над контроллером AppKit).
- Mac: у окна, содержимое которого — стек, в начале панели кнопка «назад» (`Command.back`,
  стрелка `chevron.backward`), включённая, пока стек может вернуться; дальше гибкий
  промежуток и команды верхнего экрана, меняются вместе с ним. Экран как содержимое окна —
  только свои команды. Панель ставится, только если у окна своей нет; у каждой панели свой
  идентификатор: панели с одним идентификатором в AppKit делят кнопки между окнами.
- `ControllerScreen` без команд в `toolbar` сохраняет свои кнопки панели навигации.
- Галочка у команды-переключателя в меню (`isOn`) — Mac и iPad; на кнопке панели не
  показывается (03).
- Демо: у «Входящих» в панели Edit Inbox (включается после нажатия или фокуса в папке), у
  письма — Flag Message (⌘⇧L, в меню Screen с галочкой, пока письмо помечено; на экране

## A3, часть 2: модальный показ (2026-09-28)

**Статус: реализовано.**

```swift
let compose = Presentation(NodeScreen(ComposeNode(), title: "New Message"))  // .sheet
compose.isDismissible = !draft.hasText
compose.onDismissAttempt = { askToDiscard() }
inboxScreen.present(compose)          // NavigationResult
compose.dismiss()
```

- `Presentation` — отдельный объект со своей идентичностью, не запись пути стека: путь
  стека под ним не меняется, стек внутри листа — свой `Stack`. Содержимое — экран или стек.
  Показывается один раз: после закрытия отпускает содержимое (стек закрывается), новый
  показ — новый объект. `Screen.present` отклоняет второй показ с того же экрана
  (`NavigationRejection.alreadyPresenting`) и содержимое, уже показанное где-то
  (`.screenInUse`).
- Стиль: `.sheet` — лист (iPhone/iPad — page sheet, Mac — лист окна; TV — на весь экран),
  `.fullScreen` — на всё окно (на Mac — тоже лист).
- **Состояние.** Желаемое (показ просили / `dismiss()`) и подтверждённое платформой
  (`isShown`) раздельны, как `path`/`presentedPath` у стека: ожидание презентера, показ,
  показан, скрытие, ушёл. Запрос до того, как экран в окне, ждёт; `dismiss()` во время
  показа скрывает после его конца; поздние отчёты ничего не меняют. Содержимое-экран
  получает `appeared()`/`disappeared()` по подтверждению.
- **Закрытие пользователем.** Escape (`Command.cancel`) и Menu пульта (`Command.back`, если
  содержимое само не вернулось — стек внутри листа сначала идёт назад) обрабатывает сама
  `Presentation`; смахивание листа вниз — платформа. Пока `isDismissible == false`, всё это
  вызывает `onDismissAttempt`, а лист не смахивается (`isModalInPresentation`). Модель
  меняется только по завершённому закрытию (`presentationControllerDidDismiss`): смахивание,
  отпущенное раньше, не закрывает модель. `dismiss()` закрывает всегда.
- **Граница команд.** Цепочка содержимого: содержимое → `Presentation` → окно
  (`SceneSession`) → приложение. Экран и стек под листом команды из листа не получают: Cmd-[
  в листе не уводит стек под ним назад. Вне `Application` (свой UIKit-контроллер) цепочка
  листа заканчивается на `Presentation`.
- **Экран уходит — его показ закрывается:** запись, покинувшая стек, закрытие стека,
  закрытое окно.
- Адаптеры: `PresentationPresenter` (показать/скрыть, отчёт о конце). UIKit — `ModalPresenter`
  у контроллера стека (показ над всем стеком) и у экрана без стека;
  `PresentedViewController` — контейнер содержимого: клавиатура переходит в лист, после
  закрытия — обратно верхнему экрану стека; Menu, не взятое содержимым, не отдаётся
  собственному закрытию UIKit. AppKit — `presentAsSheet`, размер листа — `preferredContentSize`
  содержимого или 480×400; Escape над контроллером AppKit — `cancelOperation`.
- Демо: New Message (⌘N; в панели «Входящих» и в меню Screen) показывает лист с Cancel и
  Send; `OPEN_COMPOSE=1` открывает его при запуске (TV — только так).

Проверено: 7 модульных тестов модели (ожидание презентера и отпускание содержимого, один
показ с экрана и содержимое в одном месте, граница команд до окна, лист без закрытия
пользователем, закрытие смахиванием, `dismiss` во время показа, уход экрана из стека и
закрытие стека-содержимого); Mac — 3 теста адаптера (лист окна и Escape в дереве, Escape над
контроллером AppKit и размер, показ, ждущий окна); UIKit — 3 теста адаптера на iPhone 17 и
Apple TV Simulator (стиль — на TV лист на весь экран, делегат листа, `isModalInPresentation`
по наблюдению, смахивание до конца и удержанное, Menu над контроллером UIKit). Хост тестов
пакета начинает переход показа UIKit и не заканчивает его — тесты завершают показ сами, как
это делает UIKit; сам показ проверяют UI-тесты демо. UI-тесты: iOS — New Message открывает
лист, Cancel и смахивание вниз закрывают, стек под ним на месте; TV — Menu закрывает лист, а
не приложение; Mac — кнопка панели и пункт меню открывают лист, Escape и Send закрывают.

## A3, часть 2б: лист на части высоты (2026-09-28)

**Статус: реализовано.**

```swift
let info = Presentation(infoScreen, style: .sheet(heights: [.medium, .large]))
screen.present(info)
info.height = .large          // наблюдаемо; тянет пользователь — меняется
```

- `PresentationStyle` — теперь значение со свойствами `coversWindow`, `heights` и
  `usableBelow`: `.sheet`, `.fullScreen`, `.sheet(heights:usableBelow:)`. `SheetHeight`: `.medium`, `.large`,
  `.points(Double)` (не выше полной), `.fraction(Double)` (доля полной). Пустой список —
  `.large`, повтор считается один раз.
- `Presentation.height` — где лист стоит сейчас: сначала первая высота списка, дальше —
  куда потянул пользователь (`userMoved(to:)` от адаптера); присваивание двигает лист,
  высота не из списка игнорируется. У показа на всё окно — `.large`.
- iPhone/iPad — `UISheetPresentationController`: `detents`, «ручка» при двух высотах и
  больше, `selectedDetentIdentifier` в обе стороны (делегат листа — `ModalPresenter`).
  TV — на весь экран, Mac — обычный лист окна, высоты не действуют.
- В tvOS листа с высотами нет, а `#if os` запрещён: настройка — в соответствии протоколу
  `SheetHeights`, недоступном на tvOS (`@available(tvOS, unavailable)`); на TV приведение к
  нему ничего не находит. Сборка и тесты на Apple TV Simulator это подтверждают.
- Демо: у письма Message Info (⌘I, в панели и в меню Screen) — лист от половины до полной.

Проверено: модельный тест (высоты стиля, начальная, чужая игнорируется, от пользователя, у
показа на всё окно, `usableBelow` только из своих высот), UIKit — высоты, «ручка»,
незатемнённая высота, модель → лист и перетаскивание → модель (iPhone 17), лист с высотами
на TV — на весь экран (Apple TV Simulator); UI-тест iOS-демо: Message Info открывается на
половину, Reply под ним работает, лист тянется наверх до полной; все UI-тесты iOS- и
TV-демо проходят. UI-тест Mac-демо после этой
части не запускался (на Mac добавилась только кнопка панели).

**Экран под листом — по настройке** (решение пользователя, 2026-09-28):
`.sheet(heights:usableBelow:)` — до этой высоты (одной из `heights`) экран под листом не
затемняется и работает, как карта под листом в Картах (`largestUndimmedDetentIdentifier`);
выше — закрыт, как у любого листа. Команды тогда идут от того места, где пользователь:
касание делает first responder дерево экрана под листом, и его цепочка — экран → стек, а
цепочка листа по-прежнему идёт мимо них к окну. По умолчанию — `nil`: экран закрыт на любой
высоте. На Mac и TV не действует. В демо Message Info — `usableBelow: .medium`: на половине
Reply на письме под листом работает.

## A3, часть 2в: предупреждения и меню действий (2026-09-28)

**Статус: реализовано.**


## A3, часть 3: вкладки и `Split` (2026-09-29)

**Статус: реализовано на iPhone, Mac и TV; на iPad вручную вкладки и split рисуются, UI-тесты
демо не дожидаются первого показа (дефект 217).**
Модель, адаптеры UIKit и AppKit и UI-тесты — ниже, в «Итогах».

Что нужно от обоих: выбор сохраняется при смене размеров; невыбранная вкладка не получает
команд и не считается показанной; sidebar доступен в компактном варианте и на TV; окно Mac
показывает панель того экрана, что показан сейчас. Не сводим `Split` к одному `path`: у
боковой панели и содержимого свои экраны, у содержимого — свой `Stack`.

```swift
let tabs = Tabs<MailTab>(
    selection: .inbox,
    [
        Tab(.inbox, title: "Inbox", symbol: "tray", content: inboxStack),
        Tab(.search, title: "Search", symbol: "magnifyingglass", content: searchScreen),
    ]
)
tabs.select(.search)                       // выбор из кода: Bool, есть ли такая вкладка
tabs.selection                             // наблюдаемо

let split = Split(
    sidebar: NodeScreen(MailboxesNode(store: store), title: "Mailboxes"),
    content: inboxStack                     // Stack или Screen
)
split.showContent()                         // компактно: показать содержимое; showSidebar() — боковую панель
```

- **`Tabs<ID: Hashable>`** — `SceneContent` и `CommandResponder`. Вкладка — `Tab<ID>`: id,
  заголовок, имя SF Symbol, содержимое; содержимое вкладки — `TabContent`: `Stack`,
  `Screen` или `Split` (вкладки во вкладках модель не принимает — на этапе компиляции). Список
  вкладок задаётся при создании и не меняется; `selection` — значение `StateCore`, адаптер
  следит за ним; выбор пользователя приходит в модель, выбор из кода — в адаптер, без петли.
- **Показ.** Экран, показанный вкладкой, получает `appeared()`, когда вкладка выбрана, и
  `disappeared()`, когда выбрана другая; `isPresented` следует за этим. Хосты невыбранных
  вкладок не в окне — `NodeHost.isShown` у них ложь без нашего участия; стеки и их состояние
  остаются.
- **Команды.** Содержимое каждой вкладки стоит в цепочке `экран → стек → Tabs → окно`. Цепочка
  идёт от фокуса наружу, поэтому невыбранная вкладка команд не получает: её деревья без
  фокуса. `Tabs` сама команд не берёт.
- **`Split`** — `SceneContent`, `TabContent`, `CommandResponder`: боковая панель — `Screen`,
  содержимое — `Stack` или `Screen`. Обе части стоят в цепочке `… → Split → окно`.
  `isContentShown` (наблюдаемо) — какая часть на экране, когда места хватает только на одну:
  его меняют `showContent()`/`showSidebar()` из кода и уход пользователя назад к боковой
  панели. Когда места хватает на обе — показаны обе, `isContentShown` хранит выбор на случай
  сужения. Сужение, поворот, смена размера окна выбор не теряют.
- **TV.** Боковая панель не прячется: на TV `Split` — боковая панель и содержимое рядом, фокус
  переходит между ними (Menu из содержимого — к боковой панели). Приложение, которому это
  не подходит, пользуется вкладками.
- **UIKit.** `Tabs` — `UITabBarController` (классический, вкладки из `tabBarItem`; режимы боковой
  панели iPadOS 18 не задействуем — минимум iOS 16). `Split` — `UISplitViewController` в
  стиле двух колонок. Проверено на iPhone 17 Simulator: в компактном виде стеки не
  сливаются — навигационный контроллер содержимого кладётся поверх боковой панели целиком,
  и путь нашего стека остаётся при уходе к боковой панели и возврате.
- **AppKit.** `Tabs` — `NSTabViewController` со вкладками сверху (`segmentedControlOnTop`, чтобы
  панель окна осталась для команд); `Split` — `NSSplitViewController` с боковой панелью.
  Панель окна принадлежит выбранной ветке: стек, ставший видимым, ставит на окно свою
  панель, вместо панели прежнего.
- **Проверки.** Модельные тесты `AppShellTests` (выбор, показ, цепочка команд, `Split`);
  адаптеры на iPhone 17, iPad и Apple TV Simulator и на Mac; UI-тесты демо на трёх
  платформах: выбор сохраняется при повороте (iPad) и смене размера окна (Mac), Menu на TV.

## A4: восстановление состояния (2026-09-29)

**Статус: модель и адаптеры сделаны; модель проверена тестами; на iOS и Mac восстановление
сработало в прогонах UI-тестов (приложение запустилось на сохранённой вкладке); сами
тесты «закрыть и открыть заново» после правки не запускались.** Дизайн принят пользователем 2026-09-29 (пять развилок,
все — по рекомендации). Deep links и очередь ссылок до готовности окна уже работают (`Shell.open`,
`Application.open`, `RouteTable`); A4 — восстановление контейнеров.

```swift
let stack = Stack(root: MailRoute.inbox) { store.screen(for: $0) }
    .restorable(using: routes) { store.canOpen($0) }    // включается на контейнер

// адаптеры сами:
let data = session.restorationData()                    // Data? — nil, если ничего не включено
let result = session.restore(from: data)                // RestorationResult: issues, isRestored
```

- **Что сохраняем.** Дерево контейнеров окна: стек — URL своего пути (`RouteTable.url(for:)`),
  вкладки — выбранную и снимки содержимого каждой, `Split` — `isContentShown` и снимок
  содержимого. Экран сам по себе, модальные показы, фокус, прокрутка, черновики — нет: это
  дело модели приложения. Включено восстановление на стеке (`restorable(using:)`); вкладки
  и `Split` сохраняют выбор всегда, содержимое — если оно включено.
- **Пути как URL.** Маршрутам не нужен `Codable`. Сохраняется URL самого длинного начала
  пути, у которого он есть и все маршруты разрешены хуком приложения (чувствительные
  исключаются). При восстановлении URL читается таблицей; если целиком не берётся, отбрасываются
  сегменты с конца, пока не возьмётся: остаётся валидный префикс, середина не выпадает.
  Путь должен начинаться с корня стека, иначе он отвергнут.
- **Оболочка.** JSON с версией схемы (сейчас 1). Неизвестная версия или испорченные данные —
  контейнеры остаются на корне, `RestorationResult` называет причину; хука миграции нет — он
  появится со второй версией. Вкладка со старым ключом (`Tab.restorationKey`, по умолчанию
  `String(describing: id)`) без такой вкладки — выбор остаётся прежним, причина названа.
- **Приоритет.** Восстановление применяется только к нетронутому контейнеру (стек без
  единого запроса пути, вкладки и `Split` без выбора из кода или от пользователя), поэтому
  новая ссылка и запоздавший снимок не перекрывают навигацию: порядок на старте — модель окна,
  снимок, ссылки. Трогать контейнер снимок не может: пути ставятся атомарно (`setPath`), без
  повторения исторических `push`.
- **UIKit.** Снимок — `NSUserActivity` в `stateRestorationActivity(for:)` сцены
  (`ShellSceneDelegate`), читается в `scene(_:willConnectTo:)` до ссылок. **AppKit.**
  Уровень приложения: `application(_:willEncodeRestorableState:)` и
  `application(_:didDecodeRestorableState:)`; данные первого окна вида сцены применяются к
  окну, когда оно есть и когда придут данные (что позже).
- **Проверки.** Модельные тесты `AppShellTests` (снимок ↔ путь, префикс, неизвестная
  версия, испорченные данные, нетронутость, вкладки и `Split`, хук); адаптеры на Simulator
  и Mac; UI-тесты «закрыть и открыть заново» на iOS и Mac.

### Итоги (2026-09-29)

- `AppShell`: `Stack.restorable(using:allowing:)` (для `Route: Sendable`), `Tab.restorationKey`,
  `SceneSession.restorationData()` и `restore(from:)`, `RestorationResult` и
  `RestorationIssue` (нечитаемые данные, неизвестная версия, неизвестный путь, путь обрезан,

  затирает восстановленный выбор) и выставляет выбор после загрузки вида, чтобы переключатель
  сверху показывал ту вкладку, что показана.
- Демо: стек демо (`DemoModel.stack`) и стек вкладки Inbox в `TABS_PROBE` включены в
  восстановление.

Проверено: 13 модельных тестов `RestorationTests` (URL пути и обратно, отсутствие включения,

нетронутость и обрезка). Сборка пакета на iPhone Simulator и демо iOS и Mac.

закрытием), на Mac — когда система сохраняет состояние приложения (вызывается ли метод при

снимок при готовой сцене на Mac применяется через `setPath` (с анимацией).

## A5: несколько окон и окно настроек (2026-09-30)

**Статус: реализовано; UI-тест окна настроек Mac прошёл, тест возврата двух окон ждёт прогона, iPad на деле не проверен.**

- **Роль сцены.** `WindowScene(_:title:role:allowsMultiple:content:)`. `.standard` (по
  умолчанию) — сцена с содержимым приложения; при запуске и для «нового окна» берётся первая
  из них, порядок объявления с окном настроек значения не имеет. `.settings` — окно настроек:
  одно, при запуске не открывается, открывается командой «Настройки…» (Cmd-,), где платформа
  его берёт (Mac). `allowsMultiple: false` у обычной сцены — одно окно этого вида: просьба
  о втором выдвигает первое вперёд.
- **Открытие.** `Shell.openScene(_:)` возвращает `SceneOpenResult`: `.opened` (платформу
  попросили; на Mac окно уже есть, на iPad система подключает сцену позже, сессия появится в
  `Shell.sessions` тогда), `.activated` (вид с одним окном и окно есть — выдвинуто),
  `.unsupported` (нет такого вида или платформа не берёт вторую сцену: iPhone, Apple TV, iPad
  без `UIApplicationSupportsMultipleScenes`; для роли `.settings` — везде, кроме Mac).
  Молчаливой подмены запрошенного вида первым нет. `SceneSession.activate()` выдвигает сцену.
- **Команды.** `Command.newWindow` (Cmd-N) и `Command.openSettings` (Cmd-,) стоят на уровне
  приложения (`Shell`), включены, пока платформа берёт сцену такого вида. Меню Mac:
  `NSMenu(standardAround:newWindow:settings:)` — «New Window» в начале File, «Settings…» после
  About; добавляются, только если приложение объявило соответствующие сцены. На iPad
  «New Window» в File даёт сама система при `UIApplicationSupportsMultipleScenes`: она
  приходит в `configurationForConnecting` без активности, сцена получает первый обычный вид.
- **AppKit.** Окно на сессию; новое окно каскадом (вниз и вправо от ключевого), не поверх.
  Выдвижение — `deminiaturize` и `makeKeyAndOrderFront`. Восстановление теперь по окнам: при
  выходе сохраняется список `{вид, состояние?}` в порядке открытия (окно без своих
  восстанавливаемых контейнеров тоже возвращается); при запуске каждое окно берёт первую
  запись своего вида, лишние записи открывают окна. Состояние, пришедшее до первого окна,
  ждёт его. Окно настроек не сохраняется.
- **UIKit.** Просьба об окне — `requestSceneSessionActivation(nil, userActivity:…)` с видом в
  активности; в `configurationForConnecting` вид переходит в `userInfo` сцены и живёт там всю
  жизнь сцены. Выдвинуть сцену — `requestSceneSessionActivation` с её сессией (подключает
  заново, если система освободила виды). Восстановление у каждой сцены своё — так было с A4.
  Отключение отпускает окно, сессию и путь оставляет; окончательное закрытие
  (`didDiscardSceneSessions`) — с A2.
- **Демо.** `WINDOWS_PROBE=1`: окно заметок со стеком, у которого кнопка «Next note» идёт к
  следующей заметке (у каждого окна свой путь, он восстанавливается), и окно настроек. Демо iOS
  теперь берёт несколько сцен (`INFOPLIST_KEY_UIApplicationSupportsMultipleScenes`).

Проверено: 4 новых модельных теста `ShellTests` (`openScene` и его отказ без платформы и на
iPhone, команды, вид с одним окном и настройки, независимые пути и ссылка в свою сцену,
закрытие одной сцены не трогает другую); тест меню Mac; сборка пакета на iPhone и Apple TV
Simulator, демо iOS и Mac.

Прогоны пользователя: UI-тест Mac окна настроек (`WindowsTests`, одно окно, из меню, при
запуске не открыто) прошёл. Тест двух окон: новое окно начинает свой путь и нажатия идут в
переднее окно — прошло; возврат окон после выхода первым прогоном не прошёл — причина в тесте:
запуск с `-ApplePersistenceIgnoreState` состояния и не сохраняет, поэтому первый запуск теста
теперь идёт без флага и сам приводит окна к одному на первой заметке. Вручную (запуск демо с
пробой, «New Window» через меню, выход `osascript`, повторный запуск) без флага два окна
вернулись; с флагом на первом запуске — нет. Путь каждого окна вручную не смотрел.

Второй прогон (без флага на первом запуске): окна не вернулись с путями — причина в пробе,
не в адаптере. Маршруты заметок были одним шаблоном `/notes/:number`, а путь — URL последнего
экрана, каждое начало которого само экран: URL `/notes/2` даёт путь из одной заметки, без
корня, и восстановление отклоняет его как чужой. Маршруты пробы теперь по глубине (`/`, `/2`,
`/2/3`, …). Отказ восстановления назван в `RestorationResult` (`rootMismatch`), но демо его не
показывает.

Не проверено: возврат двух окон с их путями (тест после правки не запускался) — логика
возврата в `ShellApplicationDelegate` (запись, порядок, состояние до первого окна) проверяется
только им; iPad — открытие сцены, выдвижение,
повторное подключение и закрытие живьём не проверены (в Simulator несколько окон зависят от
режима окон системы); порядок и размещение окон Mac после возврата (кадр окна не
сохраняется); вид, открытый при запуске, когда сохранены окна другого вида (открывается
первый обычный вид, затем возвращаются сохранённые); окно настроек Mac не запоминает свой
размер.

## Решения (приняты 2026-09-28)

1. **Системные контейнеры.** Своя модель состояния и адаптер согласования обязательны;
   свой стек Mac — локальное исключение. Собственные анимации контейнеров — позднее.
2. **`AppShell`, `AppShellUIKit`, `AppShellAppKit`.** Названия описывают назначение и не
   зависят от имени продукта. Core собирается и тестируется без Apple UI.
3. **Экран отдельно от ноды.** `NodeScreen` владеет корневой `Node`; `ControllerScreen`
   адаптирует нативный контроллер. Это даёт одинаковые навигацию и жизненный цикл обоим
   видам содержимого. Для обычной ноды достаточно обёртки, отдельный подкласс не обязателен.
4. **Тип маршрута свой у каждого стека.** Общий enum приложения допустим, но не обязателен;
   идентичность экземпляра экрана отделена от равенства маршрута. Сериализация опциональна.
5. **Сначала явные импорты.** Core и выбранный адаптер. Один импорт — отдельное удобство
   позже, не причина вводить зависимость core от платформы или обязательный underscored API.
6. **Mac: Cmd-[ для стека, Escape для отмены/закрытия подходящего представления.**
   `Close Window` — отдельная команда; нативные поля ввода сохраняют свои клавиши.
7. **Синхронная фабрика экранов.** Данные загружаются в принадлежащих экрану/модели задачах;
   асинхронные проверки внешнего запроса отделены от создания экрана и имеют отмену.

Реализация начинается отдельной задачей. Остающиеся детали A0 — написание
экранного контракта, форма результата навигации, мост видимости/команд и отображение
диагностик — должны быть проверены на минимальном примере до фиксации публичного API.
