# ADR 0007 — Request-local measure cache без LRU на 64 записи

Дата: 2026-09-11.

## Контекст

`FlexMeasureCache` (C12, перенос из Weave) — LRU на 64 записи с линейным сканом,
живущий один layout-request. Каждый контейнер измеряет каждого ребёнка минимум дважды за
проход (под `.atMost` родителя для базисов, под `.exact` main-размера для cross-размера), а
проход размещения измеряет каждый уровень ещё раз. Дедупликация повторных пар
`(нода, constraint)` держится только на кэше; при дереве шире нескольких десятков нод LRU
вытеснял записи раньше повторного обращения, и стоимость вложенности росла как 2^depth:
глубина 12 — 35 ms, 14 — 141 ms (debug), глубина 30 (первый fixture C31) не завершалась
за 10 минут.

## Решение

Кэш — hash map `[LayoutMeasureCacheKey: FlexMeasureResult]` без практического предела:
`capacity` остаётся публичной константой, но равна `1 << 20` и служит только защитой от
патологического входа (вытеснение в порядке вставки). Первая попытка с `1 << 16`
упёрлась в дефект #14: цепочка глубины 200 (1000 нод) промахивается ~100k раз, и
вытеснение снова давало thrash — глубина 150 считалась 0.34 s, 180 не заканчивалась. Кэш по-прежнему создаётся на запрос и
умирает с ним (§3.8 анализа Weave, D09), поэтому его размер ограничен числом различных пар
`(нода, constraint)` одного прохода — памяти на это уходит меньше, чем на сам snapshot.

## Последствия

- API: `FlexMeasureCache.capacity` сохранена (значение изменилось), `store`/`lookup` —
  те же. Тест LRU заменён тестом «все записи реального запроса живут; вытеснение только
  за пределом».
- Глубина 14 — 5.5 ms вместо 141 ms; рост по глубине больше не экспоненциальный.
- Остаётся квадратичная составляющая: проход размещения измеряет каждый уровень под его
  фактическим cross-constraint, который отличается от constraint'а прохода измерения, и
  промахивается всем поддеревом — O(depth²) (дефект #14, открыт до замеров C26/C31 на
  Release). При глубине ≤ 30 это ≈ 10 ms в debug.
