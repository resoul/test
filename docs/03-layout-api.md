# Layout API

Имена в примерах черновые, кроме отмеченных как согласованные.

## Модель: как в Texture

**Статус: согласовано.**

- Подкласс `Node` создаёт дочерние ноды **один раз** в `init` и хранит их в свойствах.
- Внешний вид (`appearance`, `textStyle`, …) — свойства самих нод, задаются в `init` или
  при смене данных.
- Раскладка — отдельный метод, который **только ссылается** на существующие ноды и
  никогда их не создаёт.
- Нода встраивается в UIKit/AppKit через `addSubnode` ([05-platform-adapters.md](05-platform-adapters.md)).

```swift
final class ProfileCard: Node {
    private let avatar = Image()
    private let title = Text()
    private let subtitle = Text()
    private let follow = Button("Follow")

    init(user: User) {
        super.init()
        appearance.background = .color(.card)
        appearance.cornerRadius = 12
        avatar.appearance.cornerRadius = 24
        title.textStyle = .headline
        subtitle.textStyle = .caption
        update(user)
    }

    func update(_ user: User) {
        avatar.url = user.avatarURL
        title.text = user.name
        subtitle.text = user.handle
    }

    override func layoutSpec() -> LayoutSpec? {
        FlexContainer(.row) {
            avatar
                .size(48)

            FlexContainer(.column) {
                title
                subtitle
            }
            .gap(4)
            .flex(grow: 1, shrink: 1)

            follow
        }
        .alignItems(.center)
        .gap(12)
        .padding(16)
    }
}

// UIKit
view.addSubnode(ProfileCard(user: user))
```

Почему создание нод не переносится в раскладку: раскладка пересчитывается (поворот, смена
данных, брейкпоинт). Нода, созданная внутри, была бы новой на каждом проходе — терялись бы
слой, состояние и анимации. Отвергнутые варианты: создание в раскладке с кэшем по позиции
и описания-значения с реконсиляцией (SwiftUI).

## Метод раскладки

**Статус: реализовано** для `UIView`/`NSView` (модули `LayoutUIKit`/`LayoutAppKit`):
`func layoutSpec() -> LayoutSpec?`. Возвращаемый тип — `LayoutSpec`, а не `Layout`, чтобы не
спорить с `SwiftUI.Layout` в файлах, где импортирован SwiftUI.

`.padding` на элементе ведёт себя как в SwiftUI — применяется к тому, что до него:
`avatar.size(48).padding(8)` — аватар 48 в слоте 64; `avatar.padding(8).size(48)` — слот 48,
аватар 32. На контейнере `.padding` — обычный отступ содержимого.

- Имя `layout()` **нельзя**: у `NSView` уже есть системный `layout()` (аналог
  `layoutSubviews`), и `override` там означал бы совсем другое. `layoutSpec()` свободно
  в UIKit и AppKit и отсылает к Texture. Альтернативы `arrange()`, `makeLayout()` отклонены
  (2026-09-25).
- Метод **не является** result builder'ом: он возвращает одно значение `LayoutSpec?`, внутри
  доступен обычный Swift — `guard`, локальные переменные, ранний `return`. Builder
  действует только внутри фигурных скобок контейнеров.
- Один и тот же протокол «у меня есть раскладка» реализуют `Node`, `UIView`- и
  `NSView`-адаптеры.
- Когда раскладку надо пересчитать из-за смены данных, вызывается аналог
  `setNeedsLayout` (в Trellis — `markArrangementDirty()`). **Согласовано (2026-09-25):**
  `Node.setNeedsLayout()`; у `UIView`/`NSView` — `setNeedsLayoutSpec()`
  ([07](07-naming.md#прочие-имена)).

## Элементы раскладки

**Статус: согласовано.**

- Элементом является **сама нода** (или `UIView`/`NSView` в соответствующем адаптере).
  Обёртки `Leaf(node)` нет.
- **Опциональный элемент** (`Image?`) допустим: `nil` просто пропускается.
- Контейнеры — **только описание геометрии**, как `ASLayoutSpec`. `FlexContainer` не
  становится нодой и не получает `CALayer`.

## Управление subnodes

**Статус: согласовано** (по принципу), детали — предложено. **Срез реализован
(2026-09-24)** в модуле `Nodes`: `Node` (`layoutSpec()`, `update()`, `layoutContent`,
`frame`, `subnodes`, `supernode`, `isMounted`) и `NodeHost` (размер, масштаб, направление,
`onNeedsLayout`, `layoutIfNeeded()`). Раскладка всего дерева — один проход движка: нода с
`layoutSpec()` в раскладке родителя встраивается в неё как flex-контейнер
(`LayoutElement.embeddedLayout`), кадры детей — в координатах своей ноды. Что прочитано в
`layoutSpec()` — зависимость раскладки; что в `update()` — зависимость `update()`, который
идёт до первого замера ноды. 9 тестов на Linux.

**Второй срез (2026-09-24):** `Appearance` (фон, скругление, рамка, прозрачность, обрезка —
смена перерисовывает без раскладки), `NodesRender.LayerRenderer` (одно дерево `CALayer` на
дерево нод, только QuartzCore, общий для UIKit и AppKit), `NodeView`/`NodeNSView` и
`view.addSubnode(node)`. `NodeNSView` — layer-hosting с `isGeometryFlipped`, чтобы
AppKit не трогал геометрию слоя. Apple-часть на Linux не компилируется — проверяется на
Mac (`NodesRenderTests`).

**Третий срез (2026-09-24):** `Text` (CoreText, модуль `NodesRender`): измерение
(min-content — самое длинное слово, max-content — самая длинная строка, высота при ширине,
первая базовая линия) и рисование строятся одной `TextLayout`, так что измеренное
совпадает с нарисованным; `LayerDrawing` — нода рисует своё содержимое в bitmap слоя,
перерисовка только при смене ревизии, размера или масштаба. Картинка в `contents`
показывается как есть при любой геометрии слоёв вокруг — рисуется всегда прямо (#129).
Демо `Demo` на Mac: текст, вид, раскладка — подтверждены скриншотом.

Измерение текста не повторяется (2026-09-26, дефект #188). Нода `Text` хранит то, что
измерила (min/max-content, базовую линию, высоты для последних 32 ширин), пока не сменится
текст или стиль: движок задаёт те же вопросы на каждом проходе, а без этого каждый проход
заново шёл через CoreText по всем текстам экрана. Хранилище — под `OSAllocatedUnfairLock`:
измеритель работает и на потоке решения. Шрифты стилей кэшируются по потоку
(`Thread.threadDictionary`): `CTFont` не `Sendable` и между потоками не передаётся, а подбор
начертания по дескриптору дороже, чем набор строки. Замер `ScrollBench` (экран демо 640×600,
прокрутка ленивых списков по 300 точек, релизная сборка, Mac): проход раскладки — медиана
около 70 мс до, 2,8–4 мс после (движок — 1,7 мс); только кэш шрифтов — 9–16 мс, только кэш
измерений — 6–7 мс. Каждое правило проверено поломкой: 4 теста `TextTests`.

**Image (2026-09-25), первый срез:** статичное изображение из `Data`/URL, режимы
`.fit`/`.fill`/`.stretch`, дисковый кэш URL с настраиваемой обработкой метаданных и
опциональной PNG-оптимизацией. Контракт и границы — [11-image.md](11-image.md).
`Node.mountedChanged(_:)` — нода вошла в дерево хоста или вышла из него (на переходах, а
не на каждом проходе): `Image` при уходе отменяет загрузку и отпускает bitmap.

**Четвёртый срез (2026-09-24): нажатия.** `Node.hitTest` (самая глубокая видимая нода;
выступающие за рамку дети ловятся, если родитель не обрезает), `Node.onTap` — нажатие
получает ближайшая нода с действием вверх по дереву, как у кнопки: засчитывается, если
отпущено над той же нодой; `pressChanged` — вид нажатого состояния. `NodeHost.pointerDown/
pointerUp/pointerCancelled`, адаптеры передают touches (UIKit) и мышь (AppKit); то, что
не попало в ноду с действием, идёт дальше по responder chain. `Button` в `NodesRender`.
Демо — все кнопки нодами.

**Пятый срез (2026-09-24): `NodeCache`** (см. 04) **и расчёт в фоне.** `LayoutCore`:
`LayoutSpec.prepare` → `PreparedLayout` (`input` — `Sendable`, решается где угодно;
`apply(result, in:, scale:)` — на MainActor); `ContentMeasurer.requiresMainThread` (у
измерителей view — `true`). `NodeHost.solvesInBackground`: после первого прохода движок
работает на своём потоке со стеком 8 МиБ; `layoutSpec()`/`update()` и применение кадров —
на главном; до прихода новых кадров остаются старые; обогнанный расчёт отменяется
(`Thread.cancel` → точки отмены движка) и выбрасывается; раскладка с view внутри решается
на главном. Первый проход синхронный — view не появляется пустым. Демо включает фоновый
режим. Выравнивание `leading` в RTL (2026-09-25): у правого края, когда хост раскладывает
справа налево; иначе — по направлению самого текста (`natural`). Смена направления хоста
перерисовывает текст.
**Дополнено (2026-09-24):** `TextStyle.weight` (системный шрифт по весу), `lineSpacing`,
`maxLines` (высота — по первым строкам, последняя видимая обрезается «…»); измерение и
рисование по-прежнему идут через одни и те же строки `TextLayout`.

**Шестой срез (2026-09-24): доступность.** `Nodes`: `Accessibility` (isElement, label,
value, hint, traits), `NodeHost.accessibilityItems()` — элементы в порядке чтения:
текст — сам по себе элемент; нода с `onTap` — кнопка, названная текстом внутри, дети
отдельно не читаются; нода без того и другого — не элемент, читаются её дети; скрытые и
прозрачные пропускаются. `NodeHost.activate(id)` — действие элемента (нажатие).
Адаптеры: `UIAccessibilityElement` / `NSAccessibilityElement` хранят только `NodeID` и
слабую ссылку на хост (правило Trellis: нативные AX-объекты не читают живые ноды),
пересобираются после каждой отрисовки. 3 теста на Linux, 1 — AppKit на Mac.
Проверено (2026-09-24): тесты на Mac проходят, включая AppKit (13 в `NodesRenderTests`).
Не проверено: VoiceOver вживую на Mac и iOS, `UIAccessibilityElement` вне компиляции.

**Седьмой срез (2026-09-24): анимации.** Анимация принадлежит изменению, не ноде:
`withAnimation(.spring()) { model.isFollowing.value.toggle() }`. Всё, что изменение
вызвало, — раскладка (в том числе фоновая) и перерисовка `appearance` — рисуется с этой
анимацией (`NodeHost.renderAnimation`). `LayerRenderer` анимирует кадр (position, bounds),
прозрачность, фон, скругление, рамку от того, что показано сейчас (прерывание посреди
анимации — без скачка); новая нода в уже показанном дереве проявляется, ушедшая гаснет на
месте, скрытая (`invisible`, `Breakpoint`) гаснет, потом прячется. Кривые: linear, easeIn,
easeOut, easeInOut, spring(response, dampingRatio). 6 тестов на Linux, 10 рендерера — на Mac
(проверяют слои до `commit`: вне окна он снимает анимации, дефект #131). На экране
проверено на iOS Simulator (2026-09-24); на устройстве — нет доступа.

Дополнено (2026-09-25): новое содержимое (текст) при анимированном изменении проявляется
поверх прежнего (анимация `contents` той же длительности; у пружины — easeInOut, пружина
перелетала бы); без анимации меняется сразу, как раньше, и не растягивается с кадром. Нода,
перешедшая к другому родителю, начинает анимацию там, где была показана, — положение
пересчитывается в координаты нового родителя (рендерер запоминает за проход, где показаны
начала координат слоёв). Не сделано: смена размера окна не анимируется (так и задумано);
переходы (transition: slide/scale при появлении) — только проявление.

**Восьмой срез (2026-09-24): фокус tvOS.** Фокусируема нода с `onTap` (или
`isFocusable = true`), целиком. Куда двигать фокус, решает система tvOS: `NodeView` отдаёт
по `UIFocusItem` на ноду (`NodeHost.focusItems()`), `didUpdateFocus` сообщает хосту
(`NodeHost.focus`), нода узнаёт через `focusChanged` внутри `focusAnimation`; по умолчанию —
увеличение на 10 %, `Button` добавляет тень. Кнопка Select нажимает сфокусированную ноду.
`Appearance.scale` и `Appearance.shadow` анимируются. Демо — таргет `LayoutDemoTV` в `Demo/Demo.xcodeproj`. 6 тестов на
Linux, 1 рендерера — на Mac.

Проверено вживую на Apple TV Simulator (2026-09-24): стрелки переводят фокус между
бейджами и кнопкой, фокус анимируется, Select нажимает; на устройстве — нет доступа. Стрелки ищут
только по направлению нажатия, в полосе шириной с фокусированную ноду (так ищет tvOS),
поэтому ноды надо выстраивать в линию (дефект #134).

`NodeView.zoom` (2026-09-24): дерево раскладывается в `bounds / zoom` и рисуется в `zoom`
раз крупнее; текст растрируется под итоговый размер; нажатия, фокус и доступность
пересчитываются. По умолчанию (`nil`) — 2 на TV, 1 на остальных; можно задать любое
(например, 1,5). Проверено на Apple TV Simulator. `NodeNSView.zoom` (2026-09-25) — то же на
Mac, по умолчанию 1; клики и кадры доступности пересчитываются.

Секции фокуса (2026-09-24): `node.isFocusSection = true` — `NodeView` кладёт на площадь
ноды `UIFocusGuide`; движение к любой её части фокусирует ноду внутри (последнюю
фокусированную там, иначе первую); пока фокус внутри, направляющая выключена. Как
`.focusSection()` в SwiftUI на tvOS. В демо — карточки и ряд с кнопкой. Проверено на
Apple TV Simulator.

Фокус с клавиатуры (2026-09-24). `NodeHost.focusLook`: `.lift` (TV — нода крупнее, с
тенью) или `.ring` (iPad, Mac — адаптер рисует рамку `FocusRing` цвета системы; нода по
умолчанию не меняется). iPad: те же `UIFocusItem`, система включает их с клавиатурой;
Return/Space нажимают. Групп фокуса нет: `focusGroupIdentifier` недоступен на tvOS, а
ветка по платформе — только `#if os` (дефект #135). Mac:
`NodeNSView` — first responder; Tab/Shift-Tab по нодам в порядке чтения, после последней —
к следующему view окна (`NodeHost.moveFocus`); стрелки — к ближайшей ноде в эту сторону;
Return/Space нажимают; клик рамку не показывает. 3 теста на Linux, 2 AppKit — на Mac.
Проверено вживую (2026-09-24): Mac (Tab, рамка), iPad Simulator с клавиатурой, Apple TV
Simulator; на устройствах — нет доступа.

Перевод фокуса из кода (2026-09-24): `host.requestFocus(id)` — адаптер просит систему
фокуса (UIKit: `requestFocusUpdate` к элементу ноды, до перехода он — предпочтительный;
AppKit: view становится first responder и фокусирует ноду); без адаптера хост фокусирует
сам. `host.focus(id)` — только сообщение адаптера о переходе. В tvOS-демо — Play/Pause.

В Mac Catalyst работает UIKit-путь фокуса: тесты фокуса UIKit проходят на Catalyst, демо
для iOS собирается под Catalyst и рисуется (2026-09-25, после #153). Tab по кнопкам в
Catalyst-демо проверен пользователем на Mac: кольцо фокуса переходит на следующую кнопку
(скриншот, 2026-09-25). Прокрутка к ноде, получившей фокус, — ниже, в «Прокрутке».

**Девятый срез (2026-09-25): прокрутка.** Вариант «рисуют слои, система даёт только
физику» (решение 2026-09-25): системный scroll view в дерево не встраивается, поэтому
обрезка, анимации, порядок слоёв и RTL работают как у любой ноды — класс дефектов #90–#92
Trellis не возникает.

```swift
let feed = Scroll(.vertical, content: FeedList())   // или .horizontal

FlexContainer(.column) { header; feed }            // feed занимает место под header
```

- `Scroll: Node` (модуль `Nodes`, без платформы). Одна нода содержимого (`content`);
  вдоль оси она раскладывается во всю длину (`shrink 0`) и не короче окна (`grow 1`),
  поперёк — растягивается. `contentOffset` — точка содержимого в левом верхнем углу;
  хранится в `State`, поэтому чтение в `layoutSpec()`/`update()` — зависимость (липкая
  шапка, параллакс). Запись прокручивает сразу или с анимацией `withAnimation`; значение
  за краем показывает край. `onScroll`, `contentBounds`, `offsetRange`, `canScroll`,
  `scrollToReveal(_:)`.
- Размер: базовый размер — от содержимого, поэтому размер, заданный при размещении
  (`scroll.size(height: 80)`), работает как у любой ноды. При нехватке места Scroll
  сжимается раньше соседей (коэффициент сжатия 10⁶) до нуля вдоль оси (как CSS scroll
  container); вертикальный ещё и растёт в свободное место. Горизонтальный — поперёк не
  меньше содержимого: лента карточек в колонке высотой с карточки. Модификаторы родителя
  всё это переопределяют. Сначала пробовал `flex-basis: 0` — отказался: по CSS он сильнее
  `height`, и явная высота прокрутки в колонке переставала работать.
- RTL: горизонтальное содержимое шире окна раскладывается от правого края и уходит в
  отрицательные x; диапазон смещений начинается там (`offsetRange.lowest.x < 0`), смещение
  0 показывает начало строки справа.
- Попадание касаний, кадры фокуса и доступности учитывают смещение; содержимое за окном
  обрезано. Фокус, перешедший к ноде внутри прокрутки (клавиатура, `requestFocus`),
  прокручивает к ней все прокрутки вокруг, внутреннюю первой, в анимации фокуса.
- Отрисовка: смещение — `bounds.origin` слоя прокрутки. Прокрутка без анимации не
  перерисовывает дерево: `NodeHost.scrolledSinceRender` → `LayerRenderer.renderScrolls`
  двигает только слои прокруток. Полоса прокрутки — слой поверх содержимого, показывается
  при движении и гаснет сама (keyframe-анимация прозрачности, без таймеров).
- `platformDidScroll(to:)` — для адаптеров: смещение от системной физики, часть за краем —
  `overscroll` (отскок на iOS), в `contentOffset` не входит.
- Адаптеры — [05](05-platform-adapters.md#прокрутка).

Проверено (2026-09-25): 15 тестов ноды (Linux-совместимые), 4 рендерера и 4 AppKit — на
Mac; 5 UIKit — на iPhone 17, iPad Air, Apple TV 4K Simulator и в Mac Catalyst. Вживую на
iPhone 17 Simulator (демо): вертикальный список листается пальцем с инерцией и отскоком у
края, горизонтальная лента внутри него листается вбок, не сдвигая список, нажатия после
прокрутки попадают в свои ноды. Демо на Mac рисуется; колесо проверено тестами, вживую —
нет. На устройствах — нет доступа.

**Sticky (2026-09-25).** `.sticky(top:leading:bottom:trailing:)` — CSS `position: sticky`:
элемент остаётся на своём месте в раскладке, а при прокрутке держится в заданном
расстоянии от края окна ближайшей прокрутки, пока в окне его flex-контейнер; следующая
секция выталкивает заголовок предыдущей.

```swift
FlexContainer(.column) {          // секция
    header.sticky(top: 0)
    for row in rows { row }
}
```

- Движок о sticky не знает: раскладка не меняется. Элемент получает при применении
  раскладки отступы и рамку своего ближайшего flex-контейнера (в том числе безымянного
  `FlexContainer`) — `LayoutElement.applyLayoutSticky(StickyPosition?)`. Сдвиг
  (`Node.stickyOffset`) считается из смещения прокрутки по CSS Positioned Layout §3.4, без
  прохода раскладки — рендерер и быстрый путь прокрутки двигают только слой.
- Sticky-нода рисуется и получает нажатия поверх остальных элементов своего контейнера, как
  позиционированный блок в CSS (`Node.subnodesInDrawingOrder`); фокус и доступность видят
  её там, где она показана. Порядок чтения — прежний.
- `leading`/`trailing` — по направлению раскладки; вне прокрутки ничего не двигается.
- Отличие от CSS: граница — рамка контейнера, а не его content box (отступ контейнера не
  вычитается); вложенные sticky считаются от несдвинутых кадров.

«Потяни, чтобы обновить» (2026-09-27). `scroll.onRefresh = { await model.reload() }` и
`scroll.refreshIndicator = RefreshSpinner()`: вертикальную прокрутку тянут вниз за верх; если
за этот жест натяжение хоть раз дошло до `refreshDistance` (56 точек), отпускание начинает
обновление — как у системного `UIRefreshControl`, даже если к отпусканию палец ослабил. Над
содержимым открывается место `refreshSpace` (56 точек, нижняя граница смещения ниже нуля), в
нём индикатор; когда `onRefresh` вернёт, место закрывается пружиной. `beginRefresh()` —
то же из кода (кнопка, пульт); начатое ниже по списку место открывает, но содержимое не
двигает. `isRefreshing` — идёт ли.

- `RefreshIndicator` (протокол `Nodes`): нода, которой прокрутка сообщает натяжение (0…1) и
  идёт ли обновление; прокрутка ставит её над содержимым (`absolute`, высота места), в
  границы содержимого она не входит. `RefreshSpinner` (`NodesRender`) — дуга, растущая с
  натяжением, до трёх четвертей кольца; во время обновления крутится и становится элементом
  доступности «Refreshing».
- `Appearance.spin` — обороты в секунду: слой крутится непрерывно (добавочная анимация
  `transform.rotation.z`, поверх масштаба и переходов), пока значение не 0.
- UIKit: отпускание за порогом — цель скольжения на открытое место, поля физики с ним.
  Mac: пальцы, отпущенные за порогом, вместо пружины назад открывают место. tvOS тянуть
  нечем — только `beginRefresh()`.

Масштаб (2026-09-27). `scroll.zoomRange = 1...4` — содержимое прокрутки масштабируется
щипком или `zoom(to:around:)` (в `withAnimation` — с анимацией): при 2 рисуется вдвое крупнее

содержимого не меняется. `zoomScale` — текущий масштаб, `isZoomable`,

- Рисование: слой содержимого — с масштабом от начала содержимого; текст и рисунки внутри

  трекпад двигают масштабированное содержимое в обе стороны. tvOS — только из кода.

Прокрутка к элементу, на который
встал VoiceOver на Mac, — с 2026-09-27: элементы принимают действие `AXScrollToVisible` (десятый
срез, Mac); шлёт ли его живой VoiceOver при каждом переходе, не проверено.

**Десятый срез (2026-09-26): ленивый стек.** `Scroll` раскладывает содержимое целиком, и
все его ноды смонтированы — для длинного списка это тысячи нод, слоёв и загрузок картинок.
`LazyStack` — колонка (или строка) нод для `items`, которая раскладывает только элементы
у окна; кладётся внутрь `Scroll`, одна или рядом с другими нодами (как `LazyVStack` в
`ScrollView` SwiftUI). Трудоёмкость прохода не зависит от числа элементов.

```swift
private let rows = NodeCache<Post.ID, PostRow> { _ in PostRow() }
private lazy var posts = LazyStack(estimatedLength: 72) { [rows] post in
    rows[post.id].showing(post)
}
private lazy var feed = Scroll(.vertical, content: posts)

override func update() { posts.items = model.posts.value }
```

- Замыкание — то же, что тело `for` в обычной колонке с `NodeCache`: переход от колонки к
  ленивому стеку не меняет строк. Оно вызывается в проходе раскладки только для элементов
  у окна; кэш отпускает ноды ушедших далеко (правило `NodeCache` — через проход).
- Окно — видимая часть стека вдоль оси: пересечение всех обрезающих предков
  (`clipsContent`, прокрутки) и границ хоста. Раскладывается окно плюс экран хоста до и
  после. Новый проход стек просит сам, когда окно с запасом в пол-экрана выходит за
  разложенное: прокрутка внутри запаса проходов не вызывает. Смещение прокрутки стек
  смотрит без зависимости (`untracked`) — иначе проход был бы на каждом кадре.
- Длина неразложенного элемента — измеренная при последней раскладке на текущей ширине
  (смена ширины сбрасывает измерения) или `estimatedLength`. Место до и после окна —
  отступы контейнера (`padding`), промежутки — `gap(spacing)`; стек всегда длиной во весь
  список, и диапазон прокрутки меняется по мере измерений.
- Якорь: если до окна элементы изменили длину (разложились впервые, добавлены, удалены),
  ближайшая прокрутка по оси сдвигается на столько же — видимое не прыгает. Не сдвигается,
  когда окно показывает начало стека: тогда видно добавленное в начало. Сдвиг сохраняет
  `overscroll` (`Scroll.shiftOffset`). Якорь запоминается до выбора окна, и окно берётся
  там, куда сдвинулся якорный элемент, — вставка больше экрана перед окном видимое тоже не
  сдвигает (2026-09-26, дефект #172).
- `NodeHost`: ноды, зависящие от окна (`ViewportDependent`), получают `layoutApplied()` после
  каждого прохода и `viewportMoved()` при каждом движении прокрутки. `layoutIfNeeded()`
  делает до 4 проходов подряд (`settlingPasses`), пока такие ноды просят ещё: первый проход
  не знает, где стек, и измеренные длины отличаются от оценки. До первого монтирования стек
  берёт размер экрана у хоста, который готовит раскладку (`NodeHost.preparing`).
- В фоне (`solvesInBackground`) движение, которое покрывает уже запрошенный проход, нового не
  просит — иначе каждый кадр отменял бы решение в полёте. Проход, нужный потому, что окно
  уже вышло за смонтированные элементы, решается на главном потоке сразу
  (`NodeHost.setNeedsLayoutNow`): из фона он пришёл бы через кадры, а при быстрой прокрутке
  каждый следующий отменял бы предыдущий, и окно оставалось пустым (2026-09-26, дефект #185;
  на Mac одно решение демо в отладочной сборке — до 35 мс). Проход, которому не хватает только
  запаса, по-прежнему в фоне. Проверено: тест AppKit — `NodeNSView`, настоящее фоновое
  решение, 10 000 строк текста, полэкрана за кадр 120 Гц в течение секунды — ни одного кадра
  с пустым местом в окне (до исправления — треть кадров); тест ноды — окно за разложенным
  раскладывается в том же вызове.
- RTL: строка в RTL начинается справа, окно считается от правого края.

Сетка (2026-09-26): `lanes` — сколько элементов стоит рядом поперёк оси (столбцы вертикального
стека, строки горизонтального). Элементы идут рядами по `lanes`, делят ширину поровну
(`flex: 1 1 0`, минимум 0), неполный последний ряд добивается пустыми долями, чтобы его
элементы были той же ширины. Ряд длиной с самый длинный элемент: элементы ряда растянуты до
него, неразложенный ряд берёт наибольшую из длин своих элементов (измеренных или оценки) —
после вставки ряды пересобираются из элементов, измеренных в разных рядах. Окно, запас и якорь
считаются по рядам, раскладываются только целые ряды. `spacing` — и между рядами, и между
элементами ряда. В демо — 600 квадратов по четыре в ряд.

```swift
let photos = LazyStack(items: model.photos, lanes: 3, estimatedLength: 120, spacing: 2) { photo in
    cells[photo.id].showing(photo)
}
```

Анимированный переход к далёкому месту (2026-09-26). Смещение, заданное в
`withAnimation`, Core Animation анимирует на слое прокрутки, а стек раскладывает только
конечное окно — на переходе дальше экрана между началом и концом было пусто. Теперь такой
переход идёт покадрово, как `setContentOffset(_:animated:)` у `UIScrollView`:

```swift
withAnimation(.easeInOut(duration: 0.8)) {
    feed.contentOffset = feed.offsetRange.highest
}
```

- Покадрово — только когда внутри прокрутки есть стек, для которого переход длиннее его
  запаса (экран хоста): тогда конечная раскладка не держит начальное окно
  (`ViewportDependent.needsFrames(toMove:by:)`). Короче — прежняя анимация слоя, в том
  числе шаги фокуса на Apple TV.
- `Scroll` хранит движение (откуда, куда, анимация), `contentOffset` читает, где оно сейчас.
  `NodeHost.needsFrames` просит у адаптера кадры (`onNeedsFrames`); на каждом кадре дисплея
  адаптер вызывает `advanceFrames(to:)` со временем кадра, и смещение ставится без
  анимации — как пальцем: стек раскладывает окно там, где кадр, отрисовка двигает только
  содержимое прокрутки. Первый кадр — начало движения.
- Кривые — как у Core Animation: те же Безье для `easeIn`/`easeOut`/`easeInOut`, пружина
  единичной массы из покоя с жёсткостью и затуханием, которые рендерер даёт
  `CASpringAnimation` (`Animation.progress(at:)`).
- Проход каждого кадра решается на главном потоке и в этом кадре, даже при
  `solvesInBackground`: в фоне проход каждого кадра обгонял бы предыдущий, и до конца пути
  ничего бы не применилось.
- Якорь в пути: элементы до окна, разложенные впервые, сдвигают смещение, чтобы видимое не
  прыгало. Если цель за окном (дальше от начала), она сдвигается так же и приходит на то же
  содержимое; если перед окном — остаётся, а начало пути пересчитывается, чтобы путь
  проходил через текущее смещение без рывка. Переход к концу (цель — `offsetRange.highest`)
  идёт к концу, как бы ни вырос список по пути, и заканчивается, когда кадр застал смещение
  на конце: последний кадр раскладывает элементы у конца, и они могут оказаться длиннее
  оценки.
- Остановка: сдвиг платформой (палец, колесо — `platformDidScroll`) или смещение без
  анимации останавливают движение там, где оно есть. Новое анимированное смещение начинает
  путь с текущего места.

Переход к элементу (2026-09-26): `stack.scroll(to: id)` прокручивает ближайшую прокрутку по
оси стека так, чтобы элемент начинался у начала окна — насколько прокрутка позволяет (у
конца списка — конец). В `withAnimation` — с анимацией, дальше экрана — покадрово.

```swift
withAnimation(.easeInOut(duration: 0.8)) {
    posts.scroll(to: message.id)
}
```

- Цель считается по тому, где начинается ряд элемента сейчас (измеренные длины и оценки), и
  пересчитывается на каждом кадре движения (`Scroll.scroll(to:following:)`): элементы в пути
  раскладываются и уточняют длины. Движение заканчивается, когда кадр застал смещение на
  цели, но не дольше 8 кадров после своего времени — если список всё время меняется.
- Без анимации: первая раскладка у элемента уточняет длины вокруг него, и после каждого из
  следующих проходов (до `settlingPasses`) прокрутка ставится на элемент снова; якорь в
  этих проходах не действует — прокрутку ведёт элемент.
- Ноды, прилипшие к началу окна (`sticky(top:)`, у ведущего края строки — `sticky(leading:)`),
  элемент не закрывают: он ставится после них. Считается, где они были бы на целевом
  смещении, — заголовок ушедшей секции или стоящий ниже начала окна не учитывается.
- В сетке — ряд элемента. В строке RTL элемент встаёт у правого края окна.
- Нет такого `id` или стек не в прокрутке — `false`, прокрутка не двигается.

VoiceOver в длинном списке (2026-09-26). Раньше VoiceOver получал плоский список элементов
только из разложенных строк: он не знал, что это список, что в нём 10 000 строк, а список,
не разложенный вовсе (ниже экрана), перепрыгивал целиком — от сетки сразу к кнопке под
строками. Теперь ленивый стек для VoiceOver — список, в котором есть все строки, как у
`UICollectionView`:

- `NodeHost.accessibilityEntries()` — порядок чтения, где каждый ленивый стек — одна запись
  `.list(AccessibilityList, [AccessibilityItem])`, даже если ни одна его строка не разложена.
  `AccessibilityList`: число строк, разложенные (`laidOut`), видимая часть. У элемента строки —
  `listItem` (стек и номер строки). `accessibilityFrame(ofItem:in:)` — где строка есть или
  ожидается (по измеренным длинам и оценкам, в сетке — в своей доле ряда);
  `revealItem(_:in:)` прокручивает к строке и раскладывает её. `accessibilityItems()` — прежний
  плоский список.
- Список как таблица (2026-09-27): `AccessibilityList.rowCount`, `columnCount`,
  `position(ofItem:)`, `item(row:column:)`. Строки вертикального стека — ряды таблицы, полосы
  (`lanes`) — столбцы: обычный список — один столбец, сетка в три полосы — три. У
  горизонтального наоборот: полосы — ряды, ряды стека — столбцы.
- UIKit (iOS, iPadOS, tvOS, Catalyst): стек — `ListAccessibilityContainer`, таблица данных:
  `accessibilityContainerType = .dataTable` и `UIAccessibilityContainerDataTable` (число рядов и
  столбцов, элемент по ряду и столбцу — первый элемент строки или её заглушка). Элементы строк и
  заглушки — `UIAccessibilityContainerDataTableCell`: ряд и столбец своей строки; у элементов вне
  списка — `NSNotFound`. Другого способа сказать VoiceOver «строка N из M» в UIKit нет: у
  `.list` позиции элемента нет. До 2026-09-27 был `.list`. Контейнер
  отдаёт элементы по номеру (`accessibilityElementCount`, `accessibilityElement(at:)`,
  `index(ofAccessibilityElement:)`): строки до разложенных, элементы разложенных, строки после.
  Неразложенная строка — `ListItemStandIn` с ожидаемой рамкой; VoiceOver, встав на неё,
  прокручивает список к строке, раскладывает её и переходит на её элемент
  (`UIAccessibility.post(.layoutChanged, argument:)`). Элементы строк лежат в контейнере, их
  рамки — в его координатах.

  ручного режима нет. `UIView.addSubnode` — встраивание корня в view, к этому не относится.

## Собственные контейнеры

**Статус: решено (2026-09-27) — свой алгоритм раскладки; публичный протокол не заморожен,
реализуется вместе с первым настоящим контейнером.**

Контракт «размеры детей → их места» узок: размер ребёнка зависит от предложенных ограничений
(текст в колонке 200 и 400 точек разной высоты). Алгоритм контейнера:

- получает ограничения контейнера;
- может измерять детей с разными ограничениями, сколько нужно раз;
- возвращает размер контейнера и места детей;
- работает со `Sendable`-снимком, без доступа к живым нодам и view — считается в фоне, как
  Flexbox;
- поддерживает отмену (`LayoutCancelled`) и кэш измерений в пределах прохода.

Разделение измерения и размещения есть и у `Layout` в SwiftUI, но контракт соответствует
своему движку ([10](10-layout-engine.md)), а не копирует чужой.

`Overlay`, `Center`, `Spacer` из словаря ниже рассматриваются отдельно. Для `Overlay` сначала
решить, какие дети влияют на размер контейнера: одного абсолютного позиционирования для этого
недостаточно.

## Таблица со swipe-действиями (2026-09-27)

`Table<Item>` (`NodesRender`) — строки по секциям поверх `LazyStack`: раскладываются только
возле окна; касание выбирает строку, свайп открывает её действия — как список в Почте или
Настройках. **Статус: реализовано; имена — предложено.**

```swift
let inbox = Table<Message> { message in cells[message.id].showing(message) }
inbox.sections = [TableSection(id: "today", title: "Today", items: messages)]
inbox.onSelect = { message in open(message) }
inbox.trailingActions = { message in
    [SwipeAction("Delete", role: .destructive) { model.delete(message) },
     SwipeAction("Flag", color: .orange) { model.flag(message) }]
}
inbox.leadingActions = { message in [SwipeAction("Read") { model.markRead(message) }] }
```

- Свайп к ведущему краю открывает `trailingActions`, к заднему — `leadingActions`; кнопки
  стоят за ячейкой, ячейка отъезжает. Отпустив: дальше 60% строки — сразу первое действие;
  дальше половины кнопок или бросок быстрее 300 точек/с — кнопки открыты, иначе строка
  возвращается. Тянется только к действиям, которые есть, и не дальше ширины строки.
- Одна строка открыта за раз: открылась другая, прокрутили, коснулись открытой ячейки — она
  закрывается (касание не выбирает её). Нажатие кнопки закрывает строку и делает действие.
- Секции: заголовок (`TableSection.title`) — строка-заголовок доступности; разделители под
  ячейками. `scrolls: false` кладёт таблицу в прокрутку вокруг, без своей.
- Доступность: строка — один элемент (текст содержимого) с действиями строки
  (`accessibilityActions` → «Действия» VoiceOver на iOS, `NSAccessibilityCustomAction` на
  Mac); кнопки за ячейкой не читаются и не фокусируются. Пульт tvOS идёт по строкам, если есть
  `onSelect`; свайпа там нет.
- RTL: ведущий край справа — свайп влево открывает `leadingActions`.

Под таблицей — три новые общие возможности:

- `Node.dragAxis` и `onDrag` (`Drag`: фаза, сдвиг, скорость) — нода, которую тащат по оси;
  `NodeHost.canDrag`, `dragBegan/Moved/Ended/Cancelled` — для адаптеров. Перетаскивание
  забирает касание: ноду не нажимают. UIKit — свой `UIPanGestureRecognizer` на view нод,
  начинается только если пан идёт в основном по оси ноды под пальцем; пан прокруток ждёт его
  отказа (`require(toFail:)`), как у `UITableView`. Mac — первое движение пальцев по трекпаду
  решает: по оси ноды — перетаскивание (скольжение после него гасится), иначе прокрутка.
- `Appearance.offset` — сдвиг рисунка без раскладки (как CSS `translate`); касания, фокус и
  доступность видят ноду там, где она нарисована.
- `Node.accessibilityActions` (`AccessibilityAction`) — действия элемента помимо активации;
  `AccessibilityItem.actions`, `NodeHost.performAccessibilityAction(_:of:)`.

Проверено (2026-09-27): модель — перетаскивание (ось, забранное нажатие, отмена), сдвиг
рисунка (касание, доступность, без раскладки), действия доступности; 12 тестов таблицы —
секции и выбор, свайп к кнопкам и нажатие «Delete», короткий свайп назад и бросок, полный
свайп — первое действие, свайп в другую сторону, RTL, одна открытая строка и касание
закрывает, прокрутка закрывает, только к действиям, что есть, и не дальше строки, фокус
пульта, VoiceOver — действия строки, кнопки не читаются; адаптеры — трекпад поперёк строки
тащит её и не прокручивает, вдоль — прокручивает, ось пана UIKit, действия VoiceOver (UIKit и
Mac); намеренные поломки — каждую ловит тест. Вживую на iPhone 17 Simulator (демо, раздел
«Inbox», касания симулятора): свайп влево открыл «Delete» и «Flag», «Delete» удалил письмо,
свайп вправо — «Read», он снял отметку непрочитанного. Трекпадом Mac и пультом вживую — нет;
на устройствах — нет доступа.

### Режим правки: перестановка и выбор нескольких строк (2026-09-27)

```swift
inbox.onMove = { move in model.move(move.item, from: move.from, to: move.to) }
inbox.allowsMultipleSelectionDuringEditing = true
inbox.onSelectionChange = { ids in toolbar.selected = ids }
withAnimation { inbox.isEditing = true }
```

- `isEditing` — строки не свайпаются (открытая закрывается); с `onMove` у каждой справа
  ручка «≡», с `allowsMultipleSelectionDuringEditing` слева круглая отметка, касание строки
  отмечает её или снимает отметку (`selection`, `onSelectionChange`) — отметка меняется сразу,
  не дожидаясь раскладки. Выбранная строка — голубой фон и признак доступности «выбрано».
  `canMove` — какие строки двигаются (у остальных нет ручки). Id писем, которых больше нет
  в `sections`, уходят из `selection` (с `onSelectionChange`).
- Перетаскивание ручки поднимает строку: она рисуется над остальными (`zIndex`), с тенью, и
  идёт за пальцем; сосед отъезжает, когда середина строки пересекла его середину (как у
  `UITableView`; до 2026-09-27 — середину в раскладке без строки, на место раньше, #201). Место — по
  середине строки: не выше заголовка первой секции; над заголовком секции — в конец
  предыдущей, под ним — в начало его секции (`TablePosition`). У края окна (60 точек)
  прокрутка — своя или вокруг таблицы — едет со скоростью до 600 точек/с, тем быстрее, чем
  ближе к краю, строка остаётся под пальцем. Отпустили — строка опускается на место,
  `sections` уже в новом порядке, `onMove` получает `TableMove` (что, откуда, куда: номер в
  секции после переноса). Отмену системой строка возвращает на старое место; конец правки —
  кладёт строку, куда её дотащили.
- Как устроено: пока строку тянут, таблица не раскладывается заново — соседние рисуются
  сдвинутыми (`Appearance.offset`, шаг к цели каждый кадр по таймеру, ~0,1 с). Порядок
  элементов меняется, когда строку отпустили (или она ушла дальше окна от своего места —
  чтобы оставаться в разложенной части ленивого стека), без удержания видимого
  (`LazyStack.setItemsHoldingScroll`); сдвиги снимаются в тот же проход, когда раскладка
  нового порядка смонтирована (`LazyStack.onLayoutApplied`). Так раскладка в фоне, даже
  медленная, не отрывает строку от пальца (#195).
- VoiceOver: у строки в правке действия «Move up» / «Move down» (через край секции — в
  соседнюю); кнопки и ручки не читаются.
- Mac: мышь тоже тащит ноды (`NodeNSView.mouseDragged`: после 4 точек первое движение решает
  ось, как у трекпада) — ручку, и свайп строки мышью.
- tvOS: отметки выбираются пультом (строка фокусируется в правке с выбором); переставлять —
  только действиями VoiceOver. Пульт доходит до нод за таблицей, в которой ничего не
  фокусируется, как бы высока она ни была (#198). UI-тест tvOS жмёт «вниз», пока «Rename
  Ada» не покажется, а не фиксированное число раз: нажатие во время прокрутки теряется.

Новое в модели для этого: `Appearance.zIndex` (порядок рисования среди соседей, как CSS
`z-index`; касание находит верхнюю), `LazyStack.setItemsHoldingScroll`,
`LazyStack.onLayoutApplied`.

Проверено (2026-09-27): 21 тест режима правки — отметки и выбор касанием (и без выбора — касание не берётся), без свайпа и с
действиями «Move», перетаскивание с раздвиганием соседних и `onMove`, над заголовком — в
конец предыдущей секции, под заголовком — в начало его, не выше первого заголовка,
прокрутка у края (своя и внешняя), строка под пальцем при раскладке в фоне, отмена, конец
правки посреди перетаскивания, новые `sections` посреди перетаскивания, строка далеко от
своего места остаётся разложенной, раскладка старого порядка после отпускания не сбивает
строку, короткие строки не выше первого заголовка, прокрутка вверх у верхнего края,
VoiceOver через край секции, `canMove`, выбор чистится; 24 намеренные поломки — каждую ловит
тест;
модель — `zIndex` (порядок, касание), замена элементов без удержания; Mac — мышь тащит
строку поперёк и не тащит вдоль. Вживую на iPhone 17 Simulator (демо «Inbox», «Edit»):
отметки и «Delete 2» удалил два письма; строка, дотащенная к низу экрана и удержанная,
прокрутила ленту и встала там, где её отпустили (отладочная и релизная сборки). Мышью на Mac
(2026-09-27, UI-тесты `Demo/MacUITests/MouseTests`, настоящие события мыши через XCUITest):
колесо листает ленту до входящих, полный свайп мышью удаляет письмо, ручка в режиме правки
переставляет письмо на два места при протягивании на 2,5 строки (до исправления #201 — на
три), колесо листает страницы пейджера по одной. Щипок и жесты трекпада XCUITest не
отправляет — трекпадом вживую нет; на устройствах — нет доступа.

**Выбор нескольких строк вне правки — реализовано (2026-09-28).** `Table.allowsMultipleSelection`:
касание строки добавляет её в `selection` или убирает оттуда вместо `onSelect` и сообщает
`onSelectionChange`. Выбранная строка подсвечена (смесь поверхности с акцентом, как в правке)
и несёт признак доступности «выбрано». Отметок нет, свайп с действиями остаётся. На TV строки
доступны пульту, Select делает то же, что касание. Выключенный режим оставляет `selection`,
но строки её не показывают, и касание снова вызывает `onSelect`. Проверено: модульный тест
(касания, `onSelectionChange`, без `onSelect` и без отметок, признак доступности, заливка,
свайп, выключение). В демо не включено. На Mac клик выбор переключает: Cmd и Shift, как в
`NSTableView` (одна строка по клику, добавить, диапазон), не сделаны — у касания ноды нет
модификаторов клавиш.

**Перестановка пультом и клавиатурой — реализовано (2026-09-28).**
`Node.onMoveCommand`: стрелка, нажатая при фокусе на ноде, сначала идёт ноде; если она её
берёт, фокус не двигается. Спрашивается нода с фокусом, иначе ближайшая вокруг, у которой он
есть (`NodeHost.moveCommand`). tvOS — `NodeFocusItem.shouldUpdateFocus` и неудавшийся переход
фокуса; Mac — стрелки в `NodeNSView.keyDown`. В правке таблицы ручка берёт фокус: Select
поднимает строку, вверх и вниз двигают на одну (`onMove` на каждый шаг), в стороны — ничего,
Select или уход фокуса опускает; конец правки тоже. Шаг за окно прокручивает к строке. С
отметками фокус для выбора берёт отметка (ручка внутри фокусируемой ячейки фокус не получила
бы). Система фокуса tvOS спрашивает о стрелке несколько раз за нажатие — ноде передаётся один
раз (`NodeView.takesMove`, #205). Проверено: 4 модульных теста таблицы, стрелки Mac, один
ответ на нажатие (UIKit); UI-тест tvOS `TableMoveTests` на экране `MoveProbe` (`MOVE_PROBE`,
Apple TV Simulator): подъём, два шага вниз, в сторону — на месте, опускание, затем фокус к
следующей ручке и шаг вверх. Попутно таблица в правке перестала просить раскладку на каждом
проходе (#206) — на TV экран с ней замирал.

Не сделано: перетаскивание строки между разными таблицами.

## Модификаторы — параметры места в родителе

**Статус: согласовано.**

Модификатор возвращает значение «элемент + параметры для родителя» и **ничего не пишет в
ноду**. Следствия:

- удалил модификатор — его эффекта больше нет, следов прошлого прохода не остаётся;
- одну ноду можно поставить в разные раскладки (например, в разные ветки `Breakpoint`) с
  разными параметрами;
- базовые свойства ноды (`style` в Trellis) остаются под контролем владельца ноды.

Это исправляет известное неудобство Texture, где `node.style.flexGrow` хранится в ребёнке,
хотя имеет смысл только относительно родителя.

`.padding(...)` на элементе — отступ **в раскладке** (аналог `ASInsetLayoutSpec`), а не
свойство ноды.

## Фокус пульта через высокий блок (2026-09-27)

UIKit ищет, куда перевести фокус, в полосе шириной с сфокусированную ноду и не дальше примерно
пяти окон, а при дальнем переходе сам ведёт прокрутку и может остановить её не у цели. Когда
он сообщает, что двигать некуда (`UIFocusSystem.movementDidFailNotification`), `NodeView` сам
ищет ближайшую ноду в том направлении по всему содержимому скролла ноды (затем внешних),
прокручивает к ней и переводит фокус; ноду в фокусе, оставшуюся после прокрутки UIKit за
краем, довозит в видимую часть. Обычные переходы UIKit не меняются. Проба для ручных замеров —
`Demo/TV/FocusProbe` (`FOCUS_PROBE`), UI-тест — `Demo/TVUITests/FocusReachTests`
(`TEST_RUNNER_PROBES` задаёт свои экраны).
