# M01 — Контракт на примерах

Дата: 2026-09-12. Карточка [implementation-plan-5.md](../implementation-plan-5.md)
§5, первая карточка плана 5. Зависимость: T01 (план 4, принят — текстовый
контент существует, на нём проверяются примеры §1). Код не пишется этой

## 1. Внешний API sketch по сценариям §1

Все пять обязательных форм записи (раскрытие list, отдельный цвет, вложенный
`.none`, два независимых scopes, повторное нажатие) сведены в один пример —
карточка списка с текстом, — а не в пять несвязанных фрагментов, потому что
именно их взаимодействие в одном коммите и проверяет достаточность D62/D63.

```swift
final class FeedCardNode: Node {
    let description: TextNode
    private var expanded = false

    func onTap() {
        expanded.toggle()
        // Один animate на действие: список — общий предок карточки и
        // соседей, которых сдвигает раскрытие (§1). card.animate(...) здесь
        // был бы неверен — соседи оказались бы вне области и snap'нулись
        // (см. D63 «Сосед сдвинулся за пределами области» и §4 ниже).
        list.animate(.smooth) {
            description.maxLines = expanded ? nil : 2
            style.height = expanded ? expandedHeight : collapsedHeight
        }
    }

    // Отдельное, не связанное с раскрытием действие на той же карточке —
    // независимый scope, свой timing, может случиться в том же commit, что
    // и onTap() другой карточки (D63 «Два непересекающихся animate»).
    func onDownloadComplete() {
        self.animate(.easeOut(duration: .milliseconds(180))) {
            badge.appearance.visual.opacity = 1
        }
    }
}
```

Вложенный `.none` — внутри уже открытой области `list`, часть перехода
должна произойти без анимации (например: счётчик "непрочитано" обновляется
сразу, пока сама карточка плавно расширяется):

```swift
list.animate(.smooth) {
    description.maxLines = expanded ? nil : 2
    style.height = expanded ? expandedHeight : collapsedHeight

    card.animate(.none) {
        unreadBadge.appearance.visual.opacity = expanded ? 0 : 1
    }

    // Это обычная (не обёрнутая) запись, сделанная ПОСЛЕ вложенного вызова,
    // но всё ещё внутри card — по D63 «включая последующие обычные записи
    // внешнего closure» она тоже snap'ается, а не подхватывает .smooth
    // внешнего list. Не самое интуитивное правило — явно
    // проверено ниже в §3, не только продекларировано.
    card.appearance.visual.borderColor = expanded ? .clear : .separator
}
```

Повторное нажатие в середине движения — тот же `onTap()`, вызванный снова до
завершения предыдущего перехода: `expanded` уже true, второй вызов делает
`.animate(.smooth) { style.height = collapsedHeight }`. Новый intent для
scope `list` получает больший `sequence` и побеждает предыдущий по D63; сам
переход по D66 стартует не с нуля, а с текущего **presentation**-значения
высоты — новая цель без скачка. Это единственное место, где сценарий §1
("Повторное нажатие в середине движения меняет цель без скачка") напрямую
проверяет D66, а не только D62/D63.

**"Не более одного `animate` на действие"** — авторская дисциплина, не
проверяется рантаймом. Множественные вызовы в одном обработчике не
запрещены и не небезопасны — они полностью определены D63 (каждый получает
свой `sequence`, побеждает больший на пересечении). Правило существует,
чтобы автору обычно не приходилось рассуждать о порядке `sequence` вообще:
один вызов на действие — предсказуемое поведение без вычитывания таблицы
смешения. Диагностика (например, lint на повторный `animate` в одном
синхронном пути) — не в этой карточке; не требуется существующим примерам.

## 2. Таблица scope/sequence: reparent, same-target, no-op, suspended

Расширяет таблицу D63 четырьмя ситуациями, которые сценарии §1 не
называют явно, но которые здесь неизбежно возникают (переставляемый список,
повторный коммит без реального изменения, вызов на ноде без host).

| Ситуация | Результат | Источник правила |
|---|---|---|
| Reparent — нода сменила родителя между коммитами (не просто переместилась layout'ом внутри прежнего) | Snap, даже если нода внутри активной `animate`-области; локальные координаты не переносятся через две системы | D62: «Перенос между родителями в первой версии — snap» |
| Same-target repeat — коммит с тем же итоговым значением, что уже активный target перехода (например: несвязанный dirty-флаг вызвал пересчёт без реального изменения этого свойства) | Активный переход не перезапускается и не прерывается; продолжает идти к прежнему target | D64: «Повторный commit с тем же target не перезапускает и не обрывает действующий переход» |
| No-op call — `node.animate(...) { }` вызван, но closure не тронул ни одного visual/layout/arrangement-значения в области (или все присвоения равны текущим) | Intent-запись не создаётся вовсе; как будто `animate` не вызывался | D62: «Она сохраняется только если closure вызвал релевантную ... инвалидацию»; «No-op и чистые semantic-изменения не создают работы/намерения» |
| Suspended call — `node.animate(...) { ... }` вызван, пока host в `suspend()` (или до первого `attach`, см. §3.1) | Мутации модели внутри closure применяются (состояние накапливается), но animation-intent не сохраняется; первый commit после `resume()`/первого `attach` — snap к накопленному состоянию | D67: «Изменения во время suspend накапливают состояние, но анимацию не сохраняют; первый resume commit — snap» |

No-op и same-target-repeat выглядят похоже («ничего видимого не
произошло»), но они разные: no-op — это отсутствие intent с самого начала
(closure ничего не тронул); same-target-repeat — это intent, который БЫЛ бы
создан (что-то дирти), но окончательное значение совпадает с уже
преследуемым target, поэтому существующий активный CA-переход не трогают.
Спутать их в реализации означало бы либо лишний перезапуск анимации на
каждый несвязанный re-commit (если считать same-target как обычный новый
intent), либо пропуск обновления на реальном, но неизменном-по-значению
target'е соседней области (если считать their-target-check глобальным, а не
per-property). Обе ветки должны быть отдельными путями в M03/M04, не одним
условием «значение не изменилось».

### 2.1. Пробел, не покрытый D61–D69: `.animate` до первого `attach`

D67 описывает `suspend`/`resume` только для уже подключённого к хосту
дерева. Дерево `Node` может существовать и мутироваться до какого-либо
`attach` (обычная практика конструирования сцены). `.animate` на ещё не
подключённой ноде технически может создать intent-запись у корня (D62:
«Корень хранит записи... вместе с pending work» — «корень» это корень
дерева `Node`, не обязательно подключённый), которая, будучи чисто
umounted, никогда не участвовала бы ни в каком commit до `attach`. Не
описано явно: доживает ли такая запись до первого `attach` (и тогда первый
commit после attach должен бы её анимировать) или отбрасывается как
suspended.

**Предложение (принимается этой карточкой, см. §5):** до первого `attach`
дерево трактуется как перманентно suspended для целей D67 — тем же путём,
что и «suspend после attach»: мутации накапливаются, intent не сохраняется,
первый commit после attach — snap. Это не новое поведение, а явное
распространение уже принятого правила D67 на состояние «ещё не было ни
одного attach», которое иначе осталось бы неопределённым. Не требует нового
кода в reализации — bridge уже не существует до `attach`, поэтому
intent-запись у некорневого дерева физически некому подхватить; уточнение
фиксирует это как контракт, а не как случайность реализации.

## 3. D65 против T02/T07 — согласовано, стоимость записана

Прочитан [t07-text-raster-layer.md](t07-text-raster-layer.md) (реализация)
и [t02-raster-prototype.md](t02-raster-prototype.md) (числа памяти). Три
утверждения D65 сверены с фактическим кодом `LayerRenderer`
(`Sources/TrellisRender/LayerRenderer.swift`), не только с текстом решения:

- «Внешний слой — единственный носитель NodeID/hit-test/AX/sibling order» —
  подтверждено: `rasterLayers: [NodeID: CALayer]` — отдельная таблица от
  `LayerRegistry`; растровый слой не имеет собственной identity там (T07 §1).
- «Растровый слой не попадает в сортировку node-sublayers и не перекрывает
  overlay» — подтверждено структурно: растровый layer создаётся как sublayer
  внешнего слоя ноды (`materializeRasterLayer`), а не как отдельный элемент
  `LayerRegistry`'s собственного дерева сортировки.
- «При resize старый bitmap сохраняется в своём размере... новый подменяется
  без crossfade» / «при смене текста/стиля/locale — немедленная очистка» —
  подтверждено найденным и исправленным во время T07 пробелом (первая
  версия карточки не различала эти два случая; см.
  [t07-text-raster-layer.md §2](t07-text-raster-layer.md)) — контракт уже
  проверен реальным кодом, не только описан.

**Стоимость дополнительного raster layer при анимации.** Explicit
`CABasicAnimation` на внешнем слое (position/bounds/opacity/transform)
интерполируется Core Animation на GPU, без обращения к Trellis на каждый
кадр (§2 плана). Растровый sublayer при этом **не** перерисовывается на
каждый кадр — по D65 перенос строк (и, значит, новый raster job) происходит
**один раз**, по целевой ширине, а не по промежуточным значениям bounds,
которые проходит анимация. Значит: маржинальная стоимость одной анимируемой
текстовой карточки сверх обычной (неанимируемой) — это (а) одна
`CABasicAnimation` на внешнем слое на анимируемое свойство, без нового
solve/raster; и (б) не более одного дополнительного raster job на переход
(если ширина content area меняется достаточно, чтобы измениться raster key)
— тот же bitmap, что и при обычном (неанимируемом) resize, не удвоенный.
Точные числа (создание `CAAnimation`, время до появления нового bitmap,
память активных intent-записей) измеряются M02 ([implementation-plan-5.md](../implementation-plan-5.md)
§5 M02) и сравниваются с бюджетом T02 — не эта карточка (M01 фиксирует
контракт и то, что он не противоречит уже написанному коду T02/T07, не
измеряет).

## 4. Эскиз M10 — до реализации основы

Цель проверки: подтверждают ли слои/ключи/lifecycle D61–D69 карточку →
страницу и ручной progress жеста результата B **без второго renderer**, до
того как их реализация зафиксирована в M02–M08.

Composite transition (M10) нуждается в: (а) временном overlay-слое, который
интерполирует между геометрией card и геометрией page; (б) общем progress,
которым управляет жест (не автоматическим таймингом Core Animation); (в)
отмене жеста без рывка.

- **(а) Overlay — тот же renderer, не второй.** D65 уже устанавливает
  прецедент «два слоя одной ноды в одном renderer, не вторая нода и не
  второй рендерер» для текста. Overlay перехода — структурно то же самое на
  уровень выше: ещё один `CALayer`, управляемый тем же `LayerRenderer`,
  анимируемый тем же адресным explicit-animation путём D66
  (position/bounds/opacity/transform — та же таблица D61, новых свойств не
  требуется для простого case "весь card как источник", §1). Это не
  проверено кодом (M10 не начат), но не требует нового примитива сверх
  того, что D61/D66 уже определяют — таблица свойств результата A
  оказывается достаточной и для простого перехода результата B.
- **(б) Ручной progress без display-link.** Стандартный приём Core
  Animation — `CAAnimation.speed = 0` + `timeOffset`, управляемый напрямую
  из значений жеста (`UIPanGestureRecognizer`/`NSPanGestureRecognizer`),
  без пересчёта Trellis на каждое событие — именно то, что требует §2
  («во время жеста renderer применяет progress от входных событий к
  подготовленному переходу, без solve/raster на каждое событие»). Это тот
  же explicit `CABasicAnimation`, что и D66, просто с `speed = 0` вместо
  автоматического проигрывания — retarget/token-механизм D66 (адресное
  создание/замена/удаление по `(mountEpoch, NodeID, property)`) не
  предполагает автоматического старта и совместим с ручным `timeOffset`
  без изменений контракта.
- **(в) Отмена без рывка.** D66's «новая цель начинается от видимого
  значения» (presentation, не от model) — тот же механизм, который уже
  требуется для retarget результата A (повторное нажатие §1), покрывает и
  «отпустил жест, не дотянув» (target возвращается к исходному card rect от
  текущего progress-значения, не с начала).

**Вывод M01 по эскизу M10:** ни один из трёх пунктов не требует нового
класса примитивов сверх D61/D65/D66 — overlay, ручной progress и отмена
жеста выражаются тем же (слой, адресный token, explicit animation от
presentation) механизмом, что и результат A. Это не полная проверка (M10
не реализован, GPU-поведение `timeOffset` с явным from/to не измерено на
реальном устройстве) — это довод «не видно причины откладывать M02 ради
другого фундамента», а не гарантия, что M10 не найдёт собственных пробелов
при реализации.

## 5. Итог — статус D61–D69

Разбор примеров §1/§3 не нашёл неоднозначной области или неразрешённого
правила смешения в D61–D69 как написаны — единственный пробел (§2.1,
поведение `.animate` до первого `attach`) закрыт явным распространением уже
принятого правила D67, не новой веткой поведения. D61–D69 принимаются этой
карточкой; [decisions.md](../decisions.md) дополнен записью «D61–D69
(принято M01)», параллельной существующим блокам D16–D34/D35–D48/D49–D60.
