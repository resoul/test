### 1.1. Находка: правка одной строки в списке стоит полного solve

`single-row-edit-to-artifact` (`text-list-1000`) — правка текста **одной**
строки из 1000 стоит **~99 ms p50** (Release) до нового artifact: `TextNode.
document` меняется → `markGeometryDirty(structural: false)` → полный flush
всего дерева (flexbox не может определить, что изменение intrinsic-размера
одного ребёнка не сдвинет соседей, не решив это заново, D09 — это
архитектурное свойство flexbox-солвера, не баг этой карточки и не то, что
T11 должна чинить). Число само по себе не превышает никакого явного бюджета
(T02 бюджета для этого сценария не ставил), но это первое измерение именно
этого сценария — стоит знать: список с частыми точечными правками текста
(живые данные, тикер) на 1000 строк платит цену полного relayout за каждую
правку. Если это станет реальной проблемой продукта — кандидат на будущую
карточку (виртуализация списка на стороне хоста, а не на стороне Trellis).
Открыто в defects.md не заведено — это ожидаемое свойство архитектуры,
задокументированное здесь как число, не как дефект.

### 1.2. Память растров — линейна по площади, не по числу узлов сверх площади

`text-list-1000`: `estimated-raster-bytes-rgba` = 102 400 000 байт (1000 строк
× 640×40px × 4 байта RGBA — то есть по полной ширине колонки, не по
фактической ширине текста: raster-слой растягивается на всю ширину строки,
D65). Резидентная память процесса: `resident-before` 13.97 MiB →
`resident-after-drain` 58.52 MiB, дельта ≈ 44.5 MiB — меньше расчётных ~97.7
MiB (RGBA-оценка) той же оговоркой из T02 §3.1 (незакрашенные области —
zero-page до первой записи; RSS — не точный байт-в-байт учёт). Раздел 3
(`t11_rasterByteCountScalesWithCommittedPixelAreaNotWithAFixedPerNodeOverhead`)
проверяет пропорциональность строго: колонка вдвое шире даёт ровно вдвое
больше `pixelWidth` и вдвое больше байт для одной и той же короткой строки —
никакого фиксированного оверхеда на узел, не зависящего от площади.

### 1.3. Коалессинг под нагрузкой — подтверждён числами

`text-burst-edits`: 200 строк × 3 правки за один синхронный tick, 5 измеренных
проходов → `raw-edits` (сырых присваиваний `text`) 3000, `display-scheduled`/
`display-completed` 1200 (200 начальных + 5 × 200) — то есть на **каждую**
измеренную пачку из 3000/5=600 правок пришлось ровно 1000 запланированных
растров (по одному на строку на проход, не по одному на правку) — коалессинг
(D53) держится и на 200 узлах одновременно, не только на одном (как в
`t06_colorOnlyChangeStillSchedulesANewDisplayPassWithoutANewLayoutSnapshot`).

## 2. Инварианты — проверены тестами, не только числами

`Scripts/bench.py`: «измерения — свидетельства, не гейт»; счётчики, которые
обязаны быть точными, проверяются `TrellisRenderTests` — тот же принцип
`HostRenderStatisticsTests` уже применяет к T04–T06. Новый файл
`Tests/TrellisRenderTests/TextLoadTests.swift` (4 теста):

- `t11_oneThousandTextNodesAreEachMeasuredExactlyOnceForOneFlush` —
  `CountingTextRenderer` (обёртка над реальным `CoreTextRenderer`, считает
  вызовы `measure` под `NSLock` — солвер вызывает измеритель с выделенного
  `Thread`, не с MainActor) вокруг плоской колонки из 1000 `TextNode` без
  `flexGrow`/`flexShrink`: ровно 1000 вызовов на первый коммит (по одному на
  уникальную пару `(node, constraint)` — приёмка «измерений на уникальный
  constraint == 1»), и ноль дополнительных на повторный `updateBounds` с теми
  же значениями (совпадающая работа, coalesced).
- `t11_afterDrainEveryVisibleTextNodeHasACurrentArtifact` — 1000 узлов, после
  полного дренажа у каждого `displayArtifact(for:) != nil`,
  `displayStatistics.completed == 1000`, `cancelled == 0`.
- `t11_deepChainWithATextLeafCommitsWithoutStackOverflow` — см. §3 ниже
  (дефект #45).
- `t11_rasterByteCountScalesWithCommittedPixelAreaNotWithAFixedPerNodeOverhead` —
  §1.2 выше, как точный тест, а не наблюдение.

Полный пакет: **597/597** (macOS, `swift test`, было 593 после T10, +4 новых
теста). iOS/tvOS Simulator — см. §4.

## 3. Найдено и не в бюджете этой карточки (дефект #45, defects.md)

Приёмка требует «deep tree с текстом без рекурсии в измерителе». Дефект #22
(defects.md) уже установил границу для рекурсии **солвера** — «3000 уровней
ок, 6000 — падение» — и именно поэтому солвер работает на отдельном `Thread`
с 16 MiB стека (`LayoutScheduler`). Но `RenderCoordinator.flush()` строит
входной снимок (`Node.makeLayoutInputSnapshot`) и применяет результат
(`Node.applyLayoutResult`) синхронно **на обычном MainActor-потоке**, с
обычным (не увеличенным) стеком — обе рекурсивны по глубине дерева, как и
`LayerRenderer.update`.

Проверено пробой: цепочка из 2000 уровней с `TextNode`-листом на конце,
смонтированная через настоящий `NodeHostBridge`, уронила процесс теста
(SIGSEGV) — не таймаут, не `#expect`-провал, а падение процесса. Второй проб
**без единого `TextNode`** (обычные `Node`) уронил процесс тем же образом на
той же машине — бисекция дала границу между 1500 (проходит) и 1600 (падает).
Это доказывает: находка не специфична для текста или его измерителя — это
общее свойство нескольких MainActor-side обходов дерева, не покрытых фиксом
#22. Файл `Tests/TrellisRenderTests/TextLoadTests.swift`,
`t11_deepChainWithATextLeafCommitsWithoutStackOverflow`, использует глубину
800 (запас вдвое от найденной границы) — проверяет ровно то, что действительно
относится к T11 (текстовый лист не добавляет **свою** рекурсию поверх общей),
не переоткрывая саму границу.

Починка (сделать эти обходы итеративными или перенести на поток с увеличенным
стеком) — заметно больше по объёму, чем позволяет карточка «Нагрузка», и
затрагивает код за пределами текста (`HitTestSnapshot`, `SemanticSnapshot`,
`AccessibilityTree.build`, вероятно, той же формы). Зафиксировано как
**открытый** дефект #45 в defects.md — следующая карточка/сессия, которая
захочет реально держать глубокие деревья (не только текстовые), должна
начинать оттуда.

## 4. Сравнение с бюджетом T02 и §3.2 — новый кэш растров не добавлен

T02 §3.1 дал числа для 1000 строк **вне** production pipeline (голый CoreText,
без `NodeHostBridge`/`DisplayScheduler`/слоёв) с явной оговоркой «не финальный
бюджет T11». Здесь то же самое число измерено **внутри** реального pipeline
(`text-list-1000`, drain 1000 artifacts — 47.4 ms Release) — того же порядка,
что T02's «растеризация 1000 строк» (~73 ms Debug-oriented замер T02, другая
метрика: T02 мерил только сам вызов CoreText 20 раз подряд в цикле, не полный
production drain с солвером и раскладкой по layer'ам). Дополнительный
внутренний raster layer (T07) и `DisplayScheduler`'s bookkeeping не вносят
на два порядка большую стоимость — то же порядка величины, что и голый CoreText.

§3.2 плана допускает добавить кэш **прошлых** растров (не только текущего
закоммиченного — T06/T10 уже держат ровно один текущий на узел, `committedTable`),
но требует не менять политику атомарной замены/no-crossfade молча и обосновывать
добавление числами. Числа здесь не показывают такой необходимости: ни один
сценарий (список, абзац, burst, resize) не переиспользует старый bitmap
одного и того же узла после его замены (D65 уже гарантирует «старый bitmap
живёт только до следующего», не «может понадобиться повторно» — сценарий
переиспользования появился бы только у прокручиваемого списка с recycled
node identity, которого Trellis не делает: узлы стабильны по `NodeID`, T10
уже чистит `DisplayScheduler` при реальном удалении узла). **Решение: кэш
прошлых растров не добавлен** — политика §3.2 (атомарная замена без
crossfade, один текущий artifact на узел) остаётся как есть, эта карточка не
нашла числового обоснования для большего.
