# C21 — Завершить контракт Arrangement до кодирования resolver

Дата: 2026-09-10. Это карточка контракта, не кода: `Arrangement`/`Leaf`/`Row`/
`Column`/`Overlay` и resolver ещё не существуют (C22/C23). Ничего не
собирается и не тестируется этой карточкой — приёмка состоит в том, что
каждый перечисленный в плане случай имеет однозначный ожидаемый результат,
проверенный на двух примерах ниже. D05/D06 переводятся из предложений в
принятые решения; D03/D04 подтверждаются без изменений.

## Пример A — статическая карточка

```swift
final class ProfileCard: Node {
    let avatar = Node()
    let title = Node()
    let subtitle = Node()

    override func arrangeSubnodes() -> (any Arrangement)? {
        Row(spacing: 12, align: .center, padding: .all(16)) {
            Leaf(avatar).size(width: 48, height: 48)
            Column(spacing: 4) {
                Leaf(title)
                Leaf(subtitle)
            }
            .grow(1)
        }
    }
}
```

Resolve:

- Корневой `Row` описывает **self** (`ProfileCard`): effective style для
  snapshot = база `ProfileCard.style` (D04) с наложенными `flexDirection: .row`,
  `gap: 12`, `alignItems: .center`, `padding: .all(16)`. Лишней ноды на месте
  корневого контейнера не создаётся.
- Управляемый список детей `ProfileCard` становится `[avatar, wrapper#1]`.
  `avatar` — это Leaf: существующая нода переиспользуется, ей не
  присваивается новый `NodeID`; наложенный `.size(48, 48)` действует только на
  effective-копию, `avatar.style` (база) не трогается.
- `wrapper#1` — implicit-нода для `Column`, идентифицируемая ключом
  `(ProfileCard.id, path: [1], kind: .column)` (D06). Её effective style —
  `flexDirection: .column`, `gap: 4`, плюс `.grow(1)` от модификатора снаружи.
  Управляемые дети `wrapper#1` — `[title, subtitle]`, оба Leaf, оба
  переиспользованы без нового ID.

## Пример B — удаление части содержимого

Продолжение той же карточки: автор скрывает подзаголовок условием builder'а и
переносит `.grow(1)` прямо на `title`, когда подзаголовка нет — не только
удаляя Leaf, но и **меняя тип** второго слота с контейнера на голый Leaf:

```swift
override func arrangeSubnodes() -> (any Arrangement)? {
    Row(spacing: 12, align: .center, padding: .all(16)) {
        Leaf(avatar).size(width: 48, height: 48)
        if subtitle.hasText {
            Column(spacing: 4) {
                Leaf(title)
                Leaf(subtitle)
            }
            .grow(1)
        } else {
            Leaf(title).grow(1)
        }
    }
}
```

Resolve после того, как `subtitle.hasText` стало `false`:

- Корневой `Row` по-прежнему описывает self; его effective style не меняется.
- Слот `path: [0]` (`avatar`) не меняет ни путь, ни kind (`.leaf`) — Leaf
  переиспользуется, effective style пересчитывается заново из
  `avatar.style` (в этом примере не меняется).
- Слот `path: [1]` меняет kind с `.column` на `.leaf`. Ключ D06 включает
  `kind`, поэтому это **не** тот же wrapper с новым содержимым — это конец
  жизни `wrapper#1` и появление нового слота:
  - `wrapper#1` удаляется из управляемого списка `ProfileCard` и
    **disposed** — сам wrapper resolver-owned (D05), его исчезновение не
    несёт ответственности за живые пользовательские Leaf внутри.
  - `subtitle` **не** dispose'ится вместе с wrapper: он лишь отсоединяется
    (`removeFromSupernode`), становится обычной ничьей (`supernode == nil`)
    нодой, пока новый proposal больше нигде на него не ссылается. Пользователь
    продолжает владеть `subtitle` через своё поле — она жива, просто вне
    дерева.
  - `title` реиспользуется напрямую как управляемый ребёнок `ProfileCard` на
    `path: [1]`, теперь с kind `.leaf`. Его effective style пересчитывается
    заново из `title.style` (базы) и получает только `.grow(1)` — старые
    `alignItems`/`gap` бывшего `wrapper#1` **не** просачиваются, потому что
    effective style Column'а принадлежал wrapper'у, а не `title` (D04).
- Если `subtitle.hasText` снова станет `true`: ключ `(ProfileCard.id, [1],
  .column)` не «оживляет» disposed `wrapper#1` — создаётся новая implicit-нода
  с тем же ключом. `title` и `subtitle` (обе никогда не disposed) переиспользуются
  под ней без нового `NodeID`.

Это подтверждает D03 (сигнатура `arrangeSubnodes()` не менялась, констрейнт не
появился), D04 (effective style всегда пересчитывается из базы, снятие/замена
модификатора не оставляет следов), D05 (только wrapper disposed вместе с
удалением слота; пользовательский Leaf — никогда) и D06 (ключ `(ownerID,
structuralPath, kind)`; смена kind на одном пути — это смена идентичности
wrapper'а, не апдейт на месте).

## Корневые формы Arrangement

| Возврат `arrangeSubnodes()` | Что описывает | Управляемый список self |
|---|---|---|
| `nil` | Ничего — ручной режим | Тот, что оставили `addSubnode`/`insertSubnode`/… |
| `Leaf(x)` | Ничего на self (Leaf не пишет self.style) | Ровно `[x]` |
| `Row`/`Column`/`Overlay { … }` | self: effective style self из конфигурации контейнера + база (D04) | Плоский список items контейнера (Leaf → сама нода, вложенный контейнер → implicit wrapper, D06) |
| `Row`/`Column`/`Overlay {}` (пусто) | self, как непустой контейнер той же формы | `[]` — прежние managed-дети (Leaf/wrapper) снимаются по тем же правилам, что и в Примере B |

Пустой контейнер — не то же самое, что `nil`: он остаётся под управлением
resolver'а (ручная мутация списка всё ещё диагностируется, D05), просто
временно без детей. `nil` полностью возвращает узел в ручной режим и
отсоединяет managed-связи и wrappers без dispose пользовательских Leaf — по
той же процедуре, что снятие одного слота в Примере B, только сразу для
всего списка.

Рекомендация по root Leaf: годится, когда автор осознанно хочет ровно одного
управляемого ребёнка без стилизации self (например, ветвление, которое
выбирает один из нескольких предсуществующих под-деревьев); Row/Column из
одного элемента для типичного случая читается яснее и рекомендуется по
умолчанию.

## Overlay

Overlay не вводит новую модель размещения — она ложится на уже
реализованную (`FlexboxMeasure.swift`/`FlexboxPlacement.swift`) поддержку
`LayoutStyle.positionType == .absolute`:

- **Размер self** (владельца Overlay) приходит из его собственного стиля/
  модификаторов ровно как у Row/Column — явные `width`/`height`, `.grow`,
  `padding`. Overlay **не** выводит свой размер из детей молча: это
  соответствует D03 (никакого responsive-ветвления по измеренному размеру в
  этапе 1).
- **Все дети Overlay участвуют в измерении.** Каждый получает
  `positionType = .absolute` на effective style и измеряется с
  `.atMost(innerContentBox)` — тем же путём, что и сегодняшние absolute-дети
  flex-контейнера (`FlexboxPlacement.swift:182-191`). `.size()` модификатор
  задаёт явные `width`/`height`; без него используется intrinsic content
  measurement — никогда не `0×0` по умолчанию.
- **Размещение по умолчанию — content-box origin** (top-leading внутренней
  области после padding), а не произвольный `0×0` относительно окна: это
  именно то значение, на которое уже сегодня падает `offsets.left`/`.top`,
  если они не заданы (`FlexboxPlacement.swift:154-161, 193-200`).
  Модификатор `.offset(...)` пишет `LayoutStyle.offsets` (логические,
  разрешаются по layout direction) и сдвигает от той же точки отсчёта.
- Ни один ребёнок Overlay не считается «главным» для размера self; порядок
  элементов builder'а задаёт z-order, явный оверрайд — через существующий
  `LayoutVisualProperties` z-index (вне обязательного скоупа C21).

Следствие: C22/C23 не обязаны писать новую математику размещения для
Overlay — им нужно только lowering `Overlay { … }` в контейнер с
`positionType = .absolute` детьми, что уже умеет `FlexboxEngine`.

## Некорректные предложения

Все проверки — на **proposal** (полностью развёрнутое дерево Leaf/wrapper
слотов, прежде чем `arrangeSubnodes()`'а результат тронул живое дерево, ровно
как того требует C23: «сначала построить и проверить proposal, затем менять
живое дерево»). Нарушение любого пункта отклоняет **весь** proposal одним
`Log.on(.tree, "arrangement-rejected", …)` и не мутирует дерево частично —
предыдущее resolved-состояние (или ручной режим, если resolve ещё не
запускался) остаётся как было.

| Случай | Результат |
|---|---|
| Duplicate Leaf — одна и та же `Node` названа дважды в одном proposal (в том числе в разных вложенных контейнерах) | Весь proposal отклонён |
| `Leaf(self)` — owner называет сам себя | Отклонён как cycle |
| Leaf называет текущего предка `self` (единственный реалистичный cycle в этапе 1, поскольку cross-owner ссылки идут только через Leaf) | Отклонён как cycle |
| Leaf называет ноду с живым `supernode`, который не является `self` и не освобождается этим же proposal («чужое смонтированное дерево») | Отклонён — Leaf никогда не крадёт смонтированную ноду молча, независимо от того, управляет ли текущим родителем resolver или ручной код; вызывающий должен сперва вызвать `removeFromSupernode()` |
| Leaf называет ноду, которая уже входит в **текущий** managed-список этого же owner (переиспользование с прошлого resolve) | Не «чужая» — это обычный путь обновления (D05/D06), принимается |

## Порядок recursive resolve

- Один flush может затрагивать несколько dirty owners; сам механизм, который
  помечает owner dirty (`.arrangement` из `DirtyReasons`) и планирует
  resolve, остаётся задачей C23 — C21 фиксирует только порядок, а не триггер.
- Owners резолвятся **сверху вниз**: owner подготавливается (его
  `arrangeSubnodes()` вызывается, proposal валидируется и применяется)
  строго раньше, чем резолвится любой owner, ставший достижимым только в
  результате этого resolve — например, вложенный `arrangeSubnodes()` ноды,
  усыновлённой через Leaf. Это естественный порядок вызовов: ребёнок не
  может быть «владением» arrangement родителя раньше, чем resolve родителя
  его применил.
- Внутри одного прохода `arrangeSubnodes()` каждой живой ноды вызывается **не
  более одного раза** — resolve родителя может оставить потомка чистым, и
  тогда отдельный resolve для него в этом же проходе не запускается; если
  потомок остаётся dirty (или стал новым усыновлением) после применения
  своего нового родителя, он резолвится следом, но всё ещё один раз.
- Нода, disposed в середине прохода (например, resolve предка отсоединил и
  сторонний код тут же вызвал `dispose()` на отсоединённом поддереве),
  пропускается для оставшейся части этого прохода, а не резолвится.

## Не входит в эту карточку

Реализация `Leaf`/`Row`/`Column`/`Overlay`, builder, `open arrangeSubnodes()`
на `Node`, и сам resolver — это C22/C23. Триггер, которым структурная/стилевая
мутация помечает owner `.arrangement`-грязным и планирует flush, тоже C23:
здесь фиксируется только то, что происходит **после** того, как resolve уже
решили запустить.
