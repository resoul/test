# Компоненты: Control, поля ввода, клавиатура, rich text

**Статус: направление согласовано, 2026-09-28.** Ответы по восьми вопросам и основания
выбора зафиксированы в разделе «Решение для истории». Сделаны прототип C2–C4, C0
(`Control`, подсказки), C1 (`Checkbox`, `Switch`) и C2 (`HostedView`); остальные компоненты ещё не
реализованы.
Примеры API и технические детали ниже остаются проектом; их уточняем по прототипу
и проверкам, не меняя согласованных требований.

## Зачем

Сейчас в `NodesRender` есть `Text` (строка одного стиля), `Button`, `Image`, `Table`,
`RefreshSpinner`. Пользователь просит: общий `Control`, от которого пойдут остальные;
`TextField`, `EmailField`; отличную работу с клавиатурой; rich text «как в Telegram»;
`Checkbox`, `Switch`, `Select` (выпадающее меню), `Toast`; ранее — `Tooltip`.

Источники идей: старый проект Weave (`ControlNode`, `ButtonNode`, `TextFieldNode` через мост
к `UITextField`), Telegram iOS (`docs/richtext-composer.md`, `RichTextEditor`, `Display`
— клавиатура, `SwitchNode`, `CheckNode`, `UndoUI`, `TooltipUI`).

## Что взято из Telegram и что нет

- **Модель содержимого — значение, а не `NSAttributedString`.** В Telegram `ChatInputContent`
  — дерево блоков и отрезков текста (`paragraph`/`quote`/`code`/…, отрезки bold/italic/mono/
  strike/underline/spoiler + ссылка/упоминание/эмодзи), с которым работают отправка,
  черновики, правка. Мы делаем так же: `RichText` — `Sendable`-значение в модуле без UIKit,
  проверяемое `swift test` на Linux. `NSAttributedString` — только на границе адаптера.
- **Ядро редактора без UIKit**, TextKit — за протоколом (у них `BlockLayoutEngine`: TextKit 2
  на iOS 16+, TextKit 1 ниже). У нас минимум iOS 16 — только TextKit 2 (`NSTextLayoutManager`).
- **Меню «Формат»** в системном меню правки (`UIEditMenuInteraction`, iOS 16+): Bold, Italic,
  Monospace, Link, Strikethrough, Underline, Quote, Spoiler.
- **Родитель задаёт размер и отступы**, поле возвращает высоту (`update(size:insets:) ->
  height`) — у нас это и так: нода измеряется раскладкой.
- **Клавиатура — на уровне окна**, высота клавиатуры приходит вниз как часть условий показа
  (`inputHeight`) с кривой анимации клавиатуры. У нас — через `NodeHost` (ниже).
- **Не берём:** собственную подмену вида клавиатуры и перетаскивание системной клавиатуры
  через приватные виды (`KeyboardManager`, `WindowPanRecognizer`) — это частные API и
  хрупкость между версиями iOS. Своя клавиатура-панель (эмодзи) — через публичный
  `inputView`, как у них для редактора.

## Control

Общий класс для нод, с которыми взаимодействуют. Сейчас это делает `Button` вручную
(`onTap`, `pressChanged`, `focusChanged`).

```swift
open class Control: Node {
    var isEnabled: Bool            // выключенный: не фокусируется, не нажимается, тусклее
    private(set) var state: ControlState   // [.pressed, .focused, .hovered, .disabled, .selected]
    open func stateChanged(from: ControlState)   // подкласс перерисовывает
    var toolTip: String?           // подсказка (Mac, iPad с курсором)
    var command: Command?          // нажатие = команда; включённость и подсказка — от неё
}
```

- Состояние — множество флагов, а не одна фаза (Weave: `idle/pressed/focused/disabled`):
  нажатая кнопка может быть в фокусе.
- `hovered` — курсор Mac и iPad (`UIHoverGestureRecognizer`), новое для адаптеров.
- Доступность: признак, значение, подсказка — от подкласса (`accessibilityValue` у Switch —
  «вкл/выкл»); выключенный — `notEnabled`.
- Клавиатура: Space и Return нажимают контрол в фокусе (Mac, iPad), Select — на TV (есть).
- `Button` становится подклассом `Control`, его API не меняется.
- Значение: у контролов со значением (`Checkbox`, `Switch`, `Select`, поля) — свойство
  значения на `State` (наблюдаемо) и `onChange`; привязки «два пути» нет — приложение
  само пишет в свою модель в `onChange` (как сейчас `Table.onSelect`).

## Поля ввода

### Способ: системное поле внутри дерева или своё

| | Системное (`UITextField`/`UITextView`/`NSTextField`) | Своё (`UITextInput`/`NSTextInputClient` на ноде) |
|---|---|---|
| Ввод на всех языках (IME, marked text), диктовка, автокоррекция, подсказки клавиатуры | даром | реализовать самим (Telegram — тысячи строк) |
| Автозаполнение паролей и email (`textContentType`), «Вставить из»... | даром, проверено | частично; пароли надёжно только у `UITextField` |
| Лупа, ручки выделения, меню правки | даром | самим (у Telegram отдельные разделы с «инвариантами») |
| Вид по теме, раскладка, прокрутка вместе с деревом | мост: вид поверх ноды | естественно |
| TV (полноэкранная системная клавиатура) | даром | самим |
| Rich text | `UITextView` + атрибуты — «наследная» ветка Telegram | их новый движок |

**Решение.** `TextField`, `EmailField`, `SecureField`, `TextEditor` (многострочный) —
системные виды, которые нода держит и ставит в свою рамку («вложенный вид платформы»). Это
первый шаг, и он нужен в любом случае: так же потом вставляются карта, видео, веб-вид.
Rich text редактор — второй шаг, на `UITextView`/`NSTextView` с TextKit 2 и нашей моделью
`RichText` (атрибуты — только на границе). Свой движок ввода — только если упрёмся.

### Вложенный вид платформы (новое в Nodes и адаптерах)

```swift
final class HostedView: Node          // ядро не знает UIKit: держит непрозрачный ключ
// адаптер: NodeView кладёт UIView ноды своим subview в рамку ноды после раскладки,
// сдвигает при прокрутке, прячет при isShown == false, порядок — по порядку дерева
```

- Размер: нода спрашивает вид о желательном размере (`sizeThatFits`, `intrinsicContentSize`)
  — через обратный вызов адаптера, как текст меряется сейчас.
- Фокус: поле в фокусе — first responder; фокус дерева и клавиатурный фокус согласованы
  (Tab с Mac/iPad-клавиатуры ведёт по полям в порядке дерева; на TV — фокус движка).
- Команды: пока поле — first responder, его клавиши (⌘Z, ⌘A, стрелки) у него; команды
  приложения — через цепочку: вид поля → `NodeView` → экран.

### TextField

```swift
let name = TextField(placeholder: "Name")
name.text                 // State, наблюдаемо
name.onChange = { … }; name.onSubmit = { … }       // Return
name.returnKey = .next    // .next переводит фокус на следующее поле дерева
name.content = .name      // textContentType: имя, email, телефон, адрес, код из SMS …
name.clearButton = .whileEditing
name.maxLength = 64
```

**EmailField** — `TextField` с `content = .email`, клавиатурой email, без автокоррекции и
автоматических заглавных. Встроенная базовая проверка формата не подтверждает существование
адреса. Компонент показывает состояние проверки и `validationMessage`, приложение задаёт
или переопределяет правила. Момент проверки настраивается: ввод, потеря фокуса, отправка.
Нужны синхронные и асинхронные проверки; устаревший ответ не должен менять состояние нового
текста. Точный API и представление состояний «не проверено»/«проверяется»/«верно»/«ошибка»
уточняются в C3; одного `isValid` для всей модели недостаточно.

**SecureField** — пароль: `isSecureTextEntry`, `content = .password/.newPassword`
(предложение сильного пароля).

### Клавиатура

- **Высота клавиатуры — условие показа хоста.** Адаптер следит за
  `keyboardWillChangeFrame` (или `keyboardLayoutGuide`, iOS 15+), переводит кадр клавиатуры
  в координаты `NodeView` и отдаёт хосту `keyboardInset` вместе с длительностью и кривой.
  Раскладка перестраивается в `withAnimation` с кривой клавиатуры — поле ввода внизу экрана
  едет вместе с клавиатурой, как в Telegram. iPad с плавающей клавиатурой и Stage Manager —
  по пересечению кадра клавиатуры с окном, а не по высоте экрана (у Telegram этому посвящена
  половина обработчика).
- **Поле в фокусе остаётся видимым:** `Scroll` вокруг поля прокручивает его над клавиатурой
  (как `reveal` для фокуса сейчас), с отступом.
- **Скрытие клавиатуры:** касание вне полей по настройке экрана, скрытие при прокрутке,
  Escape на iPad. Интерактивное скрытие вместе с пальцем — требование. В текущем
  `Sources/NodesUIKit/NodeView.swift` уже есть `ScrollDriver` с `UIScrollView`: он даёт
  физику, его `panGestureRecognizer` перенесён на `NodeView`, содержимое рисуется слоями.
  Поэтому сначала проверяем `keyboardDismissMode = .interactive` вместе с вложенным полем
  в этой иерархии. Наличие `UIScrollView` не доказывает работоспособность такого сценария.
  Изменение иерархии видов и жестов решаем по прототипу C2–C4; приватные API не используем.
- **Панель над клавиатурой** (`inputAccessoryView`): кнопки «Готово», «Назад/Далее» по полям,
  форматирование — нодами (`NodeView` как accessory).
- **Своя клавиатура** (эмодзи, стикеры): `inputView` поля — `NodeView` с деревом; переключение
  системная ↔ своя без потери first responder (как у Telegram).
- Mac: клавиатуры на экране нет; Tab/Shift-Tab — по полям, Return — `onSubmit`, Escape —
  отмена правки (`Command.cancel`).
- TV: поле в фокусе по Select открывает системный экран ввода; `EmailField` передаёт
  `content` — на TV это даёт подстановку email из настроек.

### Rich text

**Объём первой версии:** модель сразу блочная; показ и редактор поддерживают абзацы,
цитаты, блоки кода, жирный, курсив, моноширинный, зачёркнутый, подчёркнутый текст и ссылки.
Списки, спойлеры и упоминания — следующие расширения. Конвертеры и Markdown на лету ниже —
дальнейший объём, а не обязательное условие выпуска первого редактора.

**Эскиз расширяемой модели (`RichTextCore`, без UIKit, Linux):**

```swift
struct RichText: Sendable, Hashable, Codable {
    var blocks: [Block]              // .paragraph(runs) / .quote(runs) / .code(String, language)
                                     // / .list(ordered, items)
}
struct Run { var text: String; var marks: Marks; var link: URL?; var mention: Mention? }
struct Marks: OptionSet { bold, italic, mono, strike, underline, spoiler }
struct RichSelection { start, end: RichPosition }   // позиция: блок + смещение
```

- Правка — операциями над значением (`insert`, `delete`, `toggle(.bold, in:)`, `setLink`),
  тесты — на Linux. Отмена (`UndoManager` платформы) хранит значения.
- Конвертеры: Telegram-подобные сущности (`entities: [(range, type)]` над простым текстом),
  Markdown (`**bold**`, `_italic_`, `` `code` ``, `~~strike~~`, `||spoiler||`), HTML —
  для отправки на сервер, вставки, копирования.
- **Ввод Markdown на лету** (по настройке): набрали `**слово**` — стало жирным.
- **Отображение:** `Text` учится показывать `RichText` (сейчас — строка одного стиля): отрезки
  со стилями, ссылки нажимаются (`onLink`), спойлер скрыт до касания, упоминания.
- **Редактор (`TextEditor(rich:)`)**: `UITextView`/`NSTextView` на TextKit 2; модель ↔
  атрибуты через симметричный преобразователь (цвета темы применяются при показе и не
  попадают в модель — инвариант Telegram); меню «Формат» в меню правки; ⌘B/⌘I/⌘U — команды
  (`Command`), доступные и из строки меню Mac/iPad.

## Checkbox и Switch

- `Switch(isOn:)` — на iOS и Mac есть системные (`UISwitch`, `NSSwitch`), на TV — нет.
  `Checkbox` — на Mac системный (`NSButton` со стилем checkbox), на iOS — нет вовсе
  (у Telegram свой `CheckNode`).
- Решение: оба — свои ноды, рисуемые по теме (цвета, анимация «щелчка»), одинаковые
  на всех платформах; доступность — как у системных (признак переключателя, значение
  «вкл/выкл», действие). Системный стиль (`style: .platform`) — возможное последующее
  расширение, не обязательство первой версии.
- Состояние Checkbox: вкл/выкл/смешанное (для «выбрать всё»).

## Select (выпадающее меню)

```swift
let sort = Select(options: [.date, .sender, .subject], selection: .date) { $0.title }
```

- iOS/iPad: кнопка, открывающая системное меню (`UIButton.menu`, `showsMenuAsPrimaryAction`,
  галочка у выбранного) — родное поведение iOS 14+.
- Mac: `NSPopUpButton` (вложенный вид) или своё меню `NSMenu` из кнопки.
- TV: меню нет — список вариантов на весь экран (`Alert(style: .actions)` или экран-список).
- Много вариантов с поиском (страны) — отдельный компонент позже: экран-список в листе.

## Toast

Короткое сообщение поверх окна, само уходит: «Сообщение удалено — Отменить»
(Telegram `UndoOverlayController`).

```swift
shell.toast(Toast("Message deleted", action: ToastAction("Undo") { restore() }))
```

- Уровень окна (`SceneSession`), поверх листов; по умолчанию новый заменяет текущий,
  очередь включается настройкой. Одинаковые уведомления желательно объединять. Длительность: 4 с, с действием — дольше; касание или смахивание убирает;
  пока VoiceOver читает — не уходит.
- Доступность: объявление (`UIAccessibility.post(.announcement)`, `NSAccessibility`).
- Положение: снизу над панелью вкладок и клавиатурой (учитывает `keyboardInset`), на Mac —
  снизу окна, на TV — сверху справа, без перехвата фокуса. Действие на TV требует
  отдельного решения; глобальную кнопку пульта автоматически не занимаем. Важная ошибка
  должна оставаться доступной и после исчезновения уведомления.

## Tooltip

Было в плане раньше: `node.toolTip` (Mac — `NSView.addToolTip(rect:)` по рамкам нод, iPad —
`UIToolTipInteraction` с курсором, iPhone/TV — нет). Кнопки панели и пункты меню — из
заголовка команды. Входит в `Control` (`toolTip`), но работает у любой ноды.

## План

Сначала — ограниченный прототип C2–C4: одно системное поле внутри прокрутки, переход
фокуса, показ и интерактивное скрытие клавиатуры. Затем C0 → C1 → полноценные C2–C4 →
C5 → C6 → C7. Модель rich text проектируется заранее; реализация следует этапам.


| Этап | Что | Проверка |
|---|---|---|
| C0 | `Control` (состояние, выключенность, наведение, клавиши нажатия); `Button` на нём; `Tooltip` | модель на Linux; наведение и подсказка на Mac/iPad, UI-тесты |
| C1 | `Checkbox`, `Switch` (свои, по теме), доступность как у системных | модель; VoiceOver-признаки; TV-фокус |
| C2 | Вложенный вид платформы (`HostedView`) в Nodes и адаптерах | рамки при прокрутке, скрытие, порядок, фокус |
| C3 | `TextField`, `EmailField`, `SecureField`, `TextEditor`; Tab/Return по полям | ввод, автозаполнение email, проверка, TV-клавиатура |
| C4 | Клавиатура: `keyboardInset`, анимация по кривой, поле над клавиатурой, скрытие | UI-тесты iPhone/iPad, плавающая клавиатура |
| C5 | `Select`, `Toast` | меню iOS/Mac, список на TV, очередь тостов, объявление |
| C6 | Блочная модель `RichText` и её показ в `Text` в объёме первой версии | Linux-тесты операций и преобразований; ссылки, цитаты, код |
| C7 | Rich text редактор первой версии: системный ввод, меню «Формат», ⌘B/⌘I/⌘U | UI-тесты правки, IME, выделения и undo/redo; round-trip с моделью |

## Прототип C2–C4 (2026-09-28)

**Статус: сделан, проверен на iPhone 17 Simulator.** Ограниченный объём, как решено: одно
системное поле внутри прокрутки, переход по полям, показ и скрытие клавиатуры.

- `Nodes`: `EmbeddedNode` — нода, в рамке которой адаптер показывает вид платформы;
  `preferredSize` (адаптер ставит размер вида). `NodeHost.embeddedItems()` — рамки таких нод
  в координатах корня с учётом прокруток и обрезки (`shownFrame`, `nil` — не видно).
  `NodeHost.keyboardInset` / `Node.keyboardInset` — насколько клавиатура заходит снизу,
  наблюдаемо: раскладка экрана сама решает, что поднять (как `inputHeight` у Telegram).
  `NodeHost.reveal(_:)` стал публичным. `Scroll.keyboardDismissal`: `.none`, `.onDrag`,
  `.interactive`.
- `NodesRender`: `TextField` — текст (`State`, `onChange` только от пользователя), подсказка,
  `TextContent` (`.text`, `.name`, `.email`), `ReturnKey` (`.next` — следующее поле дерева,
  `.done` — убрать клавиатуру), `onSubmit`, `isEditing`, `beginEditing()`/`endEditing()`.
- `NodesUIKit`: `NodeView` ставит `UITextField` (`FieldView`) в рамку ноды после каждой
  отрисовки и сдвига прокрутки, поверх видов физики прокрутки; вне видимой части — обрезан
  до нуля, а не скрыт (скрытый вид выпадает из доступности). В порядке чтения доступности на
  месте ноды — сам вид. Клавиатура — `keyboardLayoutGuide` (привязанный к ней пустой вид
  заставляет `NodeView` раскладываться, когда она движется, и в элементы фокуса не
  попадает). На TV этот вид не ставится — проверкой устройства: соответствие
  `KeyboardFollowing`, недоступное на tvOS, приведение во время выполнения всё равно находит
  (дефект 210). Поле в правке прокручивается над
  клавиатурой после первого применённого прохода раскладки: экран решает раскладку в фоне
  (`solvesInBackground`), и в проходе, где пришла клавиатура, рамки ещё прежние — первая
  попытка прокрутки поэтому не срабатывала.
- **Интерактивное скрытие работает через существующий `ScrollDriver`:**
  `keyboardDismissMode = .interactive` у его `UIScrollView`, чей жест перенесён на
  `NodeView`. Переделка прокрутки не понадобилась (дефект 208).
- Демо: экран Sign Up (`OPEN_FORM=1`, маршрут `.form`) — длинный текст, под ним Name и Email.

Проверено: модельные тесты — отступ клавиатуры укорачивает раскладку и `reveal` поднимает
поле; рамка вложенной ноды и её обрезка прокруткой; `TextField` — текст от пользователя и от
кода, Return `.next`/`.done`. UI-тест iOS `KeyboardTests`: поле находится, по касанию
клавиатура, поле над ней; Return в Name переводит клавиатуру в Email; набранное приходит в
модель; Email над клавиатурой; перетаскивание текста вниз убирает клавиатуру.

Не проверено и не сделано (пункты с критериями приёмки — в
[15-keyboard-acceptance.md](15-keyboard-acceptance.md)): что клавиатура идёт за пальцем кадр за кадром и

## C0: Control и Tooltip (2026-09-29)

**Статус: сделан; модель и адаптеры проверены тестами, наведение и подсказка живым курсором
— нет.**

- `Nodes`: `Control: Node` — `isEnabled`, `isSelected`, `command`, `state: ControlState`
  (`.pressed`, `.focused`, `.hovered`, `.disabled`, `.selected` — множество флагов),
  `stateChanged(from:)` для подкласса (вызывается и один раз при создании). `pressChanged`,
  `focusChanged`, `hoverChanged` у `Control` закрыты: подкласс показывает всё через
  `stateChanged`. Выключенный контрол (`isEnabled == false` или его команду сейчас нельзя
  выполнить) не нажимается, не фокусируется, не подсвечивается курсором, теряет фокус при

  `NodeHost.toolTip(at:)`, `toolTipItems()` (видимая часть рамок). `Node.hoverChanged` и
  `NodeHost.pointerMoved(to:)` — наведение приходит ноде, куда пошло бы нажатие.
- `NodesRender`: `Button` — подкласс `Control`, API прежний; добавлены `Button(command:)`,
  светлее под курсором, тусклая выключенная.
- Mac: область слежения за мышью (`mouseMoved`/`mouseEntered`/`mouseExited`), после
  отрисовки и прокрутки наведение пересчитывается под неподвижной мышью; подсказки —
  область `addToolTip` на каждую ноду с подсказкой, текст от `NSViewToolTipOwner`.
- iPad: `UIHoverGestureRecognizer` и `UIToolTipInteraction` (рамка подсказки — видимая часть

- Клавиши: Return и Space уже нажимали ноду в фокусе на Mac и iPad — осталось как было.
- Демо: бейдж Follow — `Control` с подсказкой «Follow …» / «Stop following …» и наведением.

Проверено: модельные тесты `ControlTests` (состояния вместе, наведение, выключенность,
отбор фокуса и нажатия, команда от места контрола и её включённость, подсказки);
`AppKitPointerTests` (события мыши → наведение, текст подсказки по точке);

## C2: вложенный вид платформы (2026-09-30)

**Статус: сделан для iOS/iPad и Mac; модель и адаптеры проверены тестами, UI-тест iOS прошёл,
UI-тест Mac после правок ждёт прогона; TV — вложенные виды не проверялись.**

Прототип C2–C4 показывал только `TextField` и знал о нём в адаптере UIKit (`makeHolder` приводил
ноду к `TextField`). Теперь адаптер ничего не знает о конкретных нодах:

- `Nodes`: `EmbeddedNode` (как в прототипе) — нода, в рамке которой адаптер показывает вид
  платформы; `preferredSize`, `NodeHost.embeddedItems()`.
- `NodesUIKit`, `NodesAppKit`: `HostedView<View>` — общая нода для любого `UIView` (`NSView`):
  `HostedView(sizing:make:update:)`. `make` создаёт вид (цели и делегаты вида — там же, что
  пользователь делает в виде, возвращается в модель ими); `update` выполняется при создании вида и
  при каждом изменении `State`, прочитанного в нём. `Sizing`: `.intrinsic` (собственный размер вида:
  `intrinsicContentSize`, иначе минимум по его раскладке) или `.fixed(размер)`; `invalidateSize()`
  меряет заново. `focus()`, `unfocus()`, `hasKeyboard` (не наблюдаемо). `view` — слабая ссылка, пока
  нода в дереве.
- Адаптер: вид лежит в обрезающем виде поверх отрисовки, в рамке ноды, сдвигается с прокруткой,
  обрезается по тому, что показывают охватывающие ноды; вне видимой части он обрезан до нулевого
  размера, а не скрыт (скрытый вид выпадает из доступности). Скрытая нода или нода вне дерева
  отдаёт вид: держатель снимается, вид освобождается. Порядок — как в дереве (позже — выше); на
  Mac порядок правится, только когда он неверен: вид, снятый с родителя и возвращённый, теряет
  клавиатуру. В порядке чтения доступности на месте ноды стоит сам вид.
- `TextField` подключён к адаптеру через `UIKitEmbedded`/`AppKitEmbedded`: на UIKit — `UITextField`
  как в прототипе, **на Mac теперь `NSTextField`** (текст, подсказка, начало и конец правки, Return →
  `onSubmit`, `.next` → следующее поле дерева, `beginEditing()`/`endEditing()`).
- Демо: `HOSTED_PROBE=1` — системная кнопка в дереве (`UIButton`/`NSButton`), счётчик нажатий рядом,
  страница, которую можно прокрутить так, что кнопка уходит из виду.

Проверено: `UIKitHostedViewTests` на iPhone 17 и `AppKitHostedViewTests` на Mac — вид в рамке ноды и
размер вида как размер ноды, изменение размера вида (`invalidateSize`), обрезка прокруткой и обрезка
до нуля без скрытия, скрытая нода отдаёт вид и показанная снова делает новый, порядок по дереву,
`update` следит за `State`, фиксированный размер до появления вида, клавиатура по запросу. Полный
`swift test` на Mac прошёл; сборка пакета и трёх демо (Mac, iOS, tvOS) — да.

Первые прогоны UI-тестов пользователем (iOS, Mac) не прошли, причины две. Реальный дефект
адаптеров: размер, который вид сообщает ноде при создании, приходит внутри прохода раскладки, а
хост не просит вид о новой раскладке изнутри прохода — нода оставалась размера по умолчанию
(кнопка 200 × 44 вместо своих ~100 × 34) до следующей причины для раскладки; теперь адаптеры после
создания видов просят следующий проход. (У `TextField` в прототипе это было так же, не замечено.)
Ошибка теста Mac: у скрытой прокруткой кнопки рамка доступности сохраняет размер вида (обрезан
только держатель), поэтому «высота 0» не признак — тест смотрит, пересекает ли рамка окно. Второй
прогон Mac после правки раскладки: размер кнопки верный (113 × 26), но колесо `scroll(byDeltaX:
deltaY:)` окна страницу не сдвинуло за 8 нажатий по 300 — какие сдвиги оно даёт на Mac, неясно;
тест Mac теперь двигает страницу кнопками дерева («Page end», «Page start» над прокруткой,
`scrollToReveal`), колесо над вложенным видом этим тестом не проверяется.

После правок UI-тест iOS (`HostedViewTests`, iPhone 17) прошёл: кнопка нажимается, уходит с
прокруткой и возвращается.

Не проверено: UI-тест Mac после правок; iPad и TV;
Mac — `TextField` на живом экране (ввод, Return, Tab) и доступность вложенного вида для
VoiceOver (вид ставится родителем элементов дерева, проверку на Mac делает только UI-тест);
размер, зависящий от ширины (вид, чья высота растёт при узкой ширине, меряется один раз —
`sizeThatFits` для заданной ширины не используется); первый проход раскладки даёт виду размер
по умолчанию, следующий — измеренный; вид, у которого меняется собственный размер без вызова
`invalidateSize()`; несколько `HostedView` с общим первым ответчиком (порядок Tab между видами).

## Решение для истории — 2026-09-28

Зафиксировано по просьбе пользователя после обсуждения восьми вопросов и сверки плана
с текущими исходниками. Первый ответ был общими рекомендациями без чтения проекта;
эта запись отражает уточнённое решение после просмотра кода.

### Основания

- `Sources/NodesRender/Button.swift`: `Button` наследуется от `Node` и сам обрабатывает
  нажатие и фокус. Общий `Control: Node` соответствует существующей архитектуре.
- `Sources/NodesRender/Text.swift`: сейчас текст — строка с единым стилем. Rich text
  требует развития и показа, и редактора, с общей моделью содержимого.
- `Sources/NodesUIKit/NodeView.swift` и `Tests/NodesRenderTests/UIKitScrollTests.swift`:
  iOS-прокрутка уже использует `UIScrollView` для физики. Исходная предпосылка вопроса 4
  о необходимости впервые перевести Scroll на UIScrollView была неточной (дефект 208).
- В проекте есть состояния, темы, команды, фокус и `SceneSession`. Компоненты расширяют
  эти механизмы; `Toast` относится к уровню окна, а не к иерархии `Control`.
- Выборочно просмотрены локальные `docs/richtext-composer.md`,
  `submodules/TelegramCore/Sources/ChatInputContent/ChatInputContentModel.swift` и
  `submodules/TelegramUI/Components/RichTextEditor/Sources/RichTextEditorUIKit/Layout/BlockLayoutEngine.swift`
  в Telegram-iOS. Оттуда берём разделение модели содержимого и платформенного ввода,
  не обязательство повторить весь редактор.

### Ответы по номерам

1. **Switch и Checkbox — свои по теме.** Единый визуальный стиль, платформенные способы
   взаимодействия и доступность. Checkbox сразу поддерживает смешанное состояние.
2. **Поля — системные через общий механизм вложенного вида.** Сохраняем IME, диктовку,
   выделение, undo/redo, автозаполнение и внешнюю клавиатуру. EmailField и SecureField
   используют общую основу с настройками ввода. Свой движок в первую версию не входит.
3. **Rich text — сразу блочная модель.** Первая версия: абзацы, цитаты, код, базовое
   форматирование и ссылки. Списки, спойлеры и упоминания добавляются постепенно.
   Показ и редактирование используют одну модель.
4. **Интерактивное скрытие клавиатуры нужно.** Поле и нижняя панель следуют за клавиатурой,
   курсор остаётся видимым, контент не прыгает. Способ интеграции с существующим
   ScrollDriver подтверждается прототипом до решения о переделке прокрутки.
5. **Select — системное меню для короткого списка на iPhone.** Для длинного списка —
   отдельный режим с листом и поиском следующим этапом. Колесо не является вариантом
   по умолчанию. Модель выбора общая, представление зависит от платформы.
6. **Toast — замена текущего по умолчанию, очередь по настройке.** На TV нужен без
   перехвата фокуса. Важные ошибки не должны существовать только в исчезающем сообщении.
7. **Валидация разделена между компонентом и приложением.** Компонент хранит и показывает
   состояние и сообщение, приложение задаёт правила. У EmailField есть переопределяемая
   базовая проверка формата. Поддерживаем настройку момента проверки и асинхронные правила.
8. **Сначала прототип C2–C4, затем C0 → C1 → C2–C4 → C5 → C6 → C7.** Ранний прототип
   проверяет наиболее рискованное место: системный ввод внутри дерева, рисуемого слоями.

### Что остаётся проверить

- Вложенные виды: жизненный цикл, обрезка, порядок относительно слоёв, координаты при
  прокрутке, скрытие, доступность и сохранение редактирования при обновлении дерева.
- Согласование фокуса дерева с first responder, Tab/Shift-Tab и командами редактора.
- Интерактивная клавиатура в текущей иерархии жестов, плавающая клавиатура iPad,
  внешняя клавиатура и отсутствие двойного учёта нижнего отступа.
- Преобразования rich text: единицы смещений, Unicode, выделение, IME и undo/redo.
  Точные API, границы поддержки TextKit и формат конвертеров уточняются при реализации.

Эта запись фиксирует решение, а не результат реализации. При просмотре исходников
сборка и тесты не запускались; поведение на Simulator и устройствах не проверялось.
