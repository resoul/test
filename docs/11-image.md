# Image и дисковый кэш

**Первый срез реализован 2026-09-25.** `Image` живёт в `NodesRender`: это нода со статичным
изображением, без UIKit/AppKit. Источник — `Data` или URL. URL файла читается напрямую,
сетевой URL проходит через `ImageCache`. `ImagePipeline` загружает и декодирует вне MainActor,
а нода принимает результат только для текущего источника. Смена источника отменяет прежнюю
задачу; запоздавший результат не меняет ноду.

`Image` сообщает собственный размер в точках: ориентированные размеры исходных пикселей,
делённые на `scale` (по умолчанию 1, как у `AsyncImage`; для ресурса @2x — 2). `scale`
меняет только размер в раскладке, а не то, сколько пикселей декодируется. Пропорция
сохраняется в обе стороны, как у `<img>`: без ограничений картинка занимает свой размер;
получив ширину от контейнера или `width`, берёт высоту по пропорции (400×200 в столбце
шириной 100 → 100×50); получив высоту — от строки высотой 40 или `height` — берёт ширину
(→ 80×40). В строке шириной меньше своей картинка, как и `<img>`, не сжимается ниже
собственной ширины, пока у неё `minWidth` не 0. Для этого `Image` отдаёт движку
`LeafContent.proportional`: собственная пропорция действует как `aspect-ratio: auto` у
`<img>` (`aspectRatio` в стиле её заменяет), а сторона по пропорции не держится
содержимым. Собственная пропорция относится к области содержимого, как у `<img>`: отступы
картинки добавляются к обеим сторонам (400×200 с `padding(10)` в столбце шириной 120 →
120×70); пропорция из `aspectRatio` в стиле — ко всей рамке, как у любого блока (дефект #169,
`BoxRatio`). Абсолютно позиционированная картинка не растягивается между двумя отступами —
они её только ставят, размер остаётся своим (дефект #171). Сверено с Chromium 153 на 43
кейсах `Conformance/CSSFlexbox/fixtures/image.json`, из них 14 с отступами у картинки и 3
абсолютных с парой отступов; расхождений нет.

`.fit` вписывает изображение, `.fill` заполняет рамку с обрезкой, `.stretch` растягивает.
Ориентация применяется при создании bitmap для показа. Сначала декодируется небольшое
превью (по умолчанию до 256 пикселей по длинной стороне). Когда известна рамка ноды,
`Image` запрашивает детализацию под её размер в точках × масштаб дисплея. Для `.fit`
достаточно меньшего из масштабов по осям; `.fill` и `.stretch` учитывают ось, требующую
больше исходных пикселей. При увеличении рамки или смене масштаба дисплея изображение
декодируется заново из исходных закодированных байтов. Старый bitmap остаётся видимым,
пока готовится новый. Разрешение никогда не превышает размер оригинала.

Жёсткого предела 8K или 4096 по умолчанию нет. При необходимости приложение задаёт
`ImagePipeline.maximumDecodedPixelDimension`; это ограничивает только bitmap в памяти,
**но не меняет файл на диске**. `Image.decodedPixelSize` показывает текущую детализацию,
а `Image.pixelSize` — ориентированные размеры оригинала.

Слой показывает декодированную картинку как есть (`LayerDrawing.layerImage`): рендерер
ставит её в `contents` и не рисует копию размером «рамка × масштаб», так что картинка
лежит в памяти один раз — в pipeline и слое одна ссылка. Вписывание делает Core
Animation: `.fit` — `contentsGravity = .resizeAspect`, `.stretch` — `.resize`, `.fill` —
`.resize` и `contentsRect` с центральной частью (не `masksToBounds`: он обрезал бы тень
`appearance`). Смена рамки или масштаба не требует новой отрисовки. Цвет не
переводится в 8-битный sRGB слоя — картинка показывается в своём цветовом пространстве.
Placeholder — один пиксель его цвета, растянутый на рамку.

`ImagePipeline` разделяет готовые bitmap между нодами одного pipeline. Ключ содержит
отпечаток текущих закодированных байтов и запрошенный размер: замена файла по тому же URL
не возвращает старую картинку. Чтобы попадание в кэш не читало и не хэшировало файл
заново, pipeline помнит отпечаток для URL вместе со «штампом» файла — размером и датами
(для записи дискового кэша — размером и датой создания, которая обновляется при
перезаписи). Пока штамп тот же, картинка находится без чтения; штамп запоминается, только
если файл не менялся во время чтения. Для удалённого URL первое чтение записи на диске
после загрузки запоминает штамп, следующие обходятся без чтения. Источник `.data`
хэшируется при каждом запросе — байты уже в памяти. Штамп опирается на даты файловой
системы: на ФС с секундной точностью замена файла тем же размером в ту же секунду
осталась бы незамеченной (APFS хранит наносекунды). Одновременные запросы одного размера используют одну
декодировку. Остальные декодирования одного pipeline — любых изображений и размеров — идут
по одному, чтобы не создавать несколько больших bitmap одновременно: первым — первый в
очереди из запросов нод на экране, иначе первый пришедший (ниже, «Приоритет видимых»).
Очередь не занимает сам pipeline: попадания в кэш и отмена обслуживаются, пока идёт
декодирование. Запрос, отменённый в очереди, покидает её, не начав работу. Цена — превью
ждёт в той же очереди за начатым большим декодированием. Кэш удерживает не более
`maximumDecodedCacheBytes` (по умолчанию 64 МиБ по оценке `bytesPerRow × height`), вытесняя
давно не использованные размеры; слишком большой bitmap в него не кладётся.
Значение `0` отключает удержание. `clearDecodedCache()` освобождает ссылки pipeline;
декодировки, начатые до очистки, его не заполняют заново. Это можно вызвать после
предупреждения о нехватке памяти. Лимит относится **только к этому кэшу**:
живые ноды и их слои могут продолжать держать показанные bitmap.

## Placeholder и состояние загрузки

`ImagePlaceholder` — необязательная однотонная заливка. Она видна, пока источник пуст,
загружается или первый запрос завершился ошибкой; первое декодированное превью заменяет её.
Можно задать `size` для собственного размера до появления оригинала; он ведёт себя как
размер картинки, в том числе держит пропорцию. Без `size` раскладка должна ограничить
ноду снаружи, иначе пустой источник измеряется как ноль.

`Image.phase` — доступное только для чтения наблюдаемое значение `ImageLoadPhase`:
`.empty`, `.loading`, `.ready` или `.failed(ImageLoadFailure)`. Чтение в `update()` подписывает ноду на
изменения фазы. `.ready` наступает уже на превью и сохраняется при загрузке более чёткой
версии. `retry()` повторно загружает текущий источник. Файл (`file:` URL) и `.data`
читаются заново, поэтому файл, изменившийся по тому же URL, показывается новым. Для URL по
сети `retry()` идёт через дисковый кэш: после ошибки там ничего нет (ошибочные ответы и
не-картинки не кэшируются), и картинка скачивается заново; но если на диске лежит
свежая копия, `retry()` вернёт её, даже если на сервере картинка сменилась: свежесть
задаёт сервер (ниже, «HTTP-кэширование»). Чтобы скачать заново, приложение удаляет запись:
`cache.remove(for: url)`, затем `retry()`. Смена источника сбрасывает состояние; отменённый старый запрос не может его
изменить.

Причина ошибки (2026-09-26) — `ImageLoadFailure` в `.failed` (или `phase.failure`):
`.network(URLError.Code)` — сервер недоступен (нет сети, таймаут, имя не находится), имеет
смысл повторить позже; `.status(Int)` — сервер ответил не картинкой (404, 500); `.tooLarge` —
ответ больше `maximumDownloadBytes`; `.invalidImage` — байты не картинка или политика
метаданных неприменима; `.file` — файл не прочитан (нет, нет доступа); `.other` — остальное
(ответ не HTTP). `ImageLoadFailure(error)` переводит ошибку загрузки. `ImageCacheError`
получил `.status(Int)` вместо `.invalidResponse` для неуспешного ответа; `.invalidResponse`
остался для ответа не по HTTP. Проверено тестом на пять источников ошибки (нет файла, не
картинка, 404, нет сети, больше предела) через ноду; поломка перевода роняет его.

## Доступность

Картинка по умолчанию **декоративная**: без метки она не элемент дерева доступности, и
VoiceOver её пропускает — придумать осмысленную метку за приложение нельзя, у картинки
по URL нет даже имени. Метка задаётся как у любой ноды, `image.accessibility.label =
"Портрет Ады"`: картинка становится элементом с чертой `.image`. Отдельного параметра
`label` у `Image` нет — это был бы второй способ сделать то же самое. Кнопка из одной
картинки (нода с `onTap`) берёт имя из меток вложенных нод, то есть из метки картинки;
без метки её имя пустое, поэтому у кнопки-иконки метка нужна всегда.

## Уход из дерева

Нода, которую `layoutSpec` перестал размещать (`if`, сторона `Breakpoint`), но которую
экран держит в свойстве, получает `mountedChanged(false)`: загрузки отменяются (общая
загрузка URL — если ушли все её ждущие), декодированный bitmap отпускается. `pixelSize` и
`phase` остаются, поэтому раскладка не прыгает при возвращении. `mountedChanged(true)`
возобновляет незаконченную первую загрузку; готовую картинку рендерер запрашивает заново под
рамку, и кэш памяти pipeline часто ещё держит её. До этого кадр рисует placeholder. Смена
источника у ушедшей ноды сбрасывает состояние, но загрузку начнёт только возвращение.
Нода, ещё ни разу не смонтированная, грузит сразу — чтобы быть готовой к первому показу.
В обычной колонке внутри `Scroll` все ноды списка смонтированы и грузят сразу. В
`LazyStack` ([03](03-layout-api.md), десятый срез) смонтированы только элементы у окна: ушедшие
далеко получают `mountedChanged(false)`, и их загрузки отменяются.

### Приоритет видимых

Реализовано 2026-09-26. `LazyStack` раскладывает экран запаса до и после окна, и картинки
запаса грузятся вместе с видимыми; очередь декодирования — одна. Видимые идут первыми:

- `Node.tracksScreen` просит хост держать `Node.isOnScreen` — видна ли часть ноды в границах
  хоста и всех обрезающих предков, без скрытых и прозрачных — и звать `screenChanged(_:)` на
  переходах. Хост пересчитывает после каждого прохода и каждого движения прокрутки, только
  для таких нод. `Image` включает его сам.
- `Image` передаёт в каждый свой запрос (превью и детализация) `LoadUrgency` — флаг «на
  экране», который меняется, пока запрос ждёт. Общая декодировка срочна, пока срочен любой
  её ждущий (`SharedUrgency`).
- `DecodeGate` при освобождении отдаёт место первому срочному в очереди, иначе первому
  пришедшему. Срочность спрашивается в этот момент: картинка, прокрученная на экран, пока
  ждала, обгоняет остальные. Уже идущее декодирование не прерывается.
- Без `LazyStack` все картинки списка смонтированы и стоят в очереди — видимые обгоняют и
  там.

- Загрузки из сети (2026-09-26): у задачи `URLSession` приоритет
  `URLSessionTask.highPriority`, пока картинка на экране, иначе `lowPriority`; меняется на
  ходу, когда картинка въезжает на экран или уходит. Общая загрузка URL срочна, пока срочен
  любой её ждущий; присоединившийся срочный поднимает её. `LoadUrgency` сообщает об изменении
  наблюдателям, `SharedUrgency` — своему; задача узнаётся из `didCreateTask` делегата
  (`DownloadWatch`, он же следит за `maximumDownloadBytes`). Наблюдатели снимаются, когда
  общая загрузка или декодирование закончились. Приоритет — подсказка `URLSession`: на
  HTTP/2 это приоритет потока, на HTTP/1.1 — порядок в очереди соединений; выигрыш по времени
  не измерялся.

Проверено (2026-09-26, загрузки): 4 теста на заглушке сервера — приоритет по срочности,
смена приоритета идущей загрузки, срочный ждущий поднимает общую загрузку, наблюдатели
снимаются после загрузки; каждый проверен поломкой.

Проверено (2026-09-26): 7 тестов — порядок очереди, смена срочности в ожидании, общая
декодировка, срочный запрос через pipeline обгоняет пришедший раньше, `Image` срочна на
экране и не срочна вне его и после ухода, `isOnScreen` и `screenChanged` при прокрутке и
скрытии. Каждый проверен поломкой: без приоритета, без реакции `Image`, без обновления
хоста при прокрутке, без передачи срочности в очередь — падает. Вживую разница во времени не
измерялась.

## Настройки хранения

`ImageCacheConfiguration` задаёт папку, предел байтов (по умолчанию 256 МиБ), срок от
записи (7 дней), политику метаданных, политику сжатия и минимальный размер для попытки
сжатия (1 МБ). Кэш считает и удаляет только записи — файлы с именем «метка политик
(8 шестнадцатеричных символов) — отпечаток URL (64)»; остальное в папке он не трогает.
Папка по умолчанию общая для всех кэшей, поэтому лимит и срок каждый кэш применяет только
к записям своих политик (метаданные, сжатие, порог сжатия): кэш с малым лимитом не
вытесняет записи кэша с другими политиками. Кэши с одинаковыми политиками в одной папке
делят записи и бюджет — действует меньший из их лимитов. Файлы прежнего формата имени (без
метки) удаляются при пересчёте. Размер ведётся счётчиком:
папка пересчитывается при первой записи, при превышении лимита и раз в 64 записи (её могут
менять другой кэш или процесс), а не на каждую запись. Пересчёт удаляет просроченные файлы,
затем давно не использованные сверх лимита; `removeExpired()` делает то же явно — например,
при запуске. `removeAll()` удаляет все записи папки, какими бы политиками они ни были
записаны, `remove(for:)` — запись URL для политик этого кэша. Загрузка, начатая до
`removeAll()` этого кэша, возвращает картинку, но не записывает её; загрузки других
экземпляров `ImageCache` в той же папке этим не останавливаются. Кэш памяти pipeline и показанные
bitmap это не трогает: при выходе из аккаунта нужен ещё `clearDecodedCache()`.
Одновременные запросы одного URL ждут одну загрузку; запрос, отменённый
раньше других, уходит из неё, а последний ушедший отменяет загрузку до записи на диск.
Файл пишется атомарно.

Сеть — `URLSession`, переданная в `ImageCache(configuration:session:)` (по умолчанию
`.shared`): заголовки, таймауты и авторизация задаются её конфигурацией или делегатом.
`maximumDownloadBytes` (по умолчанию без предела) ограничивает тело ответа: ответ с большим
`Content-Length` обрывается на заголовках, без него — как только пришло больше предела;
в памяти остаётся не больше предела и одного сетевого куска, `load` бросает
`responseTooLarge`, на диск ничего не пишется. Для источников, которым нельзя доверять,
предел стоит задать. Старые по последнему обращению файлы удаляются при
превышении лимита. Ключ содержит URL и политики обработки: смена настроек не выдаёт
старый вариант файла. Ошибочные ответы HTTP и нераспознанные изображения не кэшируются.

По умолчанию сохраняются **исходные байты**. Обе политики используют Image I/O
copy-source без перекодирования пикселей и сохраняют то, что нужно для показа, —
ориентацию EXIF и цветовой профиль:

- `metadata: .removeLocation` удаляет координаты GPS (из EXIF и из XMP), остальное —
  дату съёмки, XMP, IPTC — оставляет. Текстовое место в XMP/IPTC (например,
  `photoshop:City`) при этом **остаётся**: Image I/O относит к «GPS» только координаты.
- `.removeLocationAndXMP` оставляет только теги EXIF/TIFF без GPS; XMP, IPTC и с ними
  название места удаляются. Image I/O при этом не сохраняет и дату съёмки. Если формат нельзя переписать с этой политикой (Image I/O читает WebP,
но не записывает его), картинка показывается, но на диск не попадает: сохранить оригинал
значило бы оставить то, что политика удаляет. Такой URL при следующем показе скачивается
заново. `compression: .losslessIfSmaller` пробует повторно записать
однокадровый PNG только после порога и выбирает результат только если он меньше.
Для JPEG и прочих форматов повторного сжатия нет: обещать меньший файл без потери
качества нельзя.

Настройки передаются через `ImageCache` → `ImagePipeline` → `Image`; нет глобального
изменяемого состояния. Несколько изображений могут пользоваться одним pipeline.

```swift
let cache = ImageCache(configuration: ImageCacheConfiguration(
    maximumBytes: 128 * 1024 * 1024,
    metadata: .removeLocationAndXMP,
    compression: .losslessIfSmaller
))
let pipeline = ImagePipeline(cache: cache)
let avatar = Image(
    source: .url(photoURL),
    contentMode: .fill,
    placeholder: ImagePlaceholder(
        color: Color(red: 0.9, green: 0.9, blue: 0.9),
        size: LayoutSize(width: 48, height: 48)
    ),
    pipeline: pipeline
)
```

## HTTP-кэширование

Реализовано 2026-09-26. Дисковый кэш слушает сервер (RFC 9111):

- `Cache-Control: no-store` — ответ не пишется на диск, прежняя запись URL удаляется.
- Свежесть: `no-cache` — устаревает сразу; `max-age` — от ответа за вычетом `Age`; иначе
  `Expires` (некорректная дата — уже устарел). Без них запись свежа, пока её держит кэш
  (`maximumAge`, как раньше).
- Устаревшая запись с `ETag` или `Last-Modified` сверяется условным запросом
  (`If-None-Match`, `If-Modified-Since`): ответ 304 продлевает её по новым заголовкам без
  повторной загрузки, файл остаётся тем же. Без валидаторов — загружается заново. Запись,
  исчезнувшая между запросом и 304, загружается целиком.
- `maximumAge` — верхний предел: запись старше удаляется, что бы ни сказал сервер.
- Валидаторы и срок свежести лежат в расширенном атрибуте файла записи
  (`image-cache.http`, JSON) — в папке только записи, и переписанный файл начинает без них.
- Штамп устаревшей записи — `nil`: pipeline не берёт декодированную картинку по штампу, а
  идёт в кэш, который сверяется с сервером.
- Запрос идёт с `reloadIgnoringLocalCacheData`: кэш — записи на диске, собственный кэш
  сессии не отвечает вместо сервера.

Проверено (2026-09-26): 7 тестов на заглушке сервера — свежая запись читается с диска,
`no-cache` сверяется по `ETag` (304, та же запись), по `Last-Modified`, `Age` съедает
`max-age`, устаревшая без валидаторов загружается заново, `no-store` не пишется, pipeline не
обходит сверку по штампу. Каждый проверен поломкой.

## Границы первого среза

- Показывается первый кадр. Анимированные изображения, HDR/gain map и видео требуют
  отдельного контракта.
- Смонтированные ноды и их слои держат показанные bitmap (одну копию, общую с кэшем
  pipeline, пока он её не вытеснил) независимо от лимита общего кэша, в том числе за пределами видимой области `Scroll`; бюджет всей памяти процесса
  пока не задаётся. Ушедшие из дерева ноды bitmap отпускают.
- HTTP-кэширование — без `Vary`, `must-revalidate`, `stale-while-revalidate` и
  `s-maxage`; ответ с `Vary` хранится по одному URL.
- Готового UI для повторной попытки нет: причина ошибки есть, решение показать и
  повторить — за приложением (`retry()`).

Политики метаданных проверяются на JPEG «как с камеры» (ориентация 6, полный GPS, дата,
XMP с заголовком и городом): у исходника всё это есть, после каждой политики — ровно
описанное выше; пиксели не меняются, сохранённая копия показывается повёрнутой правильно.
Приёмка первого среза: сборка пакета, тесты дисковой записи/лимита/разделения политик,
показа без кэширования формата, к которому политика неприменима (WebP через подменённый
HTTP-ответ),
одной загрузки на одновременные запросы URL и выхода отменённого запроса из неё,
предела размера ответа (с `Content-Length` и без), некэширования ответа 404,
сохранности чужих файлов папки при вытеснении и `removeAll`, `remove(for:)`,
удаления просроченных без чтения, записи без скана папки, незаписи загрузки после
`removeAll`,
отдельных лимитов кэшей с разными политиками в общей папке и удаления файлов прежнего
формата,
удаления GPS без изменения JPEG-пикселей, реального уменьшения PNG без изменения
пикселей, смены источника и режима показа. Дополнительная приёмка адаптивного
декодирования проверяет детализацию после изменения рамки и масштаб дисплея, включая
обрезку `.fill`. Тесты памяти проверяют повторное использование, объединение одновременных
запросов, декодирование по одному (пик одновременных — 1 на шести картинках), выход
отменённого запроса из очереди, отсутствие повторного чтения неизменного файла и записи
дискового кэша, вытеснение по лимиту и замену файла по тому же URL.
Тесты раскладки сверяют рамки с `<img>` в Chromium 152 (свой размер, высота по ширине,
без сжатия при `center`) и проверяют `scale`.
Тест доступности: без метки картинка не элемент, кнопка-иконка без метки — с пустым
именем; с меткой картинка — элемент `.image`, кнопка — с меткой картинки.
Тесты ухода из дерева проверяют освобождение и возвращение пикселей, отмену загрузки при
уходе и её возобновление при возвращении.
Тесты placeholder проверяют собственный размер и его пропорцию, смену на превью, ошибку, повторную
попытку и сброс состояния при удалении источника.
Поворот по EXIF: JPEG с ориентациями 1, 2, 3, 6, 8 (пиксели «левая половина красная»)
— размер для раскладки, рамка и пиксели показываемой картинки; без применения поворота
при декодировании падают 2, 3, 6, 8, без перестановки осей — 6 и 8. Ориентации 5 и 7
(транспонирование) отдельно не проверены.
Показ без копии: слой ссылается на декодированную картинку, placeholder — один пиксель,
`.fill` обрезается через `contentsRect`; тесты пикселей снимают то, что слой показывает
(`CALayer.render(in:)`), а не `contents`.
`swift test` на Mac прошёл; iOS Simulator (iPhone 17) и tvOS Simulator (Apple TV 4K,
3rd generation) — все тесты пакета, 0 ошибок (последний прогон 2026-09-25, после показа
без копии). Физическое устройство не проверялось.
