# Хранение данных и сеть: Preferences, Cache, Files, GRDB, HTTP и WebSocket

**Статус на 2026-10-09: S0–S8 выполнены; остатки S5 и S6 — в разделе «S5, S6, S8: остатки».** Пользователь запросил UserDefaults,
кэш, файлы, SQL через GRDB на устройствах проекта и удобный слой HTTP/WebSocket с их совместным
использованием. Выбор GRDB — требование пользователя. Границы модулей и контракты ниже —
предложение по результатам повторного просмотра библиотеки; результаты прототипа (S0) и Preferences
(S1) — в разделе 13. Псевдокод остальных разделов показывает направление API, а не существующие методы.
Разрешения системы — отдельный план: [18-permissions.md](18-permissions.md).

## 1. На что опираемся

Просмотрены текущие исходники, включая незакоммиченные изменения рабочего дерева:

- `Package.swift`: Swift tools 6.0; iOS 16+, tvOS 16+, macOS 14+. GRDB пока нет.
- `Sources/StateCore/State.swift`: синхронное состояние на MainActor. Файловые операции,
  запросы к SQL и сети нельзя выполнять из чтения `State.value` или `Node.update()`.
- `Sources/StateAsyncRay/StateAsyncRay.swift`: уже есть отдельный мост потоков к состоянию
  и отменяемые подписки. AsyncRay не должен стать обязательным для хранения и сети.
- `Sources/NodesRender/ImageCache.swift`: actor, дисковый кэш, возраст и размер,
  вытеснение по использованию, HTTP-валидаторы, общая загрузка для нескольких клиентов,
  отмена и обработка метаданных изображений. Это специализированный кэш, не пустое место.
- `Sources/NodesRender/Image.swift`: ImagePipeline отдельно держит декодированные картинки
  в памяти; загрузки связаны с жизненным циклом ноды.
- `Sources/AppShell/Application.swift`, `Sources/AppShell/Screen.swift`: приложение,
  сцены и экраны — естественные владельцы сервисов, моделей и подписок разного срока жизни.
- `docs/02-modules.md`: модули используются независимо, зависимости направлены вниз.

Работа по контролам продолжается отдельно в `docs/13-controls.md`. Хранение и сеть не
требуют завершения rich text и не меняют контракты движка раскладки.

## 2. Цель и границы

Единый удобный способ собирать приложение, но разные инструменты для разных данных:

| Данные | Инструмент | Гарантия |
|---|---|---|
| Небольшие настройки: тема, сортировка | Preferences / UserDefaults | Настройки, не транзакционная база |
| Восстанавливаемые ответы и байты | MemoryCache / DiskCache | Могут исчезнуть; промах — нормальный результат |
| Документы, вложения, экспорт | FileStore / FileManager | Явное расположение и ошибки файловых операций |
| Сущности, связи, выборки, миграции | DatabaseStore / GRDB | Транзакции SQLite, наблюдение за выборками |
| Запрос/ответ, загрузка файлов | HTTPClient / URLSession | Отмена, статус, заголовки и политика повторов |
| Длительное соединение и события | WebSocketClient | Порядок в соединении, явные разрывы и восстановление |

Секреты не храним в UserDefaults или обычном кэше: слой авторизации получает их через
внедряемый поставщик credentials; Keychain-адаптер можно добавить отдельно. SQL означает
SQLite через GRDB, не прямое подключение мобильного клиента к серверной SQL-базе.
Одинаковый API на устройствах не означает автоматическую синхронизацию между ними.

## 3. Предлагаемые модули

| Модуль | Содержание | Зависимости |
|---|---|---|
| `StorageCore` | Типизированные ключи, политики, ошибки, протоколы хранения, тестовые реализации в памяти | Foundation |
| `StorageFoundation` | Preferences на UserDefaults, FileStore, MemoryCache, DiskCache | StorageCore, Foundation |
| `StorageGRDB` | Открытие базы, миграции, read/write, наблюдение, резервная копия | StorageCore, GRDB |
| `NetworkCore` | Запрос, ответ, ошибки, протоколы HTTP/WebSocket, политики | Foundation |
| `NetworkFoundation` | URLSession HTTP и WebSocket, транспортный жизненный цикл | NetworkCore, Foundation |
| `DataAsyncRay` | Необязательные мосты наблюдений и результатов операций к AsyncRay | AsyncRay; зависимости от конкретных адаптеров уточняются на S0 |
| `StateAsyncRay` (существует) | Доставка потоков в StateCore, владение подписками у модели | StateCore, AsyncRay |

`StorageFoundation` и `StorageGRDB` не зависят от сети. `NetworkFoundation` не знает
GRDB или ноды. `StateAsyncRay` принимает Sendable-значения и не импортирует GRDB.
Для приложений с AsyncRay используем существующий мост; отдельный StateData не вводим.
Без AsyncRay доступны async/await и AsyncSequence с явным обновлением State на MainActor.
Не создавать универсальный ORM, контейнер зависимостей или обязательный базовый Repository.
Протоколы вводить для реальной подмены транспорта/хранилища, а не для каждого типа.

```text
HTTP / WebSocket ──► repository приложения ──► GRDB / Files / Cache
                             │                     │
                             └── наблюдение ◄───────┘
                                      │
                            DataAsyncRay → StateAsyncRay
                                      │
                                  StateCore ──► Nodes / экран
```

Стрелки здесь — поток данных. Зависимости модулей заданы таблицей. Сервисы внедряются
инициализаторами; обязательных глобальных singleton нет. Один сервис базы на файл в
процессе; несколько окон разделяют repository, но имеют собственные модели экранов.

## 4. Preferences: типизированные UserDefaults

- `PreferenceKey<Value>` задаёт имя, значение по умолчанию и кодек. Значения — Sendable;
  Codable допускается для небольших структур с версией формата.
- Явные домен/suite и пространство имён. Тесты используют изолированное хранилище.
- Методы чтения, записи, удаления и наблюдения; удаление возвращает к default.
  Ошибка декодирования отличима от отсутствия ключа, не скрывается молча default-значением.
- Actor владеет UserDefaults. UI получает загруженный снимок в State; его синхронное
  чтение не обращается к диску. Запись подтверждается отдельно, ошибка видна модели.
- Наблюдение выдаёт текущее значение, затем изменения; одинаковые значения объединяются.
  Внешние изменения домена обрабатываются повторным чтением, не обещанием точного журнала.
- Не обещать немедленный durable flush, атомарность нескольких ключей или межпроцессный
  compare-and-swap. Связанные данные с такими требованиями идут в SQL.
- При интеграции проверить privacy manifest и required-reason API для UserDefaults;
  причина должна соответствовать фактическому использованию приложением.

## 5. Files: управляемая работа с FileManager

`FileStore` владеет явно переданным корнем и предоставляет read/write/remove/move/list,
метаданные и потоковую работу с большими файлами. Не копирует весь API FileManager.

- Разделить application support, documents, caches и temporary. Политика расположения
  задаётся при сборке приложения; tvOS не получает обещание долговечности файлов.
- Относительные ключи не выходят за корень через `..`, абсолютные пути или symlink.
  Корень управляется хранилищем; произвольные пользовательские URL — отдельный API.
- Запись через временный файл в том же томе и замену назначения. Атомарная видимость
  не означает гарантированную сохранность при отключении питания.
- Ограничения размера, очистка временных файлов после сбоя, ошибки места/доступа/повреждения.
- Копирование крупных файлов не загружает весь файл в Data. Блокирующий файловый I/O
  выполняется на ограниченном исполнителе вне MainActor; actor сам по себе не делает I/O
  неблокирующим. Передача результата соблюдает Sendable без запрещённых аннотаций.
- Импорт из document picker, security-scoped URL, bookmarks и App Groups — расширения
  платформенных адаптеров, не неявные права FileStore.

## 6. Cache: общий кэш и существующие изображения

Первая версия: MemoryCache и DiskCache для Data с отдельным Codable-кодеком поверх.
Операции get/set/remove/removeAll; TTL, предел байтов и вытеснение LRU, внедряемые часы.
Промах, устаревание и ошибка I/O различимы. Политика позволяет приложению считать
повреждённый кэш промахом, но сообщает диагностику.

Ключ включает namespace, версию представления и область пользователя. Очистка учётной
записи отменяет её загрузки и меняет поколение: поздний ответ не восстанавливает удалённые
данные. Общие запросы имеют независимых ожидающих; отмена одного не отменяет остальных.

HTTP-кэширование не заменяется общим TTL: валидаторы, Vary, Cache-Control и авторизация
обрабатываются явно. В первой версии HTTP использует URLCache по конфигурации; repository
отдельно решает, нужны ли ему снимки в DiskCache или SQL. Не держать три копии одного
ответа без определённого владельца и причины.

`ImageCache` и `ImagePipeline` сохраняют публичное поведение. Сначала добавить новые
сервисы независимо, затем извлечь только общие файловые/транспортные операции при
подтверждённой пользе. Метаданные изображений, декодирование и приоритет видимых нод
остаются в изображениях. Перенос не должен терять валидаторы, лимит загрузки, разделяемую
отмену и защиту от записи после очистки.

## 7. SQL: GRDB

Выделить `StorageGRDB`, не добавляя импорт GRDB в LayoutCore, Nodes или StateCore.
Начать с одной DatabaseQueue; DatabasePool включать для подтверждённой потребности в
параллельных чтениях. Использовать GRDB для SQL и records напрямую внутри repository,
без второго языка запросов. Наружу возвращать Sendable-модели, не Row/cursor/соединение.

Контракт нашей обвязки:

- Асинхронное открытие с конфигурацией расположения; миграции до выдачи готового сервиса.
  Ошибка запуска — состояние модели с действием повторить/восстановить, не пустая база.
- Миграции именованы и последовательны; приложение владеет схемой. Запрещён автоматический
  destructive reset production-базы при изменении схемы или ошибке миграции.
- read/write и транзакции используют штатную сериализацию GRDB. Внутри транзакции нет
  await сети, ухода на MainActor или утечки соединения. SQL-параметры передаются отдельно.
- Наблюдение за запросом отдаёт первоначальный снимок и последующие согласованные снимки
  после commit. Ошибка завершает подписку явно; отписка освобождает ресурсы.
- Отмена до commit приводит к rollback, если операция успела обработать отмену.
  После commit отмена не откатывает запись: нельзя бросать CancellationError постфактум
  и создавать впечатление, что подтверждённой записи не было. Проверить гонку на прототипе.
- Backup через поддерживаемый механизм базы. Не копировать только основной sqlite-файл
  открытой WAL-базы. Restore требует остановки доступа и подписок.
- Несколько процессов/App Group, шифрование SQLCipher, полнотекстовый поиск — последующие
  расширения. В первой версии не обещаем шифрование обычного SQLite-файла.

### Платформы и версия

Под «всеми устройствами» принимаются текущие цели: iPhone, iPad, Apple TV, Mac и
Mac Catalyst. watchOS/visionOS не добавляются автоматически этим планом.

На дату просмотра официальный README указывает GRDB 7.11.1, Swift 6.1+ и поддержку
минимальных Apple OS ниже минимумов нашего пакета. Локально установлен Swift 6.4,
но манифест проекта объявляет tools 6.0. На S0 проверить конкретный тег 7.11.1 и
зафиксировать его после сборок; решение о минимальном toolchain записать явно.
Linux upstream поддерживается сообществом без официального сопровождения и автоматических
проверок: для проекта это отдельный обязательный CI-прогон, а не предположение.
Источники: [GRDB README](https://github.com/groue/GRDB.swift/blob/master/README.md),
[манифест GRDB](https://github.com/groue/GRDB.swift/blob/master/Package.swift).

На tvOS проектируем базу как восстанавливаемую: потеря кэша не должна уничтожать
единственный экземпляр пользовательских данных. Это следует из ограничений хранения
[Apple TV](https://developer.apple.com/library/archive/documentation/General/Conceptual/AppleTV_PG/).
В первой версии tvOS не обещает надёжную офлайн-очередь неподтверждённых сервером изменений.

Linux: StorageCore и модели сети тестируются без Apple UI; для FoundationNetworking
допустим `#if canImport(FoundationNetworking)`. Проверить доступность конкретных HTTP/WS
API выбранного toolchain. Отсутствующий транспорт обозначать как неподдержанный, не
заменять заглушкой, выдаваемой за работающий. При несовместимости GRDB нельзя ломать
Linux-сборку LayoutCore/AppShell: S0 должен решить размещение интеграции в отдельном
пакете, если совместная сборка всех targets не проходит. Простое наличие optional product
не отменяет разрешение package dependencies SwiftPM.

## 8. HTTP: тонкая обвязка URLSession

- `HTTPRequest` как значение: метод, URL, headers, тело, timeout; `HTTPResponse` содержит
  status, headers, body. Codable endpoint — удобный слой поверх транспорта.
- Не считать любой полученный ответ успехом: проверять ожидаемые статусы; различать
  transport/status/decoding/cancellation. Пустой ответ и 204 поддерживаются отдельно.
- Отмена Task отменяет запрос. Ограничить размер ответа; для больших файлов download в
  FileStore и streaming, без обязательного накопления всего тела в памяти.
- Внедряемая сессия, encoder/decoder и часы. Политики авторизации и повторов отделены от
  транспорта; refresh токена объединяется для одновременных 401 и имеет предел повторов.
- Retry только по явной политике с пределом, backoff, jitter и Retry-After. Запись не
  повторяется автоматически без серверной идемпотентности и возможности повторить тело.
- Credentials не уходят при redirect на чужой origin. Логи скрывают токены и тела по
  умолчанию; диагностика возвращается значением/наблюдателю, не через print.
- Reachability — подсказка, не гарантия успеха запроса. Background transfers — отдельный
  режим с платформенной интеграцией и восстановлением задач (сделан, раздел «Background transfers»).

Основа транспорта — [URLSession](https://developer.apple.com/documentation/foundation/urlsession).
Проверки выполняются локальным сервером и fake transport, не публичным API в тестах.

## 9. WebSocket

Основа Apple-адаптера — [URLSessionWebSocketTask](https://developer.apple.com/documentation/foundation/urlsessionwebsockettask).
WebSocketClient владеет соединением; методы connect/send/close и поток сообщений,
отдельно наблюдаемое состояние connecting/connected/reconnecting/closed/failed.

- Один receive-loop на соединение; исходящие сообщения сериализованы. Бинарные и
  текстовые сообщения, лимит размера, bounded buffer. Переполнение сообщает ошибку
  или инициирует resync; молча терять бизнес-события нельзя.
- close/cancel останавливает receive, heartbeat и ожидание reconnect. Поколение соединения
  не позволяет старому callback менять новое соединение.
- Reconnect настраивается: ограниченный backoff с jitter, различие временной ошибки,
  ошибки авторизации и окончательного закрытия. Скрытие экрана само по себе не закрывает
  соединение, принадлежащее аккаунту; уход приложения в фон обрабатывается явно.
- Heartbeat и таймауты по политике сервера. Не обещаем постоянно живой сокет в фоне iOS/tvOS.
- После reconnect транспорт не гарантирует доставку пропущенного или exactly-once.
  Sequence/cursor, подтверждения, дедупликация и resync принадлежат протоколу приложения.
  По умолчанию отправки во время разрыва отклоняются, не копятся в безразмерной очереди.

## 10. Как использовать вместе

Repository — обычный actor приложения, которому передаются database, HTTP и socket.
Для сохраняемых сущностей SQL — источник снимков для UI; HTTP и WS меняют базу, а не
параллельно пишут те же сущности непосредственно в State.

```text
Открытие экрана → подписка на выборку → локальный снимок → State → дерево нод
Обновить → HTTP → проверка версии ответа → SQL-транзакция → новый снимок
WS-событие → дедупликация → SQL-транзакция вместе с cursor → новый снимок
Разрыв WS → reconnect → запрос пропущенного / полный resync → SQL → новый снимок
```

Важные контракты интеграции:

- Старый HTTP-снимок не перезаписывает новое WS-изменение: серверная revision/cursor либо
  последовательный resync. Если сервер не даёт версий, ограничение фиксируется явно.
- Для snapshot + live требуется серверный способ согласовать границу: cursor снимка и
  replay событий либо подписка с буфером и последующее сведение. Без этого есть окно потери.
- Cursor и применённые события сохраняются одной SQL-транзакцией. Повтор события безопасен.
- При logout отменяются задачи аккаунта, подписки и соединение, меняется поколение;
  поздние результаты отбрасываются. Затем закрывается/очищается только его хранилище.
- StateAsyncRay доставляет снимки на MainActor и может объединять промежуточные снимки для
  медленного UI. Поток событий WS так объединять нельзя.
- Фаза загрузки сохраняет предыдущие данные при refresh: idle/loading/loaded/failed,
  ошибка и stale-данные представлены явно. Отмена не показывается как сетевая ошибка.
- Модель владеет Task/подпиской и явно отменяет её. Проверить освобождение модели без
  цикла model → Task → model; очистка не должна зависеть только от deinit.

Последующее расширение — outbox для офлайн-записей: запись сущности и операции в одной
транзакции, устойчивый idempotency key, подтверждение сервером, политика конфликтов.
Это не входит автоматически в простой WebSocket reconnect и ограничено хранением tvOS.

### S0, результаты на 2026-10-01 (GRDB)

Прототип — отдельный пакет вне репозитория: tools 6.0, те же платформы (macOS 14, iOS 16,
tvOS 16), GRDB `exact: "7.11.1"`, один target с миграцией, записью, обновлением и наблюдением.

- **Версия и toolchain.** Тег 7.11.1 существует и собирается при `swift-tools-version: 6.0`
  (установлен Swift 6.4, язык Swift 6). Минимальный toolchain проекта не меняется.
- **Платформы.** Сборка без предупреждений на Mac; сборка и один тест (миграция → пустой снимок →
  вставка → обновление, каждое изменение приходит новым снимком) проходят на iPhone 17 Simulator и

- **Наблюдение.** Перегрузка `ValueObservation.start(in:onError:onChange:)` по умолчанию
  выполняется на главном акторе и в нашей обвязке даёт предупреждение компилятора. Для
  `StorageGRDB` брать `ValueObservation.values(in:)`: это `AsyncSequence`, отмена задачи
  потребителя снимает наблюдение, а ошибка приходит как `throw` из итерации.
- **HTTP и WebSocket (URLSession).** Локальный сервер на `NWListener` (loopback, без сети).
  Проверено на Mac, iPhone 17 и Apple TV 4K Simulator: ответ 200 с телом; 204 без тела; 404 — это
  ответ со статусом, а не ошибка транспорта (статус проверяет наш слой); отмена `Task`
  завершает `data(from:)` с `URLError.cancelled`, и сервер видит закрытие соединения, то есть отмена
  доходит до сокета; WebSocket — три текстовых и одно бинарное сообщение возвращаются эхом в
  порядке отправки, после `cancel(with:)` ожидающий `receive()` завершается ошибкой.
  Обычный `http://` на loopback работает без исключений ATS.
- **Не проверено:** DatabasePool, backup при открытой WAL-базе, поведение на устройстве,
  гонка «отмена у commit», внешний сервер и TLS, обрыв сети посреди передачи, ping/pong и
  таймауты WebSocket, лимит размера сообщения, совместная сборка с остальными целями пакета
  (GRDB пока не в `Package.swift`).

S0 выполнен в объёме прототипа; совместная сборка с основным пакетом проверяется при добавлении
зависимости на S4. Блокирующих ограничений для S1–S6 не найдено.
### S1, результаты на 2026-10-01 (Preferences)

Сделано: `StorageCore` (`PreferenceKey`, `PreferenceValue`, `PreferenceError`, протокол
`PreferenceStore`, `MemoryPreferences`) и `StorageFoundation` (`UserDefaultsPreferences`).
Типизированный слой — расширение протокола, одинаковое на обоих хранилищах.

- Ключи: Bool, Int, Double, String, Data, Date, перечисления по строке и по числу, небольшие
  `Codable`-структуры как JSON (`PreferenceKey.json`). Целое читается как Double, обратное — ошибка.
- Нет значения — умолчание; значение другого типа или неизвестный case — `PreferenceError`, умолчание
  не подставляется; `remove` возвращает к умолчанию. Тип, который хранилище не моделирует (массив от
  чужого кода), — тоже ошибка чтения. Ошибка кодирования ничего не пишет.
- Наблюдение: текущее значение, затем изменения; повторы и «сохранено умолчание поверх пустого»
  не доставляются; ошибка чтения приходит значением, поток продолжается; медленный потребитель получает
  только последнее. Отмена потребителя снимает наблюдателя (проверено по счётчику наблюдателей).
- `UserDefaultsPreferences`: явные `suiteName` и namespace; Bool, число и 3.0 не путаются; изменения чужим
  экземпляром `UserDefaults` того же набора видны (уведомление приходит от того экземпляра, через который
  писали, поэтому подписка — на уведомление любого объекта, затем перечитывание).
- Проверено: 24 теста — Mac (5 прогонов подряд без падений), iPhone 17 Simulator, Apple TV 4K Simulator (tvOS —
  отдельным пакетом из этих таргетов: схема пакета не собирает тесты tvOS, см. #221).
- Не сделано и не проверено: privacy manifest и причина required-reason API для UserDefaults (нужен
  при интеграции в приложение); изменения из другого процесса (App Group); нагрузка и порядок при очень
  частых записях; рабочий пример в демо (S7).

### S2, результаты на 2026-10-02 (FileStore)

Сделано: в `StorageCore` — `FilePath`, `FileError`, `FileMetadata`, `FileEntry`, протокол `FileStore`,
`MemoryFileStore`; в `StorageFoundation` — `DiskFileStore` (с `Location` для каталогов системы) и
перевод ошибок системы в `FileError`.

- **Границы корня.** `FilePath` — только спуск вниз: пустое имя, `.`, `..`, абсолютный путь, NUL и
  имена с точки отвергаются при создании, до любого обращения к диску. Имена с точки зарезервированы
  за временными файлами хранилища. Символьная ссылка в любом имени под корнем даёт
  `outsideRoot`, её не разыменовывают; ссылки не попадают в `list`. Проверка делается в начале
  операции и не защищает от другого процесса, подменяющего каталог во время неё: корень должен быть
  закрыт для других.
- **Запись.** Временный файл рядом с назначением, затем `moveItem` или `replaceItemAt`; при любой
  ошибке и при отмене временный файл удаляется, прежнее содержимое остаётся. Каталоги выше создаются.
  `removeLeftoverTemporaryFiles()` убирает остатки после сбоя; вызывать при запуске, до работы с
  хранилищем.
- **Большие файлы.** `copy` и `importFile(at:to:)` идут кусками (1 МиБ), файл целиком в `Data` не
  читается; предел размера проверяется по мере копирования. Чтение целиком (`read`) и запись `Data`
  по-прежнему держат содержимое в памяти.
- **Исполнитель.** Блокирующая работа — на одной последовательной очереди `utility` у каждого
  хранилища, вне MainActor и вне кооперативного пула. Следствие: операции одного хранилища идут по
  очереди, долгое копирование задерживает остальные; для независимых данных — отдельные хранилища.
  Особый исполнитель actor недоступен: он требует iOS 17, а минимум пакета — iOS 16.
- **Отмена.** Отмена задачи поднимает флаг, который очередь проверяет между кусками и перед заменой
  назначения; не начатая работа не начинается. После замены назначения отмена ничего не откатывает.
- **Ошибки.** `FileError`: неверный путь, выход за корень, нет файла, уже есть, не тот вид (файл/каталог),
  слишком большой, нет места, нет доступа, отмена, прочее с описанием системы. Ошибки POSIX внутри
  Cocoa-ошибки разбираются первыми.
- **Отступления от раздела 5.** Потокового чтения нет: для плееров и загрузчиков изображений —
  `url(for:)`, который сообщает путь и не пускает через ссылку. Перенос (move) файла извне в
  хранилище не сделан — только копирование. «Повреждение» как вид ошибки не введено: для байтов оно
  неразличимо; оно появится у DiskCache и базы (S3, S4). Импорт из document picker, security-scoped URL
  и App Group остаётся расширением платформенных адаптеров.
- **Проверено:** 23 теста в `StorageFoundationTests` (общий контракт на `MemoryFileStore` и
  `DiskFileStore`: запись, замена, чтение, список, удаление, перемещение; ссылки наружу; предел
  размера; копирование 5 МиБ кусками по 64 КиБ; остатки; отмена до начала; нет доступа) и 20 в
  `StorageCoreTests`; Mac; iPhone 17 Simulator (те же тесты); сборка для tvOS Simulator и Mac Catalyst.
- **Не проверено:** тесты на tvOS Simulator и на устройстве; отмена посреди копирования проверяется
  только по инварианту (назначение целое или отсутствует, временных файлов нет), потому что момент
  отмены не детерминирован; расход памяти при копировании гигабайтных файлов (кусок читается без
  `autoreleasepool`); нехватка места на настоящем томе — проверен только перевод кодов ошибок;
  скорость. Прогон на Simulator делался при большой загрузке Mac (load average около 100) и шёл
  медленно; на время тестов это не влияет, но замеров скорости нет.

### S3, результаты на 2026-10-02 (кэши)

Сделано: в `StorageCore` — протокол `Cache`, `CacheLookup`, `CacheError`, `CachePolicy`,
`CacheEvent`, `MemoryCache`, `CachedLoader` и JSON-слой поверх байтов (`get(_:for:)`/`set(_:for:)` для
`Codable`); в `StorageFoundation` — `DiskCache` поверх `FileStore`.

- **Три исхода и ошибка.** `get` различает `hit`, `stale` (срок вышел, значение ещё лежит — его
  можно показать, пока грузится свежее) и `miss`; ошибка хранилища — `CacheError.file`. Значение
  больше предела не записывается: `entryTooLarge`. Значение `Codable`, не расшифровавшееся
  (другая форма), удаляется и считается промахом.
- **Политика.** Предел байтов, срок жизни (общий и на запись), версия формата, правило для
  повреждённой записи: `treatAsMiss` (по умолчанию — удалить, сообщить, ответить промахом) или
  `throwError`. Часы внедряются. При превышении предела уходят сначала просроченные, затем
  наименее недавно использованные; только что записанное не вытесняется.
- **`DiskCache`.** Имя файла — хэш ключа, версия и срок годности, поэтому один `list` даёт индекс
  без чтения файлов; в начале файла — заголовок с ключом и контрольной суммой значения.
  Обрезанный, подменённый или чужой файл — повреждение. Файлы другой версии удаляются при первом
  обращении; чужие имена не трогаются, но `removeAll()` очищает всё хранилище целиком: кэш владеет
  им. Порядок использования хранится в памяти, после перезапуска вытесняется самая старая запись.
  Операции идут по одной (повторный вход actor между `await` не видит половину операции).
  Область пользователя и namespace — отдельные экземпляры кэша со своими хранилищами, а не часть
  ключа; выход из учётной записи — `removeAll()`.
- **`CachedLoader`.** Свежее значение отдаётся сразу; иначе `fetch`. Вызовы с одним ключом делят
  одну загрузку, каждый ждёт независимо: отмена одного бросает ему `CancellationError` и не
  трогает остальных; загрузка отменяется, только когда ждущих не осталось. `invalidate()` отменяет
  все загрузки (их ждущие получают `CancellationError`) и очищает кэш; запись, которую поздний
  результат успел начать, берётся назад. Неудавшаяся загрузка не сохраняется. Устаревшее значение
  здесь считается промахом; показать устаревшее на время загрузки — читать кэш напрямую.
- **Не сделано из раздела 6.** HTTP-кэш (валидаторы, `Vary`, `Cache-Control`) не заменяется:
  это S5, по плану в первой версии `URLCache`. `ImageCache` не тронут — перенос общих частей это S8.
  Ключ не содержит namespace и пользователя отдельными полями (см. выше).
- **Проверено:** 36 тестов в `StorageFoundationTests` и 31 в `StorageCoreTests` (общий контракт на
  `MemoryCache`, `DiskCache` поверх памяти и `DiskCache` поверх настоящего каталога; перезапуск,
  повреждение, обрезанный файл, другая версия, исчезнувший файл, порядок вытеснения после
  перезапуска, 40 параллельных записей; загрузчик: общая загрузка, отмена одного и всех, ошибка,
  очистка во время загрузки, устаревшее). Mac — три прогона подряд; iPhone 17 Simulator — те же
  тесты; сборка для tvOS Simulator и Mac Catalyst. Проверка тестов поломкой: без отмены загрузки
  при уходе всех ждущих падает `cancellingEveryCallerCancelsTheFetchAndStoresNothing`.
- **Не проверено:** тесты на tvOS и на устройстве; поведение при очень большом числе записей
  (`MemoryCache` ищет жертву перебором, `DiskCache` читает весь список файлов при первом
  обращении); нагрузка и скорость; восстановление после остановки процесса посреди записи
  (временный файл `FileStore` убирает `removeLeftoverTemporaryFiles()`, который кэш не вызывает сам);
  очистка кэша системой при нехватке места на живом устройстве; тесты загрузчика ждут по
  опросу и теоретически зависят от тайминга (на Mac и Simulator проходили стабильно).

### S4, результаты на 2026-10-02 (StorageGRDB)

Сделано: цель и продукт `StorageGRDB`, зависимость `GRDB` — `exact: "7.11.1"` в `Package.swift`.
`StorageGRDB` зависит только от GRDB (а не от `StorageCore`, как в таблице раздела 3: общих типов с
другими хранилищами у неё нет); GRDB импортирует только она. Типы: `DatabaseStore` (actor),
`DatabaseLocation`, `DatabaseMigration`, `DatabaseStoreError`.

- **Открытие.** `DatabaseStore.open(_:migrations:)` создаёт каталоги, открывает одну
  `DatabaseQueue`, проверяет историю и прогоняет недостающие миграции; хранилище возвращается только
  с готовой схемой. Миграции именованные, имена уникальны (иначе `duplicateMigration`), порядок —
  как в списке; «стереть базу при смене схемы» GRDB-флагом не доступно. Ошибка миграции даёт
  `migrationFailed(name:)`: сама миграция откатывается, прежние остаются применёнными, данные целы.
  Файл, не являющийся базой, даёт `openFailed` и остаётся байт в байт; пустая база на его месте не
  создаётся. База, в которой применены неизвестные миграции (записана новой версией приложения),
  не открывается: `newerThanApp(unknownMigrations:)`.
- **Чтение и запись.** `read` и `write` отдают замыканию GRDB-овский `Database` и возвращают
  `Sendable`-результат; ошибки замыкания и SQLite идут вызывающему как есть. `write` — одна
  транзакция, любое исключение откатывает её целиком. Параметры SQL передаются отдельно.
- **Отмена.** Проверено на прототипе из раздела 7 и закреплено тестами. Отмена задачи отменяет
  обращение к базе средствами GRDB: пока транзакция не зафиксирована, очередной оператор (включая
  `COMMIT`) бросает `CancellationError`, запись откатывается и вызов бросает; тело замыкания между
  операторами не прерывается. После фиксации запись остаётся и вызов возвращает результат,
  даже если отмена пришла в этот момент (проверяется хуком `afterNextTransaction(onCommit:)`, который
  срабатывает сразу после фиксации). Это поведение GRDB, а не наша обвязка: мой собственный флаг отмены
  оказался лишним — все тесты проходят и без него — поэтому он удалён. Версия GRDB закреплена `exact`, а
  тесты охраняют контракт при обновлении.
- **Наблюдение.** `observe(_:)` возвращает `AsyncStream<Result<Value, DatabaseStoreError>>` с буфером
  «только последнее»: первый снимок, затем по одному после каждого изменившего прочитанное коммита;
  коммит в другую таблицу ничего не даёт; снимок — одно согласованное состояние, не половина
  транзакции (проверено пятью транзакциями по десять строк). Ошибка запроса — элемент-ошибка, затем
  конец потока. Отмена потребителя снимает наблюдение. `AsyncThrowingStream` не используется:
  стандартная библиотека допускает в нём только `any Error`.
- **Закрытие.** `close()` отменяет наблюдения хранилища, ждёт их и закрывает соединение; дальше вызовы
  бросают `closed`; повторное закрытие безвредно.
- **Резервная копия и восстановление.** `backup(to:)` — штатный backup SQLite (`sqlite3_backup`), копия
  делается рядом и перекладывается на место, так что неудачная копия не портит существующий файл;
  записи ждут, пока идёт копирование, и начатую копию отменить нельзя. `restore(from:to:)` сначала
  открывает копию только для чтения и проверяет `PRAGMA integrity_check`; не прошедшая копия отвергается
  и текущая база не тронута; затем удаляются остатки журнала старой базы (`-wal`, `-shm`, `-journal`) и
  файл заменяется. Доступа к файлу ни у кого быть не должно: сначала `close()`; после восстановления
  базу открывают заново, и миграции этой версии применяются к восстановленному.
- **Отступления и ограничения.** Только `DatabaseQueue`: `DatabasePool` нужен при подтверждённой
  потребности в параллельных чтениях (раздел 7). WAL не включается. Своей настройки `Configuration`
  GRDB не выставляем. Шифрование, App Group и несколько процессов, полнотекстовый поиск — позже.
- **Проверено:** 19 тестов `StorageGRDBTests` (миграция вперёд на файле со старой схемой; откат упавшей
  миграции; база новой версии; дубликат имён; файл не база; параметры; откат записи; отмена до начала,
  во время и после фиксации; наблюдение — снимки, согласованность, ошибка, несколько
  наблюдателей, закрытие; backup и restore, замена существующей копии целиком, отказ от плохой копии)
  на Mac; сборка `StorageGRDB` для iOS, tvOS и Mac Catalyst вместе со всеми целями пакета
  (закрывает «совместную сборку» из S0); те же 19 тестов на iPhone 17 Simulator прошли (65 с: Mac был загружен).
  Проверка тестов поломкой, пока своя обвязка отмены ещё была: тест «отмена после фиксации» падал,
  когда вызов бросал `CancellationError` после commit; а тест «отмена во время записи» не падал без моей
  проверки перед commit — так обнаружилось, что это уже делает GRDB.
- **Не проверено:** тесты на tvOS Simulator и устройстве; `DatabasePool`; backup при открытой WAL-базе
  (WAL не включён); нехватка места; большие базы (backup держит запись на время копирования);
  обрыв процесса посреди backup или restore (удаление остатков журнала и замена файла — не одна
  атомарная операция); скорость; наблюдение при очень частых коммитах.

### S5, результаты на 2026-10-02 (HTTPClient)

Сделано: цели и продукты `NetworkCore` (только Foundation) и `NetworkFoundation` (зависит от `NetworkCore`).
Политика — в `NetworkCore` над протоколом `HTTPTransport`, поэтому проверяется с поддельным транспортом;
`NetworkFoundation` — только транспорт на `URLSession`.

- **Типы.** `HTTPMethod` (знает, идемпотентен ли), `HTTPHeaders` (без учёта регистра, повторяющиеся
  имена), `HTTPRequest` (тело — `Data`, чтобы запрос можно было повторить в точности), `HTTPResponse`,
  `HTTPOrigin`, `HTTPError`. Ошибки различают: неверный запрос, кодирование, транспорт (с видом:
  таймаут, обрыв, нет соединения, нет сети, TLS), не-HTTP ответ, слишком большой ответ, статус
  (с целым ответом: тело ошибки сервера нужно), пустой ответ, декодирование, авторизация, отмена.
- **Статусы.** `send` возвращает ответ, только если статус ожидаемый (`.success` по умолчанию; можно
  `.success(or: 404)` или `.only(...)`); иначе `HTTPError.status(response)`. `204` — успех с пустым
  телом; `send(_:as:)` на пустом теле — `emptyResponse`, на неподходящем — `decoding`.
- **Повторы.** `RetryPolicy`: предел попыток, экспоненциальная задержка с потолком и джиттером, список
  статусов (408, 429, 500, 502, 503, 504) и видов сбоя транспорта (таймаут и обрыв). Повторяется
  только идемпотентный метод или запрос с заголовком `Idempotency-Key`; обычный `POST`/`PATCH` не
  повторяется никогда, как бы ни упал. `Retry-After` (секунды или дата) задаёт ожидание, если оно
  длиннее расчётного; больше `maxRetryAfter` — не ждём, ответ возвращается как есть. Отмена не
  повторяется, отмена во время ожидания обрывает его и даёт `cancelled`.
- **Авторизация.** `HTTPAuthorizer` и `TokenAuthorizer`: токен и обновление приносит приложение
  замыканиями (Keychain — его дело). Запрос на чужой origin идёт без токена. На `401` токен
  обновляется один раз и запрос повторяется — для любого метода: отказавший запрос не выполнялся.
  Одновременные `401` делят одно обновление; запрос, подписанный до обновления, не запускает
  второе. Второй `401` после обновления — обычная ошибка статуса. Отказ чужого сервера токен не
  обновляет (найдено при написании тестов: сначала отметка подписи выдавалась и неподписанным запросам).
- **Транспорт `URLSession`.** Тело читается по мере прихода и обрывается, как только превысит лимит;
  ответ, объявивший больший размер, отвергается до чтения тела; для `HEAD` тело не читается.
  Редиректы: следуем; `Authorization`, `Cookie` и `Proxy-Authorization` остаются, пока редирект в
  исходном origin запроса, и срезаются для любого другого; `https` → `http` не следуем; можно
  `.refuse` (вернуть `3xx`). `URLSession` сама срезает `Authorization` при любом редиректе, поэтому
  для своего origin заголовок возвращается. Cookie хранилища сессии не используются: уходят только
  заголовки запроса. Отмена задачи доходит до сокета (сервер видит закрытие).
- **Диагностика.** `HTTPEvent` — метод, URL без запроса и фрагмента, статус, номер попытки, причина
  и задержка повтора; заголовков и тел нет, `print` нет.
- **Не сделано из раздела 8.** Скачивание больших файлов в `FileStore` и потоковое чтение (сейчас
  ответ целиком в памяти до `maxResponseBytes`, по умолчанию 10 МиБ); отправка файла и потока;
  reachability (подсказка, не гарантия); background transfers; `baseURL` у клиента и построитель
  адреса из пути и параметров; кэширование HTTP — только `URLCache` конфигурации сессии.
- **Проверено:** 43 теста `NetworkCoreTests` на поддельном транспорте (статусы, 204, декодирование,
  политика повторов во всех ветвях, `Retry-After`, отмена в ожидании, обновление токена, чужой
  origin, диагностика без секретов) и 19 тестов `NetworkFoundationTests` с настоящим `URLSession`
  против локального сервера на `NWListener` (loopback): статусы, лимит по заголовку и по ходу
  чтения, таймаут, отмена до сокета, отказ в соединении, редиректы в свой и чужой origin,
  `.refuse`, cookie, JSON и повтор через живой сервер. Mac — три прогона подряд; те же 62 теста
  на iPhone 17 Simulator (локальный сервер там работает); сборка для tvOS Simulator и Mac Catalyst.
  Проверка тестов
  поломкой: повтор `POST`, раздельные обновления токена, отметка для чужого origin, лишние
  учётные данные при редиректе, отсутствие лимита и cookie сессии — каждая ловится тестом.
- **Особенность `URLSession`, найденная при проверке:** ответ отдаётся клиенту после первой заметной
  порции тела (порядка килобайт), а не сразу после заголовков; если сервер прислал заголовки и пару
  байт и замолчал, ответ ждёт таймаута запроса. На практике почти не заметно, но защита по
  `Content-Length` срабатывает не мгновенно.
- **Не проверено:** тесты на tvOS и устройстве; настоящий TLS и внешний сервер; `https` → `http`
  (нет `https`-сервера в тестах); обрыв сети посреди передачи; прокси; HTTP/2 и HTTP/3; ответы
  со сжатием и `Transfer-Encoding: chunked` (сервер тестов их не использует); большие тела
  (побайтовое чтение `AsyncBytes` медленнее блочного); скорость.

### S6, результаты на 2026-10-02 (WebSocketClient)

Сделано в `NetworkCore`: `WebSocketClient` (actor), `WebSocketTransport`/`WebSocketConnection`,
`WebSocketMessage`, `WebSocketState`, `WebSocketEvent`, `WebSocketError`, `WebSocketConfiguration`,
`ReconnectPolicy`, `Heartbeat`, `OverflowPolicy`; общий `NetworkEnvironment` (часы, ожидание, случайность)
вынесен из `HTTPClient` — `HTTPClient.Environment` остался псевдонимом. В `NetworkFoundation` —
`URLSessionWebSocketTransport` на `URLSessionWebSocketTask`.

- **Жизнь.** `connect()` запускает цикл подключения; клиент сам держит соединение и заводит новое
  после потери по `ReconnectPolicy`. Остановить можно только `close(code:reason:)`; жизненный цикл
  приложения клиент не наблюдает: кому сокет в фоне не нужен, тот закрывает его при уходе и
  подключает при возврате. Скрытие экрана соединение не закрывает. Клиент держит задачу, а задача —
  клиента, поэтому закрывать нужно явно, одного освобождения недостаточно.
- **Состояние.** `idle`, `connecting`, `connected`, `reconnecting(attempt:after:cause:)`,
  `closed(WebSocketClose)`, `failed(WebSocketError)`; наблюдается `states()` — текущее, затем
  изменения, подряд идущие склеиваются в последнее.
- **События.** Потребитель берёт их по одному `nextEvent()` (или `for await` по `events`) — один
  потребитель, в порядке происхождения: сообщения, `connected(isReconnect:)`,
  `disconnected(cause:willReconnect:)`, `resyncRequired`. Выдача по запросу даёт очереди настоящий
  предел: переполнение — решение, а не потеря.
- **Один цикл чтения, исходящие по одному.** Сообщения приходят в порядке отправки; `send` пишет
  по одному в порядке вызовов и бросает `notConnected`, если соединения нет: ничего не копится
  и не досылается после reconnect — повторять или нет, решает приложение.
- **Переполнение.** `suspendReading` (по умолчанию): чтение из соединения прекращается, пока нет
  места, ничего не теряется, отправителя удерживает управление потоком соединения; `resync`:
  не поместившееся сообщение отбрасывается, потребитель получает `resyncRequired`, соединение
  пересоздаётся — молча ничего не теряется.
- **Поколения.** Каждый запуск имеет номер; всё, что делает запуск после `await`, проверяет, что он
  ещё текущий. Соединение, пришедшее после `close()`, закрывается и не используется; поздний сбой
  старого соединения не трогает новое. Причина окончания соединения фиксируется до его закрытия
  (найдено тестом: иначе ответ чтения «отменено», вызванный самим закрытием, выдавал себя за
  причину, и клиент сдавался вместо переподключения).
- **Переподключение.** Экспоненциальная пауза с потолком и джиттером; счётчик неудач подряд
  сбрасывается, если соединение продержалось `stableAfter` (10 с): сервер, который принимает и
  сразу отбрасывает, не получает шквал. Окончательно, без повторов: отказ учётных данных
  (`401`, `403`) и прочие `4xx`, кроме 408 и 429; сбой TLS; слишком большое сообщение; закрытие
  сервером с кодом из `finalCloseCodes` (1000, 1002, 1003, 1007, 1008, 1009, 1010) — сессия окончена,
  состояние `closed`. Временно: `5xx`, 408, 429, обрыв, таймаут, закрытие с другим кодом (например, 1001).
  Лимит `maxAttempts` (10 по умолчанию) — после него `failed`; `connect()` начинает заново.
- **Heartbeat.** Необязательный: ping раз в `interval`, ответ в пределах `timeout`, иначе соединение
  считается мёртвым и пересоздаётся. Ответ на ping не пришёл — клиент сначала фиксирует причину,
  потом закрывает соединение.
- **Авторизация рукопожатия.** С `HTTPAuthorizer` из S5: подпись ставится на заголовки рукопожатия
  (адрес `ws`/`wss` для сверки origin приравнивается к `http`/`https`); `401` обновляет токен один
  раз и повторяет сразу, без паузы; второй отказ — `failed`.
- **Транспорт.** `URLSessionWebSocketTask`; соединение считается открытым, когда сервер ответил на
  ping после апгрейда, поэтому отказ апгрейда приходит как `handshakeRejected(status:)` с HTTP-статусом.
  Это один лишний круг и требует сервера, отвечающего на ping (так обязан любой сервер WebSocket).
  Закрытие сервером определяется по коду задачи; превышение размера — `messageTooLarge`.
- **Не сделано.** Очередь исходящих на время разрыва (по плану отклоняются); подтверждения,
  дедупликация, курсор и resync протокола — дело приложения (`connected(isReconnect:)` — момент,
  чтобы начать); привязка к жизненному циклу приложения; несколько потребителей одного клиента;
  подпротоколы и расширения; background-режим.
- **Проверено:** 26 тестов `NetworkCoreTests` с подставным соединением (порядок, `send` без соединения,
  размеры, потеря и восстановление, рост и сброс паузы, лимит попыток, разбор отказов рукопожатия,
  закрытие сервером, закрытие клиентом во всех фазах, запоздавшее соединение, запоздавший сбой
  старого, оба вида переполнения, heartbeat, подпись и обновление токена, `states()`, отмена
  потребителя) и 11 тестов `NetworkFoundationTests` с настоящим `URLSession` против сервера на
  `NWProtocolWebSocket` (обмен в обе стороны в порядке, push, заголовки рукопожатия и токен, отказ
  апгрейда `401`, обрыв без close-кадра, close 1001 и 1000, закрытие клиентом, замолчавший
  сервер и ping, слишком большое сообщение, сервер не слушает, неверный адрес). Mac — три прогона
  подряд; те же 99 тестов (с S5) на iPhone 17 Simulator; сборка для tvOS Simulator и Mac Catalyst.
  Проверка тестов поломкой: использование соединения, пришедшего после `close()`;
  повтор после любого кода закрытия; причина окончания, записанная после закрытия — каждая ловится.
- **Не проверено:** тесты на tvOS и устройстве; настоящий TLS (`wss`) и внешний сервер; прокси;
  обрыв сети (Wi-Fi выключен) вместо обрыва соединения; ограничение времени самого рукопожатия —
  его задаёт `HTTPRequest.timeout`, и работает ли оно у `URLSessionWebSocketTask`, не проверено;
  сжатие; фрагментированные сообщения; поведение приостановленного чтения на живом сервере (будет ли
  он отвечать на ping, пока клиент не читает); скорость и большие потоки; уход приложения в фон.

### S7, результаты на 2026-10-02 (DataAsyncRay, SyncDemo)

Сделано: цели и продукты `DataAsyncRay` и `SyncDemo`. Протокол сервера определён здесь, потому что
библиотека не может вывести его из транспорта (раздел 13).

- **`DataAsyncRay`.** Холодные потоки `AsyncRay` над наблюдениями: `DatabaseStore.observeRay`,
  `PreferenceStore.valuesRay(for:)`, `WebSocketClient.statesRay`. Каждая подписка начинает своё
  наблюдение, и отмена подписки (или освобождение `SubscriptionBag`) доходит до него и снимает.
  Ошибка не становится пустым значением: поток несёт `Result`. События `WebSocketClient` потоком не
  отдаются — их берёт ровно один потребитель, по одному и без слияния. Зависит от `StorageCore`,
  `StorageGRDB`, `NetworkCore`, AsyncRay и GRDB (для типа `Database` в замыкании запроса).
- **Протокол демо.** `GET /items` → снимок `{cursor, items}`; `POST /items` (с `Idempotency-Key`) →
  созданный элемент; сокет: клиент после подключения шлёт `{"subscribe", since}`, сервер повторяет
  события со `seq` больше `since` и дальше присылает живые; события пронумерованы без пропусков,
  `revision` элемента растёт при каждом изменении; если нужное уже не хранится — `resync`.
  Так снимок и живой поток согласуются без окна потери (раздел 10). Политика конфликтов — последняя
  запись по `revision`.
- **`ItemsRepository` (actor).** База — единственный источник для экрана: HTTP и сокет пишут только
  в неё. Событие применяется, только если его номер ровно следующий за курсором: меньший — повтор
  и игнорируется, больший — пропуск, и берётся снимок. Курсор и изменение сохраняются одной
  транзакцией. Снимок старше уже сохранённого отбрасывается, поэтому медленный ответ не затирает
  новое изменение. Подписка по сокету идёт после первого снимка (признак `synced` в базе), иначе
  устройство с курсором 0 получало бы лишний снимок. Один `refresh` за раз; вызовы делят результат.
- **Выход из аккаунта.** В базе хранится эпоха; `signOut()` в одной транзакции очищает базу, сбрасывает
  курсор и увеличивает эпоху, затем закрывает сокет и удаляет вложения. Каждая запись, ждавшая сеть,
  проверяет эпоху, с которой началась, и поздний ответ ничего не пишет — даже если отмена до него не
  дошла (отдельный тест вызывает загрузку мимо учёта отмены). Вложение, записанное в файл уже после
  выхода, удаляется.
- **`ItemsModel` (`@MainActor`, `State`).** Строки, фаза (`idle/loading/loaded/failed`), состояние
  соединения, сортировка, последняя проблема. Строки идут из базы, сортировка — из `Preferences`, так
  что изменение в одном окне доходит до всех. Неудачное или отменённое обновление не трогает строки;
  отмена не показывается как ошибка. Подписки держатся слабо, `stop()` снимает их явно, освобождение
  модели от `deinit` не зависит; модель, у которой `stop()` забыли, тоже освобождается. Ошибки на экране —
  словами для человека, а не описания системы.
- **Окна.** Несколько моделей делят один репозиторий и настройки, у каждой свои подписки; закрытие
  одного окна другого не трогает.
- **Вложения.** Лежат в `FileStore` (`attachments/<id>/<имя>`), в базе — имя и размер; переживают
  снимок; уходят вместе с элементом, который сервер удалил. Недопустимое имя — ошибка на экране.
- **Сервер демо `DemoServer`.** Живёт в памяти и реализует те же `HTTPTransport` и `WebSocketTransport`,
  что и настоящие клиенты, без сокетов; умеет обрыв, «нет сети», медленный ответ, потерянный ответ на
  `POST`, внешние изменения от другого пользователя. `DemoSession` собирает всё вместе для приложения.
- **Экран демо `SyncProbe`** (`SYNC_PROBE=1`): список, строка состояния, кнопки обновления, добавления,

### S5, S6, S8: остатки, 2026-10-09

Сделано в `NetworkCore`, `NetworkFoundation`, новой цели `NetworkStorage`, а также в `StorageCore`,
`AppShell` и `NodesRender`.

- **`baseURL` и построитель адреса.** `HTTPClient.baseURL`, `url(for:query:)` и `request(_:_:query:…)`
  (есть вариант с `json:`). Путь дописывается к пути базового адреса; каждый сегмент кодируется
  отдельно, так что пробел или `?` в имени остаются данными; пустые сегменты отбрасываются;
  сегменты `.` и `..` отвергаются, чтобы имя извне не вышло из базового пути. Запрос и фрагмент
  базового адреса не переносятся. Значения запроса кодируются строго: без кодирования остаются
  только `A–Z a–z 0–9 - . _ ~`, поэтому `+` и `&` в значении — данные. Базовый адрес не
  решает, кому уходят учётные данные: это по-прежнему origin запроса.
- **Скачивание в файл.** `HTTPClient.download(_:to:expecting:maxBytes:)` и требование
  `HTTPTransport.download`. Транспорт пишет тело `2xx` в новый файл, а клиент ставит файл на место
  назначения (с заменой, создавая каталоги выше) **только когда ответ принят**; пока ответ не принят,
  после любого сбоя и при отмене место назначения не тронуто и временных файлов нет. Попытка,
  которую клиент не принял или повторил, удаляет свой файл. Ответ не `2xx` в файл не пишется: его
  тело, обрезанное до 64 КиБ, возвращается в памяти, как у `send`. Предел по умолчанию не задан —
  скачивание нужно ровно для того, что не лезет в `maxResponseBytes`; пределом тогда служит диск.
  Реализация по умолчанию в протоколе читает всё тело в память и записывает его: поддельный
  транспорт тестов работает без изменений, а `URLSessionTransport` переопределяет метод.
- **Транспорт `URLSession`.** `TransferDelegate` на задаче данных: ответ решает судьбу тела (файл,
  память или отказ), куски пишутся на диск по мере прихода, размер проверяется по объявленному
  `Content-Length` до первого байта и по записанным байтам после; при превышении, ошибке записи
  и отмене соединение обрывается, файл удаляется. Правила редиректа (credentials только своему
  origin, `https` → `http` не следуем) вынесены в `RedirectRules` и общие с `send`.
  `URLSessionTransport(downloadDirectory:)` задаёт каталог файлов скачивания.
- **Отправка файла.** `HTTPClient.upload(_:fromFile:expecting:)` и `HTTPTransport.upload`: тело — файл,
  `body` запроса игнорируется. Система читает файл по мере отправки; ответ собирается в памяти до
  `maxResponseBytes`. Повтор читает файл заново, а допустим он по тем же правилам, что и для
  обычного запроса: `PUT` повторяется, `POST` нет. Нечитаемый файл — `HTTPError.fileSystem`
  до отправки.
- **Общий цикл.** Попытки, повторы, `Retry-After` и обновление токена вынесены из `send` в один
  `perform`, которым пользуются `send`, `download` и `upload`; поведение `send` не менялось
  (все прежние тесты проходят).
- **Скачивание в `FileStore`.** Новая цель `NetworkStorage` (зависит от `NetworkCore` и `StorageCore`):
  `HTTPClient.download(_:into:at:…)` скачивает во временный файл и передаёт его хранилищу через
  `FileStore.importFile(at:to:)`, который теперь требование протокола (у `MemoryFileStore` — чтение
  и запись, у `DiskFileStore` — копирование кусками, как было). Лимит размера и замена целиком —
  гарантии хранилища, а не клиента. Ошибки различаются: `DownloadError.http` и `.file`.
- **Пауза WebSocket.** `WebSocketClient.suspend()`, `resume()` и состояние `suspended`. Пауза
  закрывает соединение кодом 1001, сообщает `disconnected(cause: nil, willReconnect: false)`,
  останавливает переподключение и **не заканчивает** поток событий: потребитель продолжает ждать.
  Накопленные сообщения остаются в очереди. `resume()` (или `connect()`) подключает заново, и
  `connected(isReconnect: true)` говорит о возможно пропущенном. Пауза у клиента, который не
  запущен, закрыт или сдался, ничего не меняет, поэтому возвращение приложения на передний план
  не оживляет намеренно закрытый клиент. Читатель, ждущий места в очереди, при паузе
  освобождается: иначе его прогон не заканчивался бы.
- **Привязка к приложению.** `WebSocketClient.follow(_:)` ведёт клиента по последовательности
  `Bool`, а `Shell.activations()` отдаёт активацию приложения (`active`, `inactive`, `background`)
  как `AsyncStream` без повторов. Вместе: `await socket.follow(shell.activations().map { $0 != .background })`
  в отдельной задаче. Платформенных уведомлений клиент по-прежнему не слушает; `inactive`
  (окно показано без ввода) соединение не закрывает.
- **S8.** Из `ImageCache` вынесено то, что не связано с картинками: разбор свежести и валидаторов
  ответа (`Cache-Control: no-store`/`no-cache`/`max-age`, `Age`, `Expires`, `ETag`, `Last-Modified`)

### Остатки сети, 2026-10-09 (второй проход)

Сделано в `NetworkCore` и `NetworkFoundation`: `baseURL` у `WebSocketClient`, отправка потока, докачка по `Range`,
reachability. Background transfers в этом проходе не были сделаны (причина ниже); сделаны в третьем.

- **`baseURL` у `WebSocketClient`.** `init(baseURL:path:query:headers:transport:…) throws(HTTPError)`: адрес строится
  тем же построителем, что у `HTTPClient` (сегменты кодируются по одному, `.` и `..` отвергаются, запрос базового адреса
  отбрасывается, значения запроса кодируются строго), но основа может быть `ws`, `wss`, `http` или `https`.
  Построитель вынесен из `HTTPClient.url(for:)`: у того прежняя проверка «только `http`/`https`».
- **Отправка потока.** `HTTPBodyStream` (длина, если известна, и фабрика `InputStream`), `HTTPClient.upload(_:from:)` и
  требование `HTTPTransport.upload(_:from:maxResponseBytes:)`. **Фабрику вызывают заново на каждую попытку и каждый
  повтор тела при редиректе**, поэтому поток обязан уметь начаться сначала: открыть файл ещё раз, пустить генератор ещё раз.
  Читаемый один раз поток здесь не годится — такому запросу место с методом, который не повторяется. Известная длина даёт
  `Content-Length`, неизвестная — отправку кусками (`Transfer-Encoding: chunked`). Фабрика, бросившая ошибку, останавливает
  запрос с `HTTPError.fileSystem(underlying:)`. Реализация `URLSession`: `uploadTask(withStreamedRequest:)` и
  делегат `needNewBodyStream`. **Особенность:** async-вариант метода делегата система не вызывает (запрос кончался как
  отменённый), работает только вариант с обработчиком завершения. Готовые потоки: `HTTPBodyStream.data(_:)` и `.file(at:)`.
  Реализация протокола по умолчанию читает поток в память (`readAll()`).
- **Докачка по `Range`.** `PartialDownload` (файл и рядом запись с `.validators`) и параметр `continuing:` у
  `HTTPClient.download`. Запись — валидаторы ответа (`ETag`, `Last-Modified`); **их пишет транспорт в момент ответа**, до первого
  байта тела, потому что оборвавшийся запрос ответа клиенту уже не вернёт. Продолжение: `Range: bytes=N-` и
  `If-Range` (сильный `ETag`, а слабый `W/"…"` в `If-Range` нельзя — тогда `Last-Modified`; нет подходящего валидатора или
  записи — докачки нет и файл начинается заново). Ответ `206`, начало которого равно размеру файла, дописывается;
  любой другой `2xx` (сервер не поддерживает диапазон или вещь изменилась) начинает файл сначала, поэтому смеси двух
  версий не бывает; `206` с другого места отвергается как `HTTPError.status` до записи байта. Файл и запись **остаются** при
  обрыве и при отмене; повтор внутри одного вызова (`RetryPolicy`) продолжает с места обрыва сам. `416`: если размер файла равен
  размеру вещи из `Content-Range: bytes */N`, файл считается целым (результат — ответ `416`, `file` — `destination`), иначе файл
  выбрасывается и вещь скачивается заново целиком. Превышение `maxBytes` (на весь файл) выбрасывает и файл. По окончании
  файл переносится на `destination`, запись удаляется. Транспортное требование теперь
  `download(_:maxBytes:partial:)`; прежняя двухаргументная форма осталась расширением.
- **Reachability.** `NetworkPath` (маршрут есть / нет / нужно подключение, дорогой, ограничен) и `NetworkPathMonitoring`;
  `SystemNetworkPathMonitor` на `NWPathMonitor` (на каждый вызов `paths()` свой монитор, отмена потока его снимает).
  Это подсказка, а не гарантия, и отказ от запроса по ней не делается. Применено в одном месте:
  `WebSocketClient.reconnectNow()` кончает ожидание перед следующей попыткой (оно стало задачей, которую можно
  завершить; закрытие клиента отличается от «разбудили» по флагу), а `reconnectWhenReachable(_:)` вызывает его на каждый
  достижимый путь. Счётчик неудач подряд не сбрасывается: сервер, который отказывает, всё равно будет оставлен на пределе
  попыток.
- **Background transfers не сделаны.** Это сессия `URLSessionConfiguration.background`, которая живёт, пока приложение не
  запущено, и доставляет результат делегату при его повторном запуске (`handleEventsForBackgroundURLSession`).
  Для этого нужна связка с жизненным циклом приложения (точка входа, хранение идентификаторов задач, восстановление
  делегата), а проверить её можно только на живой системе с настоящим перезапуском приложения. Начинать без этой проверки
  значило бы написать код, о котором нельзя сказать, работает ли он.
- **Проверено** (Mac, `swift test` с фильтром): `NetworkCoreTests` 121 тест (в них новых 17: адрес сокета, поток по умолчанию,
  `PartialDownload`, `Content-Range`, докачка на подставном транспорте, ожидание и пробуждение, путь);
  `NetworkFoundationTests` 60 тестов (новых 15: поток известной и неизвестной длины с разбором `chunked` в тестовом сервере, повтор
  с новым потоком, фабрика-ошибка, файл как поток; обрыв и докачка, повтор внутри вызова, изменившаяся вещь, байты без
  записи, `416` целого и лишнего файла, чужой `206`, предел на весь файл, отмена; монитор пути). Проверка поломкой: без хранения
  файла при обрыве, с дозаписью при `200`, без `If-Range`, с приёмом чужого `206` и без различения «разбудили» — каждая ловится.
  Один старый тест паузы WebSocket (`messagesQueuedBeforeASuspendAreStillDelivered`) упал при параллельном запуске: он ждал, пока
  соединение отдаст сообщения читателю, а доставка в очередь идёт чуть позже, и `suspend()` по документации может потерять
  сообщение «в полёте». Тесту дано время; сам метод не менялся. Сборка `NetworkFoundation` для iOS Simulator, tvOS Simulator
  и Mac Catalyst проходит.
- **Не проверено.** Всё это на iOS Simulator, tvOS и устройстве; докачка на настоящем сервере с `Range` в сети (проверен локальный);
  докачка гигабайтных файлов; сервер, у которого `ETag` слабый или нет валидаторов вовсе, кроме случая в тестах;
  `SystemNetworkPathMonitor` при настоящем переключении сети (проверено только первое значение); поток, фабрика которого
  открывает сетевой источник.

### Background transfers, 2026-10-09 (третий проход)

Сделано: передачи, которые идут, пока приложение не запущено, и результат которых ждёт его при следующем запуске.
`NetworkCore/BackgroundTransfers.swift` (типы и протокол), `NetworkFoundation/URLSessionBackgroundTransfers.swift` (актор поверх
`URLSessionConfiguration.background`), `BackgroundTransferRecords.swift` (метка задачи и записи), `Shell.backgroundSessionHandler`
в `AppShell` и `application(_:handleEventsForBackgroundURLSession:)` в `AppShellUIKit`.

- **Что отдаётся системе.** `download(_:to:id:)` — запрос без тела, файл после скачивания кладётся в `directory/<path>`
  (путь относительный, `..`, абсолютный путь и папка записей отвергаются как `invalidRequest`; существующий файл заменяется);
  `upload(_:fromFile:id:)` — файл как тело, ответ сохраняется в результате (предел `maxReplyBytes`, по умолчанию 1 МиБ,
  больший ответ — `responseTooLarge`). Потока и тела в памяти здесь нет: система читает файл тогда, когда отправляет.
- **Чего приложение лишается.** Повторов и обновления токена: запрос подписывается один раз при постановке
  (`HTTPClient.download(_:inBackground:to:id:)` кладёт заголовки по умолчанию и подпись `HTTPAuthorizer`), а система отправит его
  через часы, когда от приложения ничего не запущено. Токен, истёкший к тому времени, вернётся как `401` в результате, и
  приложение ставит передачу заново. Докачки тоже нет: скачивание всегда новый файл. Переадресации система выполняет сама, пока
  приложения нет; пока оно запущено, действует то же правило, что у `URLSessionTransport`: учётные данные только своему origin.
- **Метка в самой задаче.** Всё, что нужно после перезапуска (имя, вид, куда класть файл), лежит в `taskDescription` задачи в
  виде JSON; система хранит его вместе с задачей. В памяти о передаче ничего нет, поэтому делегат ведёт себя одинаково в первом
  запуске и после перезапуска. Задачи без метки (чужие) не трогаются.
- **Результат записывается раньше, чем кто-то его ждёт.** Делегат пишет файл-запись `directory/.background-transfers/<имя>.json`
  в тот момент, когда пришёл результат, и только потом сообщает слушателям. `outcomes()` сначала отдаёт все записи, ещё не
  подтверждённые, потом новые; чтение записей и подписка делаются под одной блокировкой с записью, поэтому результат не
  теряется и не приходит дважды. Доставка «хотя бы раз»: `acknowledge(_:)` удаляет запись, до этого она приходит при каждом
  запуске. Файл в записи хранится относительным путём, потому что абсолютный путь контейнера приложения меняется при обновлении.
  Нечитаемая запись пропускается и не прячет остальные.
- **Имя передачи.** Передача под именем, которое ещё идёт или чей результат не подтверждён, второй раз не запускается
  (одновременные вызовы тоже, актор не даёт им разойтись): приложение может на каждом запуске говорить «убедись, что файл
  скачан», и не качает его на каждом запуске.
- **Системное завершение.** Для iOS `Shell.backgroundSessionHandler` получает идентификатор сессии и завершение; приложение
  передаёт его в `finishingEvents(_:)`, который вызывает его на главном акторе, когда делегат получил
  `urlSessionDidFinishEvents`. Вызов, пришедший до установки обработчика, ждёт его; если события доставлены раньше, чем
  завершение передали, оно вызывается сразу. Сессию нужно создать при запуске приложения, до любой сцены (в демо — в `init`
  приложения), иначе при запуске в фоне без окна события никому не достанутся.
- **Особенности системы, найденные при работе** (проверены в тестах на Mac):
  - система держит одну сессию на идентификатор; второй объект с тем же идентификатором в том же процессе не получает ничего,
    поэтому объект один на идентификатор, на всё время работы приложения. `deinit` вызывает `finishTasksAndInvalidate()`;
  - фоновая передача не падает, когда сервера нет или сети нет: она ждёт его до `timeoutIntervalForResource` (неделя по
    умолчанию). Параметр `timeout` объекта задаёт этот срок; по истечении результат — `timedOut`;
  - система сама запускает приложение в фоне, когда передача кончилась, пока приложения не было; запуск из теста в этот момент
    может упасть («Simulator device failed to launch»), поэтому в UI-тесте перед вторым запуском пауза (дефект #223);
  - имя передачи занято любой задачей с такой меткой, и отменяемой тоже: у отмены есть результат, и до его подтверждения имя не
    свободно (#222, остаётся узкое окно);
  - ответ загрузки (`uploadTask`) приходит через `didReceive data` обычного делегата, а не в файле;
  - файл скачивания система удаляет по выходе из `didFinishDownloadingTo`, поэтому его переносят, а тело отказа читают до выхода.
- **Проверено на Mac** (`swift test`). Два набора. `BackgroundTransferDelegateTests` — 18 тестов без системного демона: делегат
  вызывается руками (для этого `downloaded`, `replyReceived` и `completed` вынесены из методов `URLSession` и принимают
  ответ значением): скачанный файл ложится на место и заменяет прежний; отказ — без файла, с телом, обрезанным по
  `errorBodyLimit`; файл, который нельзя положить (на месте папки файл), — `fileSystem`; ответ загрузки собирается из кусков, а
  превышение предела останавливает задачу, и причина — не «отменено»; семь видов ошибок системы; ни ответа, ни ошибки — сбой;
  записи отдаются новому слушателю от старых к новым, переживают делегата (новый делегат над той же папкой), нечитаемая запись
  не прячет остальные; **500 результатов приходят с разных потоков, пока подключается слушатель, — ни один не потерян и не
  повторён**; ход передачи под именем; чужая задача не трогается; проверка пути и запроса; системное завершение до событий,
  после них и после нового результата. `BackgroundSystemTests` — 9 тестов через настоящий демон (`@Suite(.serialized)`, одна общая
  сессия `tests.background.shared`, имена передач разные): скачивание, отказ 404, нет сервера и срок, отправка файла, одно
  имя — одна передача и свободное имя после подтверждения, отмена, ход, подпись клиента, переадресация на чужой origin без
  учётных данных. `AppShellTests` — 2 теста на `backgroundSessionHandler`. Проверка поломкой (ломали, видели падение, возвращали):
  без переноса файла, без проверки записи при постановке, без защиты от повторной постановки, без проверки пути, без отдачи
  записей новому слушателю, без сброса «события доставлены» при новом результате, с записью вне блокировки слушателей (тест на
  500 результатов падает не при каждом прогоне: гонка вероятностная) и с ошибкой системы раньше нашей причины.
  **Демон как среда.** Первое обращение процесса тестов к системному демону может занять до 20 секунд, а после долгой серии
  прогонов демон отвечал на часть задач дольше минуты. Причина не установлена (#224); подозревались задачи прошлых прогонов, которые
  остаются у демона до недели (сервер ушёл, задача ждёт его): поэтому набор делит одну сессию с постоянным именем, а первое
  использование отменяет то, что осталось от прошлого прогона, и тесты с отдельной сессией тоже берут постоянное имя. Сессии,
  названные UUID в первых прогонах, из демона убрать нельзя. Логика проверяется набором без демона, поэтому его настроение
  ей не мешает.
- **Проверено на iOS Simulator с настоящим перезапуском** (`BackgroundRelaunchTests`, схема `LayoutDemoiOS`): первый запуск
  ставит скачивание и завершается, пока сервер ещё не ответил (сервер живёт в процессе теста и отвечает через 8 с);
  сервер отвечает, приложения нет; второй запуск получает результат `200`, 200000 байт, файл на месте; третий получает его снова
  (подтверждения не было); после `Acknowledge` четвёртый запуск не получает ничего. Четыре прогона подряд прошли (последний — после выноса методов делегата); один из первых пяти упал по причине, которая не установлена (#223, открыт). Сборка пакета для iOS Simulator, tvOS Simulator
  и Mac Catalyst и трёх демо (iOS, tvOS, Mac) проходит.
- **Не проверено.** Реальное устройство (политика энергопотребления, `isDiscretionary`, мобильная сеть, «Фоновое обновление»
  выключено пользователем, принудительное закрытие приложения из переключателя: после него система не запускает приложение,
  пока пользователь не откроет его сам — это правило системы, не код); запуск приложения самой системой в фоне по окончании
  передачи (в тесте приложение запускает тест, а не система); tvOS (сборка проходит, но фоновая загрузка там зависит от
  системы, и проверка не делалась); `sharedContainerIdentifier` с расширением приложения; Mac (`AppShellAppKit` не получает
  вызова — macOS запускает приложение без него, сессию нужно создавать при запуске, как и на iOS); большие файлы и передачи,
  идущие часы.

## 14. Уточнение: роль AsyncRay — 2026-09-29

После вопроса пользователя просмотрены локальные README, Package.swift, реализации
AsyncStream-моста, SharedAsyncRay, Pipe, операторов времени и существующий StateAsyncRay
в этом пакете. AsyncRay уже подключён; полезно использовать его для композиции данных,
не создавать параллельную систему подписок StateData. Это уточняет первоначальную таблицу.

### Где используем

| Сценарий | Механизм |
|---|---|
| SQL-выборка → UI | Наблюдение GRDB → адаптер в AsyncRay → существующий bind(to:) |
| Поиск при вводе | State.asyncRay → distinct/debounce → flatMapLatest с явным буфером → результат в State |
| Данные + сортировка + фильтры | combineLatest со снимками настроек и данных; вычисления вне MainActor |
| Состояние подключения | CurrentValueDistinct для актуального состояния и новых подписчиков |
| События после разбора протокола | Pipe с выбранной политикой и проверкой переполнения |
| Жизненный цикл экрана | SubscriptionBag; cancelAll при завершении выбранного срока жизни |

Одноразовые HTTP-запросы и SQL-записи остаются async throws. AsyncRay-обёртка добавляется
для композиции, не становится обязательным способом каждого чтения файла. Хранилища
сами не зависят от AsyncRay; тонкие мосты находятся в DataAsyncRay. StateCore остаётся
источником синхронного UI-состояния, CurrentValue не заменяет его отслеживание чтений.

### Контракты, которые необходимо сохранить

1. **Ошибки передаются явно.** AsyncRay<T> построен на AsyncStream и не имеет failure
   channel. Адаптер throwing-наблюдения передаёт Result либо отдельный Sendable enum
   состояния: snapshot/failed. Ошибка не превращается в пустой список или обычное
   завершение. `.throwingStream` не создаёт отсутствующий канал ошибок; `.timeout`
   завершает поток, поэтому сетевой timeout должен формировать явную ошибку транспорта.
2. **Снимки и события различаются.** Для снимка UI допустим bufferingNewest(1).
   Bounded buffer не означает backpressure с ожиданием: Pipe может отбрасывать значения;
   sendObservingOverflow позволяет увидеть это. Применение SQL-событий выполняется
   последовательным receive-loop до публикации снимка. При потере события нужен resync.
3. **Холодный поток запускается на каждую подписку.** Нельзя случайно открыть отдельный
   сокет или повторить HTTP-запись для каждого окна. Общим соединением владеет сервис,
   подписчики получают его опубликованные данные. Сырой WS-поток не направляем в
   конкурентные merge/flatMap до разбора, проверки порядка и применения транзакции.
4. **Мост asAsyncRay одноразовый.** После окончания upstream или ухода последнего
   подписчика SharedAsyncRay становится terminal. Возвращение на экран требует новой
   фабрики наблюдения либо живущего дольше сервиса с актуальным снимком, а не повторного
   использования завершённого моста.
5. **Отмена подписки должна доходить до ресурса.** Адаптер регистрирует cleanup SQL-
   наблюдения/задачи. Освобождение отдельного Subscription не отменяет его автоматически;
   используем bag или cancel. Не захватываем модель сильно в удерживаемой ею подписке.
6. **flatMapLatest подходит для поиска, не для записей.** Переключение отбрасывает старую
   выдачу, но не откатывает уже совершённый серверный эффект или SQL commit.

### Версия и проверка

`1f7f192f2abb628b48b7b29df45454535c056a23`. Локальная библиотека при просмотре —

## 15. План AsyncRay 1.1.0: потоки с ошибками

**Статус: запланированный релиз, не выпущен и не подключён.** 2026-09-29 пользователь
уточнил, что AsyncRay — его библиотека и её можно развивать для этой интеграции.
Целевая версия — **1.1.0**, если изменения остаются аддитивными и проходят проверки
совместимости. Ломающие изменения существующих типов или поведения требуют отдельного
решения о 2.0.0. Этот документ не создаёт тег, не публикует пакет и не меняет dependency.

### Решение по API

Сохранить `AsyncRay<Value>` как поток без ошибок. Добавить отдельный
`AsyncThrowingRay<Value: Sendable>` на основе фабрики `AsyncThrowingStream<Value, Error>`.
Оба типа поддерживают AsyncSequence; throwing-вариант потребляется через `for try await`.
В первой версии не вводить обязательный второй generic-параметр Failure: доменные ошибки
остаются конкретными Error-типами, которые можно распознать и преобразовать на границе.

Это эскиз API; точные сигнатуры проверяются в репозитории AsyncRay:

```swift
// Фабрика создаёт новую операцию на каждую подписку.
let request = AsyncThrowingRay<Response>.task {
    try await api.load()
}

let subscription = request.sinkOnMain(
    next: { response in /* обновить модель */ },
    completed: { /* нормальное завершение */ },
    failed: { error in /* показать ошибку */ }
)
subscription.store(in: bag)
```

Обязательный объём 1.1.0:

- Холодная фабрика throwing-потока и одноразовой `async throws` операции. Каждая подписка
  владеет своей задачей и очисткой. Оборачивание одного уже созданного stream не выдаётся
  за перезапускаемую фабрику; для retry нужен именно новый producer.
- Throwing emitter: send, finish, finish(throwing:), регистрация cleanup. Завершение,
  ошибка и отмена конкурируют за единственный терминальный переход; cleanup каждого
  обработчика вызывается ровно один раз, включая позднюю регистрацию после await.
- `sink`/`sinkOnMain` с явной обработкой ошибки, существующие Subscription и SubscriptionBag.
  Ошибка не вызывает completed. Отмена подписки не вызывает failed и останавливает новые
  доставки; уже исполняющийся callback не откатывается. Итерация сохраняет стандартную
  семантику отмены AsyncThrowingStream, не обещает обязательный throw при отмене потребителя.
- Мост из throwing-фабрики/наблюдения без потери исходной ошибки. Нормальный finish и
  finish(throwing:) доставляются после уже принятых буфером значений; отмена может
  прекратить доставку раньше. При upstream CancellationError учитывать контекст:
  собственная отмена подписки — cancellation, ошибка активного источника — failure.
- map/filter для throwing-потоков, tryMap из обычного потока, flatMapLatest с throwing
  inner-потоком. Ошибка активного inner завершает результирующую подписку и отменяет
  outer/inner; поздняя ошибка уже заменённого inner не завершает новый поток.
- Явное восстановление через catch/recover с новым потоком и materialize в обычный
  AsyncRay событий value/finished/failed. Терминальное событие materialize нельзя потерять
  из-за политики dropping; это отдельный контракт реализации и теста. Для UI допустим
  более простой адаптер в снимок состояния с error и предыдущими данными.
- Throwing timeout с отдельной ошибкой и отменой upstream. Определить его как idle timeout,
  сбрасываемый каждым значением; deadline всей операции — другая настройка. Существующий
  timeout у AsyncRay не менять молча: он сохраняет прежнее завершение без ошибки.
- Явная/унаследованная политика буфера на каждом операторе. Не называть dropping-buffer
  гарантией backpressure. Терминальная ошибка хранится вне очереди обычных значений и
  не исчезает при переполнении. Для событий протокола остаётся последовательный обработчик.

Автоматический retry не обязателен для 1.1.0. Его политика остаётся у HTTP/WS-сервиса:
идемпотентность, повторяемое тело, предел попыток и reconnect нельзя вывести из Error.
Новые merge/combineLatest/zip с ошибками можно добавить следующим релизом после определения
их завершения и отмены; не переносить весь набор операторов ради первой интеграции.

### Изменения интеграции в этом пакете

- `DataAsyncRay`: GRDB observation → AsyncThrowingRay со снятием наблюдения при отмене;
  HTTP async throws → холодная операция. Библиотека AsyncRay не импортирует GRDB/URLSession.
- `StateAsyncRay`: новый overload привязки throwing-потока к состоянию с обязательным
  onError либо к явному состоянию загрузки. Не оставлять ошибку необработанной и не
  заменять сохранённые данные пустым значением. Старый bind(to:) остаётся совместимым.
- WebSocket сохраняет владельца соединения и последовательный receive-loop. После
  исчерпания политики восстановления failure завершает поток; для новой попытки создаётся
  новая подписка. Не создавать соединение на каждую подписку UI случайно.
- До выхода 1.1.0 применим описанный в разделе 14 Result/enum-адаптер поверх AsyncRay 1.0.0.
  После обновления он остаётся полезен для бизнес-состояний и восстанавливаемых ошибок;
  настоящие терминальные ошибки операций идут через AsyncThrowingRay.

Проверки: Swift strict concurrency, Linux и Apple-цели; холодные независимые подписки,
ошибка до первого значения и после значений, заполненный буфер, порядок termination,
throw из tryMap, recovery, idle timeout, cancellation во время регистрации и отсутствие
утечек ресурсов. Тесты существующего AsyncRay обязательны как защита от регрессий.

S0 включает R0 и минимальный R1-прототип; S7 использует R3. Релиз R4 и обновление
Package.swift/Package.resolved — отдельный шаг после проверок, не замена номера версии
на несуществующий тег. Реализация storage/HTTP на async throws может идти до R4.
