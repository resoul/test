# Trellis — план реализации: простая запись анимации

Статус: переработанный проект для обсуждения, 2026-09-12. D61–D74 ниже —
предложения взамен предыдущей редакции, не принятые решения. Код не реализован.
Общий порядок текста и анимации находится в
[плане 4, §4](implementation-plan-4.md#4-порядок-и-зависимости).

## 1. Сначала сценарий и запись

Цель всего плана: сложные повторяемые переходы должны иметь простую запись.
Референс пользователя — четыре кадра App Store: карточка в ленте, открытая
страница и уменьшенная страница поверх фона. Кадры показывают состояния, но
не доказывают timing, физику или управление жестом. Закрытие пальцем ниже —
предлагаемая обязательная возможность Trellis, не утверждение о записи референса.

План имеет два обязательных результата: A — анимация свойств (M01–M08),
B — переиспользуемый переход «карточка → страница → обратно» (M10–M14),
включая отменяемое закрытие жестом. M09 (spring) остаётся отдельным расширением.
Закрытие результата A не означает достижения цели всего плана.
**Результат A (M01–M08) и результат B (M10–M14) оба закрыты** — цель плана достигнута;
[m14-close-result-b.md](validation/m14-close-result-b.md) закрывает результат B, не весь
navigation backlog N07 (§7).

Сценарий результата A: список карточек с настоящим текстом. Нажатие раскрывает
описание, увеличивает карточку и сдвигает соседние. Повторное нажатие в середине
движения меняет цель без скачка. Смена цвета работает без layout. Это первая
часть N07. Результат B добавляет presentation одной страницы в пределах одного
хоста; универсальный navigation stack и application integration не входят.

Предлагаемый API, ещё не существующий в пакете:

```swift
list.animate(.smooth) {
    description.maxLines = expanded ? nil : 2
    card.style.height = expandedHeight
}

card.animate(.easeOut(duration: .milliseconds(180))) {
    card.style.visual.opacity = 0.5
}

card.animate(.none) {
    card.style.visual.opacity = 1
}
```

Автор задаёт **область движения, новые значения и характер движения**. `card`
охватывает карточку и потомков; `list` — также соседей, перемещённых раскладкой.
Поэтому раскрытие в списке использует `list.animate`, даже если меняется только
описание. Новые значения записываются сразу, переход начинается при актуальном
коммите. Возвращаемое значение — `Void`, closure синхронный, `@MainActor`, без
`await`. `animate` использует batching существующего `InvalidationTransaction`.

Для результата A одна точка входа — `Node.animate`. Статический `Transaction.animate`, глобальный
контекст, постоянные modifiers на нодах и отдельный публичный animator не нужны
первому сценарию. Несколько хостов вызываются отдельно, без обещания синхронного
кадра между окнами.

`.smooth` — обычная ease-in-out длительностью 250 ms; `.none` — явный мгновенный
переход. Точные имена закрепляет M01 внешним consumer-примером. Пружина следует
отдельным M09 с тем же способом записи, только после работающей основы.

Для результата B нужен второй уровень: готовый переход с внутренним владельцем
жизненного цикла. Желаемая запись (псевдокод, имена и владелец `present` уточняются M10):

```swift
present(details, transition: .expand(from: card))
```

Простой случай использует весь card как источник; сложный связывает изображение,
заголовок и полосу иконок через локальные роли перехода. Автор описывает два
состояния и соответствия один раз. Геометрию, временные слои, общий progress,
закрытие и отмену жеста обслуживает система. Готовый `.expand` строится поверх
того же механизма, который доступен для собственной композиции, без отдельных
реализаций для каждой страницы.

## 2. Что именно упрощаем

Лёгкость оценивается и по записи, и по стоимости исполнения:

- Обычная сцена не знает о слоях, animation keys, revisions и отмене.
- Layout считает конечную геометрию один раз на актуальное изменение; растр
  строится для конечного размера. Solver и CoreText не запускаются каждый кадр.
- Автоматические кадры интерполирует Core Animation. Trellis хранит только намерение и небольшой
  набор активных переходов. Собственного display-link и физического движка нет. Во время жеста renderer
  применяет progress от входных событий к подготовленному переходу, без solve/raster
  на каждое событие; после отпускания продолжает автоматическое движение.
- Результат A имеет узкий набор свойств и проверенное прерывание. Completion,
  delay, sequences, keyframes и уход ноды не входят в её обязательный API.
- Обычный коммит не создаёт animation objects и не читает presentation у всех
  слоёв. Отдельно измеряем стоимость diff, обходов и хранения активных переходов.

Предыдущий план предлагал включать implicit actions для всего коммита. Это
короткая реализация, но она связывает независимые изменения одним timing и
усложняет адресную отмену. Предлагаем явные `CABasicAnimation` для небольшой
таблицы поддерживаемых свойств при постоянно выключенных implicit actions.
Core Animation допускает отдельные анимации свойств; ограничение «одна анимация
на весь коммит» было выбором прежнего плана, а не ограничением платформы.

## 3. Контракты до реализации

### D61. Модель и границы первой версии

`Animation` — `Sendable, Hashable` value-тип в Core: `.none`, timing с `Duration`
и кривыми linear/easeIn/easeOut/easeInOut, preset `.smooth`. Duration <= 0
означает `.none`; непредставимые значения отклоняются с диагностикой по правилам
проекта. Нет delay и completion. UIKit/AppKit остаются только в адаптерах.

Первая таблица: `position`, `bounds`, `opacity`, affine `transform`,
`backgroundColor`, `cornerRadius`. Для transform сначала scale/translation и
проверенные комбинации; поворот между представлениями матрицы проверяется M04,
пока его интерполяция не определена — snap с документированным ограничением.
Пары цветов нормализуются в одно цветовое пространство; отсутствие цвета —
прозрачный цвет для интерполяции, целевое model-значение сохраняется.
`border*`, `shadow*`, `zPosition`, `masksToBounds`, порядок слоёв и содержимое
растра меняются мгновенно. Расширение таблицы — самостоятельная приёмка.

### D62. Область, batching и отложенный Arrangement

`node.animate` задаёт политику **следующего изменения представления поддерева**,
не журнал отдельных Swift-присваиваний. Корень хранит записи
`(scopeNodeID, sequence, animation)` вместе с pending work. Запись создаётся
на входе в closure; sequence монотонный в пределах владельца. Она сохраняется
только если closure вызвал релевантную visual/layout/arrangement-инвалидацию
в области. No-op и чистые semantic-изменения не создают работы/намерения.
Учёт мутаций выполняется до clean-to-dirty guard в `notifyPending`, даже если
ping уже был отложен или отправлен. Это локальный сборщик области у root,
а не глобальный текущий animation context.

Scope разрешается по актуальному дереву при коммите, после
`resolveDirtyArrangements`. Поэтому новые wrapper'ы входят в область, но новые
слои не получают enter-animation. Сохранившиеся слои внутри области получают
переход; удалённые снимаются сразу. Перенос между родителями в первой версии —
snap: перенос локальных координат через две системы требует отдельной приёмки.
Отложенная мутация из Task после выхода из closure не принадлежит вызову.

### D63. Смешение — явная семантика области

| Ситуация до одного коммита | Результат |
|---|---|
| Два непересекающихся `animate` | Каждая область сохраняет свой timing |
| Пересекающиеся области | Для слоя побеждает запись с большим sequence |
| Вложенный вызов | Получает больший sequence и перекрывает внешний в своей области, в том числе последующие обычные записи внешнего closure |
| Поздний `.none` на области | Перекрывает прежнее намерение в этой области |
| Обычная мутация вне области | Snap, даже если попала в тот же commit |
| Обычная мутация внутри уже заданной области | Входит в конечный diff области; для snap автор использует `.none` |
| Сосед сдвинулся за пределами области | Snap; для совместного движения нужно выбрать общего родителя |

Это намеренно не per-assignment/per-property provenance. Такая модель позволяет
анимировать последствия layout, не отслеживая причинную связь каждой координаты
с каждой мутацией. В M01 проверяется, достаточно ли такого правила для примеров;
если нет, сначала пересматривается контракт, а не добавляется скрытая эвристика.

### D64. Commit, retry и отдельные идентификаторы

Animation intent — metadata публикации, а не вход solver. Предпочтителен
внутренний commit envelope рядом с `HostRenderRequest`; менять его публичный
initializer без нужды не требуется. Сравнение layout work игнорирует intent,
но ветка same-work обязана обработать paint/animation metadata.

При запуске solve pending intents переходят во владельца active work. При
stale/retry они объединяются с новыми по sequence: старый intent не перезаписывает
новый `.none`. При commit текущие appearance-изменения и их intents сливаются
вместе, поскольку appearance читается актуальным. Semantic-only publish не
воспроизводит завершённый intent. После публикации intent потребляется один раз.

Layout generation недостаточно для paint-only. Активные переходы имеют собственный
монотонный token и ключ `(mountEpoch, NodeID, property)`. Callback от предыдущего
token не может завершить или удалить новый переход. Снимок для solver не хранит
closure, Node, CALayer или таблицу живых анимаций.

### D65. Текст движется, но не растягивается

Контракт общий с T02/T07 плана 4: renderer владеет внешним слоем ноды и внутренним
слоем растра. Это два слоя одной ноды в одном renderer, а не две ноды и не второй
рендерер. NodeID, hit-test, AX и порядок детей относятся к внешнему слою.

Внешний слой анимирует position/bounds, фон, opacity и transform. Внутренний
слой имеет размер bitmap, фиксированную привязку к началу content area и
обновляется без actions. Изменение bounds контейнера не масштабирует glyphs.
Явный transform автора масштабирует всё поддерево, включая текст — ожидаемо.
Растровый слой не попадает в сортировку node-sublayers и не перекрывает overlay.

При перемещении без изменения raster key bitmap переиспользуется. При resize
старый bitmap сохраняется в своём размере и обрезается по content area до
готовности нового; новый подменяется без crossfade, только после проверки ключа.
Если изменились текст/стиль/locale, старое содержимое убирается; временная пустота
допустима и замеряется, показывать прежние данные как актуальные нельзя.
Перенос строк меняется один раз по целевой ширине. Плавная типографическая
перекомпоновка не обещается. T02 проверяет этот видимый компромисс до переноса.

### D66. Retarget и прекращение

Для каждого изменившегося поддерживаемого свойства renderer:

1. Сохраняет начальное значение из presentation при активном переходе, иначе
   из прежней модели; при отсутствии presentation использует прежнее model-значение.
2. Устанавливает конечное model-значение с actions disabled.
3. Заменяет собственную explicit animation с from/to и новым token либо удаляет
   её для `.none`. Удаление делается адресно, без `removeAllAnimations` чужих слоёв.

Новая цель начинается от видимого значения; сохранение скорости в первой версии
не обещается. Повторный commit с тем же target не перезапускает и не обрывает
действующий переход. Изменение другого свойства тоже его не отменяет. Обычная
неанимированная запись с новой целью прерывает только затронутое свойство и snap'ит.

Внутренний adapter завершения очищает записи по token; способ безопасного хопа
из CA callback на MainActor проверяется M02 при strict concurrency. Публичного
completion пока нет. `CATransaction` callback приходит также после удаления
анимаций, поэтому сам по себе не доказывает успешное завершение.

### D67. Lifecycle и Reduce Motion

Владелец intent и активных переходов — bridge/renderer. `detach`, `replaceRoot`,
`dispose` удаляют соответствующие intents и собственные анимации; поздний callback
отбрасывается по epoch/token. На `suspend` активное движение заканчивается snap'ом
к committed target, pending intentions очищаются. Изменения во время suspend
накапливают состояние, но анимацию не сохраняют; первый resume commit — snap.
Это единый контракт, без скрытого продолжения CA в фоне.

`ReduceMotionKey` в environment, host читает систему при attach и изменениях.
Значение true резолвит intent в `.none` при commit; включение во время движения
немедленно завершает собственные активные переходы на target, без нового solve.
Возврат false влияет только на будущие вызовы. UIKit/AppKit notifications и
их отмена при detach покрываются соответствующими host-тестами.

### D68. Снимки и взаимодействие

D25/D34/D46 не меняются: hit-test, pointer sessions, focus, AX и DebugOverlay
читают committed target. Presentation доступен только renderer для retarget.
Тап по движущейся карточке проверяется в её конечном месте; это ограничение
первой версии должно быть видно в примере и документации. Для результата A interactive drag и «поймать на лету» не входят. В результате B
жест принадлежит неподвижному transition overlay; hit-test движущихся частей
не вводится автоматически. Взаимодействие и AX для B уточняются в D73/M10.

### D69. Проверка результата и стоимости

Эталон снимается после подтверждённой готовности layout, актуальных display
artifacts и отсутствия активных переходов сцены. Не `sleep(60 ms)` и не подбор
delay под экспорт. Timeout — ошибка экспорта, не разрешение снять промежуточный
кадр. Все существующие эталоны сохраняются; новые сцены получают новые номера.

M02 устанавливает измеренный бюджет, M08 сравнивает median/p95, память и счётчики.
Не обещаем математический ноль накладных расходов. Обязательные инварианты:
нулевое создание CAAnimation для обычной сцены, отсутствие новых solve/raster
jobs от самих кадров анимации, освобождение активных записей после завершения.

## 4. Что переносим и что проверяем заново

| Источник/точка | Использование |
|---|---|
| Weave `Animation.swift`, conversions | Value-параметры и конверсия timing; spring-as-ease не переносится, дефект #41 |
| Weave coordinator retry | Сохранение intent полезно; здесь merge учитывает более новые sequence |
| Weave `TransitionSession` | Не переносится: таймер и callback не заменяют lifecycle анимации |
| Trellis `Node.notifyPending` | Учёт intent до coalescing guard; weak/ID ownership сохраняется |
| Trellis `RenderCoordinator.flush` | Обычный, same-work, paint-only и semantic-only пути проверяются отдельно |
| Trellis `LayerRenderer` | Все model-записи сохраняют actions disabled; explicit transitions добавляются адресно |
| Текст T07 | Внутренний raster layer и собственный display key, общий с D65 |

Чтение текущих Node/RenderCoordinator/LayerRenderer подтверждает точки интеграции,
но не является экспериментальной проверкой CA. История источников остаётся в
[source-provenance.md §8](source-provenance.md); Weave не меняется. Ошибки прежнего
проекта контракта отмечены в [defects.md #42](defects.md).

Платформенные основания: explicit animation не записывает конечное model-значение —
его нужно установить отдельно ([Apple: Animating Layer Content](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/CoreAnimation_guide/CreatingBasicAnimations/CreatingBasicAnimations.html));
completion транзакции вызывается и после удаления анимаций
([Apple: completion block](https://developer.apple.com/documentation/quartzcore/kcatransactioncompletionblock)).
Все остальные правила выше — предлагаемые контракты Trellis, доказываемые карточками.

## 6. Результат B: составной переход как переиспользуемая возможность

### D70. Один переход, несколько согласованных частей

`Transition` описывает переход между исходным и целевым представлением:
геометрия контейнера, clipping/radius, изображение, заголовок, иконки, фон,
появление текста страницы и кнопки закрытия. Все части используют единый progress
0…1, собственные интервалы и кривые внутри него. Для жеста progress ограничен
этим диапазоном; rubber-banding — отдельное расширение. Нет цепочки независимых
`animate` и таймеров. Первый preset `.expand` обязателен.

Общие элементы сопоставляются по ролям, локальным для одной сессии (например,
hero/title/accessories), а не по совпадению NodeID между двумя деревьями.
Пропущенный необязательный элемент использует fade; дубликат роли диагностируется
и отклоняет переход с безопасным snap. Геометрия переводится в пространство
одного host. Cross-window transitions не входят.

### D71. Владелец и подготовка

Bridge владеет одной `TransitionSession` в пределах host: source/destination IDs,
mountEpoch, подготовленные endpoints и artifacts, временные render layers,
progress и внутренний completion token. Сессия не становится глобальным registry.
Временные слои принадлежат тому же LayerRenderer и не создают логические Node/AX
дубликаты. Live source/destination остаются во владении обычных деревьев; session
не удерживает их через callbacks без необходимости.

Сначала измеряется destination и готовится требуемое содержимое, затем начинается
движение. Пока destination не готов, исходная карточка остаётся видимой и может
получить отмену запроса. Timeout/ошибка подготовки дают определённый snap или
отмену с диагностикой; поздний artifact после отмены не оживляет переход.

Для картинки выбирается явный режим crop/fit; для заголовка — политика смены
переносов строк, а не растягивание bitmap по двум осям. Первая версия предлагает
два endpoint-растра с согласованным положением и crossfade; промежуточный текст
не перемеряется каждый кадр. Это отдельная политика перехода B, не изменение
обычного текстового resize D65. Изображение в прототипе — локальный fixture:
сетевой loader, ImageNode и весь N02 не становятся скрытой зависимостью.

### D72. Открытие, закрытие и жест

Состояния session: preparing → opening → presented → interactiveClosing →
settling → presented/closed; возможны отмена подготовки и неинтерактивное closing.
Таблицу допустимых событий фиксирует M10. Закрытие кнопкой и жестом используют
тот же обратимый переход. Отмена жеста возвращает **представленную страницу**,
завершение — исходную карточку. Решение finish/cancel учитывает progress и скорость
в согласованных единицах; пороги — часть preset и проверяются граничными тестами.

Повторное действие во время движения меняет направление текущей session, не
создаёт вторую копию слоёв. Для первой версии скорость при retarget может не
сохраняться, но положение непрерывно. Конкурирующий `present` другой страницы
отклоняется с определённым результатом до завершения текущей сессии. Если source
удалён, скрыт или больше не имеет валидного committed frame, закрытие использует
fade вместо полёта в устаревший прямоугольник. При resize host во время движения
session завершается к выбранному логическому endpoint с новой раскладкой.

### D73. Взаимодействие, доступность и остановка

Система принимает жест через неподвижную host-overlay область: presentation
геометрия движущихся элементов не становится источником обычного hit-testing.
Во время движения действия временных копий недоступны. На presented странице
работают обычные события; во время закрытия жест принадлежит session.

На время представления background исключается из focus/AX через существующий
modal scope D40. Публикуется одно логическое представление страницы без копий
текста, focus восстанавливается при закрытии, если источник ещё eligible.
Скролл и pan должны иметь явное правило арбитража: на первом срезе используется
страница без ScrollNode; при появлении scroll закрытие начинается только при
разрешённом состоянии scroll. Нельзя объявить интеграцию со scroll проверенной
по статической странице.

Reduce Motion использует мгновенный переход между endpoints. Detach/replaceRoot
очищают session, overlay, удержанные artifacts и pending callbacks по epoch/token.
Suspend завершает к логическому endpoint: opening → presented, closing → closed,
незавершённый interactiveClosing → presented. После resume нет скрытого движения.
Это дополнение к D67 для владельца составного перехода, а не его фоновые таймеры.

### D74. Критерий «сложное стало легко»

Две разные сцены используют один механизм: редакционная карточка → статья и
компактная карточка профиля → профиль. Первая проверяет крупное изображение и
текст; вторая — иной состав общих элементов и независимые интервалы появления.
Обе имеют открытие, обратное движение, finish/cancel жеста и Reduce Motion.

Во внешнем consumer: одно действие открытия и локальное описание соответствий
элементов; нет CALayer, координатной арифметики, ручных таймеров, snapshot-копий
или cleanup. Отличия второй сцены задаются данными/композицией перехода без правок
coordinator/renderer. Именно эта приёмка проверяет переиспользуемость API.

## 7. После обязательных результатов

Произвольные navigation stacks, cross-window matching, универсальные keyframes,
публичные completion/sequences/delay, presentation hit-testing всех нод и
интеграция со ScrollNode остаются отдельными расширениями. M09 добавляет настоящую
пружину, когда нужна физика. Раскрытие страницы, обратный переход и отменяемый
жест уже входят в обязательный результат B и не переносятся в неопределённое «потом».
