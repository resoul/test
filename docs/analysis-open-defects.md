## #11 — Стабильность подписей без изменения NodeID

### Почему сброс не минимальный риск

В [NodeID.swift](../Sources/TrellisCore/NodeID.swift) прямо гарантируется
уникальность ID среди **всех живых деревьев процесса**. Она используется как
идентичность, в том числе в словарях рендерера и ключах измерений.
`#if DEBUG` не отменяет этот контракт: в Debug тоже возможны несколько хостов,
живые старые деревья и незавершённая работа с их snapshot.

Есть конкретная проблема с предложенным местом сброса:
в `switchScenario(to:)` из
[PlaygroundApp.swift](../Playground/macOS/PlaygroundApp.swift)
старая `instance` заменяется только **после** `scenarioName.make(...)`.
`teardown()` и `detach()` сами по себе не доказывают освобождение всех старых нод.
При сбросе непосредственно перед `make` старое и новое деревья могут иметь
одинаковые ID. Даже перенос освобождения раньше не докажет отсутствие других хостов.

Кроме того, `NodeIDAllocator` — internal enum. Объявить только метод `public`
недостаточно для вызова из Playground; понадобится ещё публичная точка доступа.
Расширять API идентичности ради формата скриншотов неоправданно.
Формулировку в реестре «публичный сброс … отдельным решением» я читаю как
предложенный вариант, а не уже согласованное исключение из контракта.

### Что предлагаю

У overlay два режима подписей:

- интерактивный: настоящий `NodeID`, чтобы искать ноду в логах;
- экспортный: локальный номер в детерминированном preorder-обходе текущего
  дерева, например `n1`, `n2`, …, с отдельным обозначением от runtime `#42`.

Локальный номер — исключительно представление. `entries`, runtime-логи,
snapshot, cache и layer registry продолжают использовать настоящий `NodeID`.
Сопоставление `локальная метка → путь → NodeID` при необходимости сохраняется
рядом со скриншотом как диагностический файл; runtime ID в нём не сравнивают
между запусками. Выбор режима нужно протянуть из экспортера через host/bridge,
не добавляя платформенные импорты в TrellisRender.

Это локализует diff внутри изменённой сцены. Добавление ребёнка в начале S02
по-прежнему может перенумеровать остаток S02 — такой гарантии локальные номера
не дают. Пути также меняются при вставке/перестановке соседей; стабильность
при таких изменениях требует явных ключей сценария и отдельного контракта.

Альтернатива при требовании видеть именно runtime ID: отдельный свежий процесс
на сцену с детерминированной инициализацией. Это медленнее и сложнее для
экспортера; прочие создания нод до сцены всё равно влияют на номера.
Скриншоты без текста возможны, но перестанут проверять сами подписи.

**Приёмка:** одинаковая сцена после произвольных посторонних аллокаций и при
другом порядке экспорта даёт одинаковые экспортные подписи; добавление ноды
в S02 не меняет S03; интерактивный overlay сохраняет связь с логами; два живых
хоста сохраняют уникальность ID. Геометрия и число commit не меняются.

## #12 — Размещать подписи с учётом фактических пересечений

В [DebugOverlayRenderer.swift](../Sources/TrellisRender/DebugOverlayRenderer.swift)
ширина подписи вычисляется приблизительно по числу символов,
а её начало всегда `(0, 0)` относительно outline. Это не фиксированные 50–70 pt,
но причина наложений описана верно: ширина не ограничена рамкой и соседние
подписи не учитываются.

Компактный формат полезен, однако порог `16 pt` произволен: пригодность
определяется шириной конкретной строки. А `depth % 2` не решает случай S19:
у соседей одинаковая глубина, значит одинаковое смещение. Даже чередование
по индексу лишь уменьшает вероятность пересечения. Сдвиг вверх может вывести
текст за canvas или наложить его на другую ветку.

### Предлагаемый алгоритм

1. Собрать рамки и подписи в координатах корня. Рамки рисовать для всех нод.
2. Зафиксировать порядок обработки, например сначала глубокие ноды, затем
   preorder-индекс. Тогда мелкие ноды имеют приоритет над общим контейнером.
   Порядок не должен зависеть от обхода Dictionary или глобального NodeID.
3. Для каждой подписи проверить небольшой фиксированный набор позиций:
   у верхнего левого края, ниже него, над рамкой. Кандидат должен помещаться
   в canvas и не пересекать уже принятые подписи с небольшим зазором.
4. Если полная строка не помещается, повторить для одной метки без размеров.
   Если места всё равно нет — скрыть текст этой ноды, сохранив outline.

Это гарантирует непересечение **показанных** подписей, но не одновременную
видимость всех подписей. В плотном дереве последнее геометрически невозможно.
Проверять только ширину собственной ноды недостаточно: мешают также предки
и другие ветви. Удалённый от рамки бейдж потребует указателя связи; для первого
варианта разумнее ограничиться близкими позициями.

Для маленьких сцен линейный поиск пересечений по уже принятым прямоугольникам
прост, но весь алгоритм тогда O(N²). Если замер покажет проблему на больших
деревьях, добавить пространственную сетку. Логику выбора прямоугольников
лучше сделать чистой функцией, независимо от CALayer.

Hover/HUD — полезное продолжение, но это отдельная функциональность ввода.
На iOS/tvOS нужен tap/focus, а не только мышь. Платформенный выбор ноды
должен жить в соответствующем адаптере/Playground.

**Приёмка:** S19, соседние узкие ноды одной глубины, совпадающие рамки
родителя и ребёнка, длинные метки, края canvas и scale 1×/2×.
Показанные подписи не пересекаются и остаются внутри canvas; скрытие текста
не убирает рамку; повторный apply даёт те же позиции. Сохранить проверки
[DebugOverlayTests](../Tests/TrellisRenderTests/DebugOverlayTests.swift)
на отсутствие влияния overlay на layout и на освобождение слоёв.

## #24 — Сначала разделить рост вызовов и рост разных состояний

В [FlexboxMeasure.swift](../Sources/TrellisCore/Layout/FlexboxMeasure.swift)
действительно есть первоначальный `measure(child, childConstraint)` и повторный
`measure` под `.exact(main)`, когда `main != naturalMain`. Повторное измерение
контейнера снова проходит по этому алгоритму. ADR 0008 устранил часть повторов,
но не эту ветку. Размещение также иногда вызывает `measureContainer` под exact
по двум осям — его нельзя исключать из анализа.

Однако две рекурсивные ветки ещё не доказывают фактические `2^depth` промахов.
Такой рост получается, если ветки продолжаются на каждом уровне и кэш не
объединяет состояния. Constraints могут совпадать, размеры могут достигнуть
нуля/min/max, часть элементов не flex'ится. В C26 зафиксировано незавершение
depth 300, но нет доказательства «depth 30 ≈ миллиард операций» для #24.
Замеры старого #13 с LRU на 64 записи нельзя переносить на нынешний алгоритм.

Рабочая оценка: стоимость определяется числом различных состояний
`(node, constraint, revisions, direction)` и стоимостью обработки детей в каждом
состоянии, плюс повторной работой после вытеснения. Поэтому нужен небольшой
воспроизводимый benchmark со счётчиками входов в measure, hits/misses,
уникальных ключей на ноду, пикового размера кэша и вытеснений.

Сравнить серии глубин, например 10/20/40/80, затем 150/300, отдельно для:
shrink, grow, отсутствия flex, одинаковых осей и чередования row/column.
Тяжёлые случаи запускать отдельным процессом с внешним таймаутом.
Замерять Release с логом off; считать отдельно measure, placement, память
и отзывчивость отмены. Эти серии предложены для проверки, не выполнены здесь.

### Почему max-content — хорошее направление, но не готовое доказательство

В CSS `flex-basis: auto` сначала берёт main-size property (`width`/`height`),
и только если оно тоже auto, переходит к content. Алгоритм определения basis
имеет отдельные случаи для definite basis, intrinsic constraints и зависимости
от cross-размера. Поэтому «auto всегда означает unspecified main» — слишком
сильное упрощение. См. [CSS Flexbox §7.2.3](https://www.w3.org/TR/css-flexbox-1/#flex-basis-property)
и [§9.2](https://www.w3.org/TR/css-flexbox-1/#algo-main-item).

Для Trellis я бы проектировал отдельный запрос intrinsic basis, не содержащий
финальные flex-линии, и отдельное измерение под выделенный размер. Это позволяет
повторно использовать basis, когда меняется доступный main, вместо повторного
решения всего поддерева ради его естественного размера.

Но «ключ только по cross» означает лишь отсутствие доступного main в
**определённом intrinsic-запросе**, а не удаление width/height из общего
`LayoutMeasureCacheKey`. В ключе остаются identity/revisions, direction, режим
измерения и ось запрашиваемого basis. Для итоговой геометрии нужен полный
constraint. Процентные размеры требуют явно определить, относительно какого
известного размера они разрешаются; `.unspecified` не должен молча менять
этот контекст.

Есть два препятствия для обещания строго O(N):

- у дочерней column главная ось родительской row становится поперечной;
  изменение выделенной ширины может создавать новые cross-ключи дальше вниз;
- wrap, cross-выравнивание и вызовы measure из placement могут порождать
  дополнительные состояния. Кэш basis не устраняет их автоматически.

Линейное число обходов можно обещать для ограниченного класса деревьев после
доказательства, что каждая нода получает ограниченное константой число состояний.
Даже это ещё не доказывает линейность всех внутренних циклов распределения
на произвольных широких линиях. Практическая цель сначала — убрать взрыв
на зафиксированном воспроизведении, затем очертить проверенный диапазон.

### Поправка про текст

Сейчас [LayoutContentMetrics](../Sources/TrellisCore/Layout/LayoutSnapshot.swift)
хранит фиксированный `intrinsic`, независимый от constraint; живой системы
измерения текста на этом этапе нет. Следовательно, рассказ о текущем переносе
текста до shrink и новой длинной строке после смены basis не описывает этот код.
Такой контракт понадобится при появлении текста. Сейчас регрессии нужно искать
в размерах вложенных контейнеров, flex-wrap, fraction, min/max, grow/shrink
и итоговом placement. «Обновить снапшоты» можно только после объяснения каждой
ожидаемой перемены геометрии.

### Почему один ребёнок не означает fill

Контрпримеры к безусловному `.exact(availableMain)`:

| Условия по main-оси | Ожидаемый смысл |
|---|---|
| Контейнер 200, ребёнок 40, grow = 0 | Ребёнок остаётся 40 |
| Контейнер 100, ребёнок 200, shrink = 0 | Ребёнок остаётся 200 с overflow |
| Контейнер 100, ребёнок 200, min = 150 | Ребёнок не может сжаться до 100 |
| Контейнер 200, ребёнок grow = 1, max = 80 | Ребёнок ограничен 80 |

В Trellis grow по умолчанию вообще равен нулю. Отсутствие конкурентов
не отменяет basis, grow/shrink и ограничения размера.

Узкий fast path возможен, когда окончательный main доказуемо известен без
обхода поддерева: например, из definite basis и условий распределения,
с учётом margins/min/max. Он должен использовать ту же математику и проверяться
сравнением с общим путём. Необходимо также сохранить данные для cross-размера
и размещения. Само `relativeChildren.count == 1` таким доказательством не является.

### Порядок работы и критерий закрытия

1. Зафиксировать fixture #24 и число состояний на растущих глубинах.
2. На этапе 1 оставить известное ограничение явно открытым. Проверить, что
   отмена дорогого запроса позволяет обработать следующий. Не считать
   глубину 300 без overflow подтверждением работоспособности случая с overflow.
3. Если нужна защита от чрезмерной работы, отдельно определить бюджет операций
   и явный исход ошибки, очистку worker slot и дальнейшее поведение хоста.
   Простой лимит глубины неточен; успешный частичный layout нарушит D09.
4. Для этапа 2 оформить ADR с семантикой intrinsic basis, fraction и смены осей;
   проверить прототип на том же fixture и на геометрических контрпримерах.
5. Закрывать #24 после завершения overflow/shrink и grow depth 300 в согласованном
   бюджете, проверки роста числа состояний, памяти, отмены и регрессий ADR 0006–0008.
   Гейт скриншотов и equivalence-тесты нужны наряду с точечными проверками геометрии.

«Реальных UI глубиной 300 нет» может объяснить приоритет, но не исправляет
алгоритм и не задаёт безопасную границу: количество implicit wrappers зависит
от способа построения дерева.

## #10 и #22 — согласен с направлением, с оговорками

**#10:** решение отложить точечный paint разумно в рамках измеренного профиля.
1.5 ms — результат конкретного Mac/Release, не общий бюджет всех устройств.
При 120 Hz весь кадр занимает около 8.33 ms, и эти расходы делят время с другой
работой. Возвращаться к оптимизации стоит по профилю целевого устройства.
Для `Set<NodeID>` нужно заранее описать накопление изменений за pending-окно,
удаление нод, инвалидирование темы/окружения и момент очистки после применения.
Одного множества без этих правил недостаточно.

**#22:** явный стек на куче — разумное направление для рекурсивных measure и
placement. Это снимает зависимость этих обходов от глубины нативного стека,
но не делает вложенность бесконечной: остаются память, стоимость snapshot,
другие обходы и освобождение рекурсивных структур. Границы 3000/6000 — наблюдения
конкретного профиля, не переносимая гарантия. Сам перевод рекурсии в цикл
не уменьшает число состояний #24: это две разные задачи.

## Рекомендация

Сначала обеспечить воспроизводимость и измеримость #24. Для небольшого
самостоятельного исправления взять #11 через экспортные метки, затем #12
через разрешение пересечений. Перестройку basis делать отдельным ADR после
замеров; безусловный reset аллокатора и fast path «один ребёнок = fill» отвергнуть.

Эта записка не меняет реализацию, принятые контракты или статусы реестра.
