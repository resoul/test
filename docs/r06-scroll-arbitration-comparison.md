# R06 — Relay vs coordinated-native: сравнение подходов (предложение)

Implementation-plan-6.md's чек-лист R06 просит: «минимальная шапка + горизонтальная
и вертикальная области — сравнить relay и coordinated-native подходы по
input/AX/momentum; записать выбранный вариант». Это предложение (не D-решение) —
рекомендация для обсуждения перед реализацией R08/R09/R13/R14.

## 0. По пути найден и исправлен реальный дефект окружения

Первый прогон живого прототипа на iPhone 17 Pro Simulator показывал системно
неверную геометрию (шапка визуально заметно ниже, чем вычисленные в коде
значения frame/offset) на **каждом** `xcrun simctl launch` без интерактивного
запуска — воспроизводилось даже после полной перезагрузки самого симулятора.
Причина найдена и исправлена — дефект #65 ([defects.md](defects.md)):
`Playground-iOS` target не объявлял `INFOPLIST_KEY_UILaunchScreen_Generation`,
из-за чего iOS запускал сцену в legacy-режиме совместимости (`320×480`,
`scene.activationState == .unattached`) и растягивал этот фиксированный canvas
на реальный экран. Правка — одна строка в `project.pbxproj`
(`INFOPLIST_KEY_UILaunchScreen_Generation = YES` для Debug/Release
`Playground-iOS`). После исправления `scene.coordinateSpace.bounds`
корректно репортит `(0, 0, 402, 874)` и `activationState == .foregroundActive`
на холодном `simctl launch` без единого интерактивного действия — то, что
раньше воспринималось как «не диагностированная аномалия рендеринга», было
реальным, воспроизводимым и теперь закрытым багом конфигурации проекта, а не
особенностью песочницы. Обычный browse-flow (`TrellisHostView`) страдал от
того же самого весь сеанс, просто визуально незаметно — тёмная тема холста
почти совпадает по цвету с чёрными letterbox-полосами.

Итог: все последующие находки в этом документе получены **после** исправления,
на подтверждённо корректной геометрии, не на сломанной.

## 1. Relay — прочитан реальный, работающий код

`../old/TabBarPager/Sources/TabBarPager/TabBarPagerController.swift` (270 строк,
реально используемый пакет, не черновик) и
`../old/ProfilePage-main/ProfilePage/ViewControllers/ProfileViewController.swift`
прочитаны полностью. Механизм (`TabBarPagerController`):

- Две реальные `UIScrollView`: `containerScrollView` (держит header + page
  content, обычный layout) и `relayScrollView` — прозрачная, `zPosition =
  .greatestFiniteMagnitude` (поверх всего), **единственная**, что реально
  получает жест: её `panGestureRecognizer` добавлен и на `containerScrollView`
  тоже (`containerScrollView.addGestureRecognizer(relayScrollView.
  panGestureRecognizer)`), а `page.pageScrollView.panGestureRecognizer.
  require(toFail: relayScrollView.panGestureRecognizer)` практически
  гарантирует, что страница никогда не распознаёт **свой** жест сама.
- `relayScrollView.contentSize` = header height + tabBar height +
  max(page content height, remaining viewport) — то есть relay always знает
  «полную» прокручиваемую длину композиции.
- `scrollViewDidScroll(relayScrollView)` — единственное место, где что-либо
  происходит: пока `relayScrollView.contentOffset.y < topMaxContentOffsetY`
  (ещё в зоне шапки), `containerScrollView.contentOffset.y` **вручную**
  зеркалится тем же числом (шапка коллапсирует) и текущая страница сбрасывается
  в 0 (`resetPageContentOffset`); после — `containerScrollView.contentOffset.y`
  пиннится на `topMaxContentOffsetY` (шапка зафиксирована), а
  `page.pageScrollView.contentOffset.y` **вручную** пишется каждый кадр как
  `relayScrollView.contentOffset.y - topMaxContentOffsetY`.
- `ProfileViewController.swift` использует тот же приём между **соседними**
  страницами (не активной): при смене вкладки состояние прокрутки других
  grid'ов синхронизируется вручную (`setContentOffset`), чтобы вернувшись на
  них, шапка визуально совпадала.

### Сильные стороны relay

- **Один momentum на всю композицию.** Единственный реальный interactive
  scroll — `relayScrollView` — значит деселерация после отпускания пальца
  целиком системная и непрерывная через границу «шапка коллапсирует → страница
  скроллится»: нет точки передачи между двумя независимыми momentum.
- Один source of truth (`relayScrollView.contentOffset.y`), из которого всё
  остальное производно.

### Слабые стороны relay

- Страница практически никогда не получает свой собственный реальный жест
  (`require(toFail:)`) — платформенная функциональность, завязанная именно на
  эту `UIScrollView` (VoiceOver's scroll-by-gesture, `refreshControl`,
  `scrollsToTop`) работает на неправильном объекте; `containerScrollView.
  scrollsToTop = false` в самом коде признаёт это явно.
- Программная запись `page.pageScrollView.contentOffset.y = …` сама вызывает
  чужой `scrollViewDidScroll`, если у страницы свой delegate — синтетическое
  неотличимо от настоящего пользовательского скролла без отдельного флага.
- Один и тот же relay-паттерн независимо переписан дважды (активная страница
  в `TabBarPagerController`, соседние — в `ProfileViewController`) — ровно то,
  что implementation-plan-6.md §1.2 просит не дублировать.

## 2. Coordinated-native — построен, прогнан, даёт другой результат, чем ожидалось

`Playground/iOS/ScrollArbitrationPrototype.swift` (временный, удалён после
записи находок) — вложенные **настоящие** `UIScrollView` без единой строки
relay-кода: внешний вертикальный `UIScrollView` (шапка как первый content-view
+ horizontal pager) → горизонтальный `UIScrollView`-pager (только paging) →
у каждой страницы свой вертикальный `UIScrollView` со списком. Ни
`scrollViewDidScroll`, ни `shouldRecognizeSimultaneouslyWith`, ни ручная
запись `contentOffset` — только конфигурация frame/contentSize.

### Что реально показал прогон на исправленной геометрии (не предположение)

Три контролируемых свайпа на iPhone 17 Pro Simulator, каждый подтверждён
скриншотом до и после:

1. **Touch-down внутри списка страницы** (уже в её собственном верху, свайп
   вверх на ~600pt — заметно больше высоты шапки): список проскроллил с
   row 0 до row 21+, **шапка не сдвинулась ни на пиксель**. Один непрерывный
   жест **не** передаётся от списка к внешнему scroll, даже когда список уже
   в начале своего контента и продолжает тянуться в направлении, где ему
   больше некуда скроллить внутри себя же на первый взгляд (на самом деле
   есть куда — весь список из 40 строк).
2. **Touch-down на самой шапке**: шапка корректно коллапсирует (внешний
   `UIScrollView` реагирует), список ниже остаётся на прежней позиции
   (row 21+, не сброшен).
3. Значит: **какой `UIScrollView` получает весь жест от down до up, целиком
   определяется тем, где случился touch-down** — простое вложение
   `UIScrollView` **не даёт** автоматического hand-off «список докрутился до
   верха → жест переходит к шапке» посреди одного пальцевого движения. Это
   не баг конкретной сборки — это документированное поведение UIKit: нет
   отдельного механизма, который бы «отдавал» уже начатый и распознанный pan
   gesture другому scroll view при достижении границы контента.

### Пересмотренный вывод (важнее исходной гипотезы)

Первоначальная гипотеза этого документа — «vanilla nested `UIScrollView`
бесплатно даёт коллапсирующую шапку, как в Mail.app/App Store» — **опровергнута
прямым экспериментом**, не подтверждена. Реальный нативный паттерн для
непрерывного «шапка коллапсирует → список продолжает» — это **одна**
`UIScrollView` на страницу, где шапка — часть **того же** прокручиваемого
контента (аналог `UITableView.tableHeaderView`), а не отдельный внешний
scroll view. Тогда: список получает жест всегда сам (никакого relay, никакого
`require(toFail:)`), а шапка утекает вверх и уходит из видимости просто потому,
что она физически первая в контенте той же самой scrollview — без единой
строки координации вообще, для **одной** страницы.

Открытая часть для композиции (implementation-plan-6.md §1.1): pager с
**несколькими** страницами, каждая — независимая scrollview с собственной
позицией, но шапка/сегмент-контрол должны выглядеть **общими** для всех
страниц (не дублированными и не пересозданными на каждой). Это требует шапку
**вне** hit-testable content любой отдельной page-scrollview (наложение
поверх/под pager'ом, как это уже описывает `TabbedScrollNode` в §1.1: «верхний
блок — обычная композиция Node»), с её presentation (высота/collapse progress),
управляемой **чтением** (не записью!) `contentOffset` **текущей активной**
страницы через её delegate — однонаправленно, без второго `UIScrollView`,
получающего synthetic offset, и без переключения гонки за жест между двумя
scroll-поверхностями. Это не relay (нет записи в чужой `contentOffset`, нет
`require(toFail:)`, каждая страница владеет своим настоящим жестом целиком) и
не «наивное вложение» (которое не работает для непрерывного коллапса) — третий,
более узкий вариант, ближе к тому, что реальные iOS-приложения делают на
практике.

## 3. Рекомендация (для обсуждения, не решение)

**Coordinated-native, но не в форме «два вложенных `UIScrollView`»** — правильная
форма: одна scrollview на страницу (список + шапка как единый content для
самостоятельной страницы; в композиции — шапка вне page-scrollview, презентация
управляется чтением текущей активной page's offset). Обоснование:

1. **Список никогда не теряет владение своим настоящим жестом** — ни в каком
   из двух рассмотренных вариантов relay не нужен: coordinated-native (в
   исправленной форме) списку вообще не с кем делить touch-down, а не
   потому, что кто-то specifically разрешает ему быть «главным».
2. **Момент передачи через границу «шапка → список»** — открытый пункт: при
   единой scrollview-на-страницу (без внешнего pager-scroll) momentum
   действительно непрерывен бесплатно (тот же сценарий, что relay даёт ценой
   ручной синхронизации); при варианте «шапка отдельно, страницы отдельно»
   этот непрерывный momentum не гарантирован без дополнительной проверки —
   именно то, что реальный gesture-recognizer прогон R08 должен подтвердить
   или опровергнуть, не эта карточка.
3. Relay's структурные слабости (страница не главный получатель input,
   synthetic delegate-события, дублирование логики) остаются веским доводом
   против relay независимо от того, какую форму coordinated-native выберет
   R13/R14.
4. **Открытый риск, теперь куда более конкретный, чем в предыдущей редакции
   этого документа**: «просто вложить `UIScrollView`» не работает для
   непрерывного коллапса — R08/R13 должны спроектировать точную форму (шапка
   вне page-scrollview + read-only офсет-наблюдение), не полагаться на
   default nested-scroll поведение, которого не существует.

## 4. Provenance и очистка

Прототип `Playground/iOS/ScrollArbitrationPrototype.swift` был временным —
удалён из дерева после записи находок выше. `PerfRecorder.swift`/
`PerfHarness.swift` (§6.1) — отдельная, постоянная инфраструктура, не
затронуты этой очисткой; **но** их предыдущие измерения (до фикса дефекта
#65) вероятно тоже собирались на 320×480-сцене, если `--perf-viewport` не
совпадал с логической 320×480 экраном — численные значения из прошлых
прогонов не переизмерялись заново в рамках этой карточки (R06 не требует
финального baseline — это R15), но baseline-документ R15 должен собирать
числа **после** этого фикса, не до. `TabBarPagerController.swift`/
`ProfileViewController.swift` не изменялись (AGENTS.md: «Weave не изменяется
ради Trellis» — тот же принцип для остальных источников §3 плана).
