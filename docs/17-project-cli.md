# CLI для создания приложений и подключения возможностей

**Статус: идеи и проект направления, 2026-09-30.** Пользователь предложил мастер создания
приложения по образцу Vite: выбрать платформы, основу приложения и нужные возможности,
получить готовый проект без ненужных интеграций. Документ сохраняет обсуждение для
последующего расширения; архитектура, команды и этапы ниже — предложения, не утверждённый
контракт. Реализация CLI не начата.

## 1. Зачем

Библиотека уже разделена на модули. Следующий уровень удобства — помочь разработчику
собрать из них приложение, не изучая сначала весь граф зависимостей и платформенные
особенности. Результат работы мастера: проект можно открыть, собрать и запустить.

CLI создаёт исходники и конфигурацию, подключает выбранные интеграции и объясняет
следующие действия. Под «разворачиванием» первой версии понимается локальное создание
проекта, а не публикация в App Store, настройка аккаунта разработчика или серверный deploy.

Цель — сократить ручную настройку, сохранив обычную разработку в Xcode. Пользователь
должен понимать и владеть созданным проектом, иметь возможность продолжить без CLI.

## 2. Как может выглядеть мастер

Имена команд условные; публичное имя утилиты выбирается отдельно.

```text
create-app MyApp

Платформы:
  ✓ iPhone / iPad
  □ Mac
  □ Apple TV
  □ Mac Catalyst

Основа приложения:
  ● AppShell — приложение целиком
  ○ UIKit — обычное приложение с нодами
  ○ SwiftUI — приложение с интеграцией нод

Возможности:
  ✓ Состояние — StateCore
  □ Реактивные потоки — AsyncRay
  □ SQL — GRDB
  □ Настройки — UserDefaults
  □ Файлы и кэш
  □ HTTP
  □ WebSocket

Пример:
  ● Минимальный экран
  ○ Список с загрузкой данных
  ○ Локальное приложение с SQL
```

Это целевой интерфейс. Пункт появляется в выпущенном CLI только при наличии работающего
шаблона и проверки соответствующей комбинации. SwiftUI-интеграция не считается готовой
только потому, что её можно перечислить в меню. Mac требует соответствующей основы,
а не механического добавления UIKit-target.

Состояние и другие обязательные зависимости выбранной основы показываются как необходимые,
а не как флажки, которые можно выключить и получить неработающий проект.

После выбора выводится конкретный план: файлы, targets, зависимости и необходимые шаги.
Повторять подтверждение каждого пакета не нужно. Для конфликтов и перезаписи существующих
файлов действует отдельная проверка; создание по умолчанию — в новой папке.

## 3. Выбираем возможности, вычисляем зависимости

Пользователь выбирает «экран на нодах», «SQL» или «HTTP», а не вручную отмечает все
технические модули. Генератор вычисляет транзитивные зависимости и показывает результат:

```text
Приложение: MyApp
Платформа: iOS
Основа: AppShell
Возможности: HTTP, AsyncRay

Будут созданы приложение, тесты и минимальный экран.
Внешние пакеты: Espalier, AsyncRay.
GRDB не требуется.
```

Нужны проверки совместимости: поддерживаемые платформы, toolchain, конфликты интеграций,
совместимые версии шаблона и библиотеки. Ошибка выбора объясняется до записи проекта.
Нельзя молча игнорировать несовместимую возможность или добавлять неподдерживаемый target.

Важно различать три обещания:

1. Модуль не используется и не импортируется приложением.
2. Модуль не собирается и не включается в итоговый продукт.
3. Пакет не разрешается и не скачивается менеджером зависимостей.

Одно не означает другое. Отказ от продукта SQL не гарантирует отсутствие разрешения GRDB,
если он объявлен зависимостью общего пакета. На этапе проектирования packaging нужно
проверить реальное поведение SwiftPM. Для независимой установки тяжёлые интеграции могут
потребовать отдельных пакетов. CLI не должен обещать того, чего структура пакетов не даёт.

## 4. Три части системы

| Часть | Ответственность |
|---|---|
| CLI | Вопросы, чтение конфигурации, проверка окружения, план и запуск генерации |
| Шаблоны | Структура приложения, исходники, схемы, тесты и примеры |
| Каталог интеграций | Возможности, зависимости, ограничения платформ и изменения проекта |

Логику выбора и проверки графа отделяем от интерактивного терминала. Один механизм
генерации используется и мастером, и командой с аргументами, и конфигурационным файлом.

Файлы и типы называются по содержимому: например, ProjectConfig, TemplateCatalog,
DependencyResolver, ProjectGenerator. Названия продукта и версии не входят в имена
внутренних модулей. Это эскизы, а не обязательный набор абстракций.

## 5. Что здесь означает «плагин»

Плагин генератора — описание интеграции, которая добавляет определённую возможность.
Например, SQL-интеграция может добавить GRDB, место открытия базы, начальную миграцию
и тест. Она не загружается динамически в готовом приложении.

Для интеграции нужны:

- стабильный id, версия, описание и поддерживаемые платформы;
- обязательные и конфликтующие возможности;
- пакеты и products, которые действительно нужны;
- необходимые параметры и их значения по умолчанию;
- список создаваемых файлов и настраиваемых targets;
- критерии проверки и инструкция пользователю.

Первый каталог — встроенные проверенные интеграции. Внешний marketplace и выполнение
произвольных пользовательских скриптов не входят в первую версию. Сторонние шаблоны
в будущем должны иметь явный источник и версию; запуск их кода не должен происходить
незаметно при просмотре каталога или предварительного плана.

## 6. Результат генерации

Обычный проект с исходниками, который можно развивать самостоятельно:

- приложение и схемы для выбранных платформ;
- один работающий экран и минимальные осмысленные тесты;
- только необходимые пакеты и точки подключения выбранных сервисов;
- README с запуском, проверками и пояснением структуры;
- конфигурация выбора и версия схемы этой конфигурации;
- версии генератора, шаблона и разрешённых зависимостей для воспроизводимости.

Сервисы передаются через инициализаторы, а не скрытый глобальный контейнер. Базовые
шаблоны не навязывают обязательные ViewModel/Repository-протоколы и дополнительные слои.
Repository появляется в примере с сохраняемыми/сетевыми данными, где он нужен.

Пользователь задаёт имя проекта и bundle identifier. Signing team при необходимости
настраивается отдельно. Генератор не встраивает учётные данные и не обещает запуск на
физическом устройстве без необходимых настроек подписи.

## 7. Xcode-проект и способ генерации

До реализации выбрать один механизм и проверить его на эталонном приложении:

| Вариант | Преимущество | Что нужно проверить |
|---|---|---|
| Готовый шаблон xcodeproj | После создания открывается напрямую в Xcode | Безопасная замена имён, добавление targets и поддержка версий формата |
| Описание проекта через внешний генератор | Удобнее выражать комбинации платформ и зависимостей | Дополнительная установка, версии, обязанность повторной генерации |
| Собственный генератор xcodeproj | Полный контроль | Стоимость реализации и сопровождения формата |

Не выбирать инструмент только по удобству разработки CLI. Важен путь пользователя
«создал → открыл → запустил», включая установленный Xcode и доступные Simulator runtimes.
SwiftPM отвечает за библиотеки; способ получения полноценного приложения и схем должен
быть отдельным явно проверенным решением.

Предпочтение для первого прототипа — минимальное число новых инструментов у пользователя.
Если используется внешний генератор, его роль, версия и ограничения фиксируются в README.

## 8. Команды и воспроизводимость

Предлагаемый минимальный набор:

```text
create-app MyApp               # интерактивный мастер
create-app --config app.json   # тот же результат без вопросов
app doctor                    # проверка окружения существующего проекта
```

Возможные следующие команды:

```text
app add sql
app add websocket
app plan --config app.json
```

Это концептуальные примеры, не готовый синтаксис. У мастера должны быть аргументы или
конфигурация для всех существенных выборов. В CI отсутствующий обязательный параметр
даёт понятную ошибку вместо бесконечного ожидания ввода.

Конфигурация сохраняет прямые выборы пользователя отдельно от вычисленных зависимостей.
Порядок файлов и генерация детерминированы. Изменение каталога не должно незаметно менять
проект при повторении той же зафиксированной конфигурации. Проверять чистую генерацию
одинакового набора входов; не включать случайные даты в каждый файл.

`doctor` сообщает о найденном Xcode, toolchain, зависимостях и доступных целях запуска.
Он не меняет окружение и не устанавливает инструменты без отдельной команды.

## 9. Создание и последующее добавление — разные задачи

Первая версия создаёт проект в новой папке. Генерация проходит сначала во временную
папку, проверяет результат и переносит его в назначение; при неуспехе не оставляет
полусобранный проект вместо пользовательских файлов.

Для `app add` позже понадобятся:

- распознавание версии конфигурации и текущей структуры проекта;
- предварительный diff, обнаружение конфликтов и сохранение пользовательских правок;
- идемпотентность: повторное добавление не дублирует файлы, пакеты и настройки;
- понятная граница файлов, которые ещё управляются генератором;
- восстановление после частично выполненной операции.

Обновление библиотеки, обновление шаблона и миграция пользовательского кода — отдельные
операции. Не перегенерировать изменённое приложение целиком ради обновления пакета.
Команда удаления интеграции ещё сложнее: пользователь мог начать использовать её API.
Её не включаем в первый выпуск.

## 10. Возможности для каталога

| Возможность | Что добавляет шаблон | Условие готовности |
|---|---|---|
| AppShell | Точка входа, окно, экран, навигация | Рабочий шаблон выбранной платформы |
| Ноды внутри UIKit/AppKit | Платформенный контейнер и пример дерева | Проверенный адаптер без обязательного AppShell |
| AsyncRay | Модель с подпиской и явным временем жизни | Совместимость с закреплённой версией |
| Preferences | Настройка интерфейса и её сохранение | Готово: `StorageCore`, `StorageFoundation` (S1 плана storage) |
| Files / Cache | Конфигурация каталогов и пример использования | Реализация и контракты очистки |
| GRDB | База, миграция, наблюдаемая выборка | Проверка версии и платформ; политика хранения tvOS |
| HTTP | Конфигурация клиента и обработка ошибки | Рабочий клиент из плана сети |
| WebSocket | Владение соединением, состояние и завершение | Определённый протокол примера и reconnect |
| Разрешения | Ключи `Info.plist` для выбранных видов, пример экрана объяснения и отказа | Реализация плана [18-permissions.md](18-permissions.md) (этап P5) |

Каталог не предлагает будущий API как уже готовый. Хранение и сеть зависят от реализации
`docs/14-storage-and-network.md`. Пример HTTP работает с локальным тестовым сервером или
явно выбранным endpoint; случайный внешний сервис не нужен для успешных тестов шаблона.

## 11. Первая версия и расширение

Сначала вручную довести одно эталонное приложение до хорошего состояния. Только затем
выделять шаблоны и автоматизировать создание.

| Этап | Результат |
|---|---|
| G0 | Эталон: iOS + AppShell, один экран, схема запуска и тесты; выбран способ генерации |
| G1 | Неинтерактивная генерация из конфигурации, валидация имён и зависимостей |
| G2 | Интерактивный мастер поверх G1, README, doctor, понятные сообщения об ошибках |
| G3 | Опциональные AsyncRay и HTTP, если соответствующие API уже готовы |
| G4 | Mac, tvOS и Catalyst с собственными проверенными шаблонами |
| G5 | Preferences, Files/Cache и GRDB после готовности слоя данных |
| G6 | Добавление интеграций в существующий проект с diff и защитой пользовательских правок |

Полная матрица всех комбинаций быстро растёт. Выделить поддерживаемые профили и отдельно
проверять зависимости/конфликты; не заявлять любую комбинацию рабочей без проверки.

За пределами первого выпуска: marketplace, собственный package manager, автоматическая
публикация в App Store, настройка сертификатов, серверный deploy, миграция произвольного
приложения на библиотеку и универсальная архитектура для всех типов приложений.

## 12. Проверки

- Генерация в пустую папку, путь с пробелами, неверное имя, занятый каталог, отмена мастера.
- Неинтерактивный режим не спрашивает ввод; одинаковая конфигурация даёт одинаковые файлы.
- Пакеты и products соответствуют выбору, отсутствуют неразрешённые placeholders.
- Каждый поддерживаемый шаблон собирается; минимальные тесты запускаются на своей цели.
- Для optional-интеграции проверяется и её наличие, и отсутствие.
- Схемы shared и доступны командной строке; bundle identifiers не конфликтуют между targets.
- README содержит рабочие команды и явно отмечает требования к подписи/устройствам.
- Прогоны библиотеки выполняются по AGENTS.md, длительные — с deadline и диагностикой.
- Smoke-проверка запуска создаваемого приложения на Simulator отделена от проверки
  на физическом устройстве. Недоступные проверки не считаются пройденными.

## 13. Открытые решения

1. Публичное имя CLI, язык реализации, способ установки и обновления.
2. Где живут CLI и шаблоны: отдельный репозиторий или часть текущего; как связаны версии.
3. Готовый xcodeproj или описание проекта с генератором; какие внешние инструменты нужны.
4. Отдельные пакеты для интеграций и реальные гарантии «не скачивать ненужное».
5. Состав первого поддерживаемого профиля и доступность HTTP к моменту выпуска.
6. Формат конфигурации, versioning и граница владения файлами при будущем `app add`.
7. Нужен ли SwiftUI-профиль и в каком объёме будет проверена интеграция.
8. Когда открывать каталог для сторонних расширений и как проверять их происхождение.
