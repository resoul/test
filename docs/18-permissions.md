# Разрешения системы: Permission

**Статус на 2026-10-09: P0–P4 выполнены (P2: UI-тест Simulator нестабилен, см. §13; P3 и P4 — §14 и §15, проверены сборкой и тестами пакета, не на Simulator); P5 не начат: нет самого CLI. План от 2026-10-01.** Пользователь попросил собрать работу с разрешениями
(камера, микрофон, фото, уведомления, геолокация и другие) в одном месте. Реализация идёт по этапам, см. разделы 11–13;
псевдокод в разделе 5 показывает направление API. Что именно доступно на каждой
платформе, здесь не утверждается по памяти: матрицу заполняет этап P0 проверкой SDK.

## 1. Зачем отдельный слой

У каждой системной возможности свой фреймворк, своя форма «статуса» и свой способ спросить:
`AVCaptureDevice`, `PHPhotoLibrary`, `UNUserNotificationCenter`, `CLLocationManager`,
`CNContactStore`, `EKEventStore`, `CBManager`, `SFSpeechRecognizer`, `ATTrackingManager` и другие.
Приложению нужно одно и то же: узнать состояние, спросить, объяснить отказ, отправить в Настройки,
заметить, что пользователь передумал. Если каждый экран делает это сам, получаются одинаковые
ошибки: запрос не вовремя, падение из-за отсутствующей строки в `Info.plist`, молчаливая кнопка после
отказа, устаревший статус после возврата из Настроек.

Цель — одна модель и один порядок действий для всех видов разрешений, с честным признанием различий.
Это не обёртка, скрывающая платформу: возможности, которых у вида разрешения нет, остаются видны.

## 2. Что известно о системе (проверить на P0)

Эти свойства определяют форму API; каждое подтверждается на P0 по документации и пробой, не памятью.

- **Спросить можно один раз.** После отказа системное окно больше не показывается; остаётся
  отправить пользователя в Настройки.
- **Узнать статус не значит спросить.** Чтение статуса окна не открывает.
- **Без строки назначения запрос роняет приложение** у многих видов (ключ `NS…UsageDescription` в
  `Info.plist`). Слой обязан проверить ключ до запроса и вернуть ошибку, а не упасть.
- **Статус не одноцветный.** Фото и контакты имеют «ограниченный доступ», уведомления — «временный»,
  геолокация — «при использовании» и «всегда» и точность; ещё есть «ограничено» (родительский контроль,
  MDM), когда спросить нельзя вовсе.
- **Статус меняется вне приложения** — в Настройках. Приложение узнаёт об этом при возврате на
  передний план, а не по событию.
- **Не у каждого вида есть простой «статус».** У некоторых он выводится косвенно или недоступен
  (в частности локальная сеть); P0 выясняет, что честно можно обещать для каждого вида.
- **Окно запроса показывается только приложению на переднем плане**, по одному за раз.

## 3. Границы

Входит: единый тип статуса, список видов разрешений, запрос с учётом состояния, ошибки, проверка строк
`Info.plist`, переход в Настройки, наблюдение изменений, подмена в тестах, примеры экранов объяснения.

Не входит: сами возможности (съёмка, выбор фото, показ уведомлений, получение координат) — их делают
приложение или будущие модули; запись и хранение пользовательских данных, которые разрешения открывают;
Keychain и биометрия (`LocalAuthentication`) — отдельный вопрос, это не разрешение со статусом; серверная
сторона push-уведомлений.

## 4. Модули

| Модуль | Содержание | Зависимости |
|---|---|---|
| `PermissionCore` | Виды, статус, ошибки, протокол поставщика, запись и подмена для тестов | Foundation |
| `PermissionSystem` | Поставщики для системных фреймворков, каждый под `#if canImport(...)`; проверка `Info.plist`; Настройки | PermissionCore, платформенные фреймворки |
| `PermissionAsyncRay` (необязательный) | Наблюдение статуса как поток для привязки к `State` | PermissionCore, AsyncRay, StateCore |

`PermissionCore` собирается без Apple UI. Нет импортов UIKit/AppKit вне адаптеров; `#if os(...)`
запрещён, различия платформ — через `#if canImport(...)` и значения доступности. Поставщик одного
вида не знает о других. Приложение владеет экземпляром и передаёт его внутрь; глобального единственного
экземпляра нет. Хранение факта «объяснение уже показывали» — через Preferences из
[14-storage-and-network.md](14-storage-and-network.md), а не отдельным механизмом.

## 5. Контракт (направление API)

```swift
public enum PermissionKind: Sendable, Hashable { /* camera, microphone, photos, notifications, … */ }

public enum PermissionStatus: Sendable, Equatable {
    case notDetermined          // ещё не спрашивали: можно показать системное окно
    case granted(Grant)         // полный доступ или его вариант
    case denied                 // отказ: окно больше не покажется
    case restricted             // спросить нельзя: родительский контроль, MDM
    case unavailable(Reason)    // на этом устройстве или платформе нет
}

public protocol PermissionProvider: Sendable {
    func status(of kind: PermissionKind) async -> PermissionStatus
    func request(_ kind: PermissionKind) async throws(PermissionError) -> PermissionStatus
}
```

- `status` не показывает окно и не имеет побочных эффектов. `request` показывает системное окно только
  при `notDetermined`; в остальных состояниях возвращает текущий статус, не пытаясь спросить.
- Варианты доступа (`Grant`) — перечисление с вариантами, нужными конкретным видам (ограниченный,
  временный, при использовании, всегда; точность). Состав уточняет P0; лишние варианты не добавляем.
- Несколько одновременных `request` одного вида объединяются в один запрос, все ждущие получают один
  результат. Запросы разных видов идут по одному: система показывает одно окно за раз.
- Ошибка отличает: нет строки назначения (с именем ключа), приложение не на переднем плане, запрос
  невозможен на платформе, ошибка системы. Отказ пользователя — не ошибка, а `denied`.
- **Отмена.** Отмена задачи прекращает ожидание вызывающего и бросает отмену; системное окно и его
  результат слой не отменяет и не откатывает: после ответа пользователя `status` покажет итог.
  Нельзя обещать закрытие уже показанного окна.
- Переход в Настройки — отдельная операция платформенного модуля; результат её вызова не означает, что
  пользователь что-то изменил.

### Наблюдение

Статус может меняться вне приложения. Слой даёт `statusChanges(of:)`: текущий статус, затем каждое
отличающееся значение, найденное повторным чтением при возврате приложения на передний план и после
собственного запроса. Это перечитывание, а не журнал: если статус сменился и вернулся между проверками,
изменения не будет. Поток держит только последнее значение, как настройка, не как событие.

## 6. Как использовать

```text
Экран открывается → status(of:) → State модели
notDetermined → объяснение (свой экран) → request → State
denied/restricted → объяснение, что сделать → открыть Настройки
возврат на передний план → status(of:) → State обновился → экран изменился
```

Модель экрана держит статус в `State` и показывает его через ноды; обращения к системе идут из
`Task`, который модель отменяет сама. Пример объяснения перед системным окном и пример отказа с кнопкой
«Открыть Настройки» входят в демо. Тексты и порядок показа решает приложение: библиотека не навязывает
экран, но не даёт запросить разрешение там, где ключа в `Info.plist` нет.

## 7. Связь с проектом CLI

Каталог возможностей [17-project-cli.md](17-project-cli.md) добавляет возможность «Разрешения»: шаблон
вносит нужные ключи `Info.plist` (и права для песочницы Mac) для выбранных видов и проверяет, что
для каждого выбранного вида строка назначения не пустая. Текст строки пишет человек; генератор
подставляет заметный маркер, который проверка не пропускает, пока он не заменён.

## 9. Проверки

- Контракты — на подмене поставщика: заранее заданные статусы и ответы, внедряемая очерёдность.
- Системные окна на Simulator ограничены: часть видов (камера, Bluetooth и другие) там недоступна или
  ведёт себя иначе. Что проверено на Simulator, а что нет, записывается; «на устройстве» без устройства
  не пишется, пишется «нет доступа».
- Отдельно проверить: запрос без ключа (ошибка, не падение), объединение запросов, возврат из Настроек,
  ограниченный доступ, отказ и повторный запрос, приложение не на переднем плане, отмена во время окна.
- `swift build`, `swift test`, формат по `AGENTS.md`; поставщики — на Simulator iOS и tvOS и на Mac по
  матрице P0 (на tvOS и Mac видов меньше).

## 11. P0: результаты на 2026-10-02

### Что показала проба на iOS Simulator (iOS 27.0, iPhone 17)

Проба — экран `PermissionProbe` в демо (`PERMISSION_PROBE=1`): сырые статусы системы без нашего
слоя и запрос по кнопке; `Demo/iOSUITests/PermissionProbeTests` проходит.

- **Начальные статусы** новой установки читаются без окна: камера, микрофон, фото, уведомления,
  геолокация, контакты, календарь и напоминания — `notDetermined`; Bluetooth — `allowedAlways`
  (Simulator не имеет настоящего Bluetooth и сообщает «разрешено»).
- **Уведомления.** Системное окно «“Layout Demo” Would Like to Send You Notifications» с кнопками
  «Don’t Allow» и «Allow»; после «Allow» статус `authorized`; повторный `requestAuthorization`
  окна не показывает и сразу отвечает.
- **Запрос без ключа** (ключей в `Info.plist` демо нет). Камера, микрофон, фото и контакты:
  система **завершает приложение**, в журнале — «The app's Info.plist must contain an
  `NS…UsageDescription` key» с названием ключа. Геолокация: система пишет в журнал то же
  предупреждение (`NSLocationWhenInUseUsageDescription`), приложение продолжает работать, окна нет.
  Календарь и напоминания: ни падения, ни окна, ответ «отказано». Вывод для слоя: отсутствие ключа
  то убивает приложение, то молчит, поэтому проверять ключ надо **до** запроса.
- Передача окружения в приложение через `simctl launch` в этой среде не сработала (SYNC и TOAST пробы
  тоже не открылись); пробы запускаются UI-тестом с `launchEnvironment`.

### Ответы на вопросы из раздела 10

- **Первые виды:** камера, микрофон, фото, уведомления, геолокация «при использовании». Остальные —
  по заявке (P3).
- **Какой доступ даёт каждый вид:** таблица выше; формы доступа — `Grant`: полный, ограниченный (фото,
  контакты с iOS 18), условный (уведомления), временный (уведомления в App Clip, iOS и Catalyst),
  «при использовании» и «всегда» (геолокация).
- **Что нельзя узнать без побочных эффектов:** локальную сеть — статуса нет; результат запроса
  геолокации и Bluetooth приходит позже, а не возвратом.
- **Точность геолокации:** отдельная ось (`accuracyAuthorization` есть на всех платформах), в
  `PermissionStatus` не входит; тип для неё вводится, когда понадобится приложению.
- **Mac Catalyst:** API тех же видов, что у iOS, по матрице; настройки Mac и песочница (права
  `com.apple.security.personal-information.*`) не изучались — **нет проверки**, остаётся для P2.
- **Биометрия:** не входит.

### Не проверено на P0

Запуск проб на tvOS, Mac и Catalyst (только компиляция против их SDK); устройство; статусы
«ограничен доступ» и «только добавление» на живой системе (выдача прав через `simctl privacy` до
запуска сбрасывается переустановкой приложения тестом); возврат из Настроек; ключи Bluetooth,
движения, медиатеки, локальной сети и добавления фото; права песочницы Mac.

## 12. P1: результаты на 2026-10-02

Сделано: цель и продукт `PermissionCore` (только Foundation, собирается и на Linux по составу, но
Linux не цель проекта): `PermissionKind`, `PermissionStatus` (`Grant`, `Reason`), `PermissionError`,
`PermissionProvider`, `Permissions` (actor) и `InMemoryPermissionProvider` для тестов.

- **Виды.** Камера, микрофон, фото (`readWrite`/`addOnly`), уведомления, геолокация
  (`whenInUse`/`always`). Уровни — разные разрешения; каждый вид сообщает ключи `Info.plist`, которые должны
  быть заданы и непусты до запроса (`usageDescriptionKeys`); у уведомлений их нет.
- **Спрашивать.** `Permissions.request` показывает окно только при `notDetermined`; при любом другом
  статусе возвращает его, не обращаясь к системе. Отказ человека — `denied`, не ошибка. Одновременные
  запросы одного вида делят один и получают один результат. Разные виды идут по одному, в порядке
  прихода. Ошибка поставщика достаётся всем ждущим и не запоминается.
- **Отмена.** Отмена задачи вызывающего прекращает его ожидание (`PermissionError.cancelled`), запрос и
  окно остаются; ответ человека сохраняется, `status` и наблюдатели его видят.
- **Наблюдение.** `statusChanges(of:)` — текущий статус, затем каждый отличающийся, найденный повторным
  чтением (`refresh()` — вызывать при возврате на передний план) и после собственного запроса; поток
  держит последнее значение. Статус, сменившийся и вернувшийся между чтениями, не виден. Наблюдатели одного вида
  независимы, другие виды не получают чужого.
- **Подмена.** `InMemoryPermissionProvider`: заданные статусы, ответ человека на запрос, задержка запроса
  (окно открыто), счётчики чтений и запросов, наибольшее число одновременных запросов.
- **Не сделано из раздела 5:** `PermissionProvider` системы (P2); проверка ключей `Info.plist` (P2: её
  делает поставщик); наблюдение за возвратом на передний план (P4); виды сверх первых пяти (P3).
- **Проверено:** 19 контрактных тестов на подмене (чтение без запроса, запрос только при `notDetermined`,
  отказ как статус, повторный запрос без обращения к системе, уровни как разные разрешения,
  объединение пяти запросов, очередь разных видов с «одним открытым окном», отмена одного ждущего,
  сохранение ответа после отмены, отмена до запроса, ошибка всем ждущим и повтор, неудача не держит
  очередь, наблюдение без повторов, склейка быстрых смен, независимые наблюдатели, медленный
  наблюдатель, освобождение наблюдателя, ключи видов) три раза подряд на Mac. Проверка тестов поломкой:
  запрос при любом статусе, отсутствие очереди видов, повторы наблюдателям — каждая ловится (последняя
  — после переделки теста: буфер «только последнее» склеивал повторы, и первый вариант теста их не видел).
- **Платформы.** `PermissionCore` собирается для iOS Simulator, tvOS Simulator и Mac Catalyst; приложения
  демо (с экраном пробы) — для iOS, tvOS и Mac. Сборка для tvOS нашла то, что предсказывала
  матрица: камера и микрофон там только с tvOS 17, а у демо минимум 16 — код пробы ограждён
  проверкой доступности.
- **Не проверено:** тесты `PermissionCoreTests` на Simulator и tvOS; настоящий поставщик.

## 15. P4: результаты на 2026-10-09

Сделано: `Permissions.follow(_:)`, потоки переднего плана в адаптерах, цель `PermissionAsyncRay`, экран

- **Возврат на передний план.** `Permissions.follow(_:)` берёт последовательность `Bool` «приложение

  изменения, найденного повторным чтением; подписка холодная, отмена снимает наблюдение. Привязка к экрану:
  `permissions.statusRay(of: .camera).bind(to: model.camera)`.

  изменила; ошибка запроса (например, нет строки) текстом на экране. Тексты по статусу собраны в `Screen`.
  Экран читает статус через `statusChanges` и `follow`, поэтому смена в Настройках меняет его при возврате.

  читает, отмена завершает); `PermissionAsyncRayTests` — 3 (текущий и следующие статусы, независимые подписки
